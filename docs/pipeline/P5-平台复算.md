# P5 · 平台链路复算（注入测试集 62 份）

> 目标：把用户实验的 96%/0%/100% **放在一边**，用平台**自己既有**的 `checker/generator.js` + `ruleExecutor` 跑一遍注入测试集，给出**平台自己的真实数字**。
> 结论先行：**误扣率与满分正确性平台是干净的（0.00% / 100%），但检出率只有 42.62%——不是 96%，也不是 98.31%。**

## 1. 复算对象与"既有链路"的确切含义

### 1.1 平台真正的评分链路（读代码确认，非猜测）

```
server/src/services/projectGrading.js:181  gradeWithChecker()
  ├─ 185: rules = JSON.parse(question.checkerScript)      ← 题目已生成的规则 JSON
  ├─ 192: const checkerRes = await runRules(rules, stuDir) ← 确定性客观层（本次复算对象）
  ├─ 202-219: 主观分项 → gradeSubjectiveItems(...) LLM 评分（23 分）
  └─ 223: totalScore = clamp(Σ分项, 0, question.maxScore=100)
```

- **客观层**：`runRules`（`server/src/infrastructure/rule/executor.js`）——**纯函数**，只依赖 `node:fs`/树解析，零 DB、零网络、零 LLM。可完全离线复现。
- **主观层**：23 分交 LLM 评分（`gradeSubjectiveItems`），**不属于** `checker/generator.js + ruleExecutor` 这一层，本次未复算（见 §6 边界声明）。

### 1.2 题目 353 的既有 checker（DB 只读导出）

```sql
SELECT id,title,max_score,checker_status,script_len... FROM questions WHERE id=353;
-- 353 | 作业：用户管理系统（前端） | 100 | ready | checker_script 12805 字符 | rubric_items 已缓存
```

| 项 | 值 |
|---|---|
| checker_status | **ready**（2 轮自举校准后"校准满分就绪"） |
| max_score | 100 |
| objective_items | **75 条 / 77 分** |
| subjective_items | 2 条 / 23 分（s1 主页布局权限 14、s2 规范健壮 9） |
| 规则类型分布 | `file_exists` 8 · `contains_text` 63 · `contains_regex` 4 |
| 校准日志 | round1 `totalScore=75/100`（负例覆盖 73）→ round2 `totalScore=77/100`（负例覆盖 75，跳过 0，weak 0）→ ready |

> ★ **关键事实 1**：`checker/generator.js` 一共支持 11 种 rule_type，本题的 AI 生成结果**一条都没用** `fact` / `ast_pattern` / `syntax_check` / `count_imports` 等结构性规则，75 条里 67 条是「某文件里有没有某个字符串」。
> ★ **关键事实 2**：**既有 checker 已经 ready，无需重新生成**。任务书预留的"一次 LLM 调用"因此**没有发生**——本轮全程未读取、未使用 `deepseek_api_key`（也就不用担心明文泄漏）。

### 1.3 为什么没有调用 `generateChecker()`

`server/src/infrastructure/ai/checker/generator.js` **强依赖 DB 且必须写库**（`prisma.question.update` 至少 4 处：置 `generating`、写 `inputsSnapshot`、回写 `rubricItems`、写 `checkerScript`/`checkerStatus`），第 85 行还会对 `generating/calibrating` 状态做幂等短路。本轮铁律是**只读 DB**，因此：

> **结论：`generator.js` 无法在"只读 + 不启服务"约束下独立复算；但既有链路（checker 已 ready 时）可以——`runRules` 是纯函数。**

## 2. 方法（可逐条复查）

### 2.1 归因口径的定义

平台交付物是一组"扣分项"。要判"某个注入错误是否被平台抓到"，必须先定义归因。本报告给出**两套**口径，并明确哪套是头条数字。

**（A）机械口径——只看位置，不看语义**

| 代号 | 定义 |
|---|---|
| A 组级 | 该错误 `rubric` 映射到的平台分组内有任何扣分 |
| B 文件级 | 有任何扣分项的 `params.path` == 该错误的 `file` |
| C 严格 | 同时满足 A 与 B（扣分项既在该组、又指向该文件） |
| D 宽松 | A ∪ B |

rubric → 平台分组映射（`一、项目初始化`→`项目初始化`、`二、路由与跳转`→`路由与页面跳转`、`三、登录功能`→`登录功能`、`五、Pinia`→`Pinia状态管理`、`七、个人信息`→`个人信息展示`、`八、管理员列表`→`管理员用户列表`；`六、主页布局权限`→主观 s1、`九、规范健壮`→主观 s2，**平台客观层不覆盖**）。

**（B）语义口径（★头条数字采用）——只有"对应该缺陷的那条规则真的失分"才算检出**

机械口径会**高估**：例如 `梁勇20` 同份里 L2（密码正则放宽）与 L3（不跳转）同在 `Login.vue`，唯一扣分项 `a25` 实际只对应 L2，机械口径却把 L3 也算检出。语义口径逐类给出唯一判定谓词（下表可对代码逐条复核）：

## 5. 与手写检测器的差距归因

| # | 根因 | 证据 | 影响 |
|---|---|---|---|
| **1** | **规则表达力坍缩为"文本存在性"** | 75 条规则 = `file_exists`×8 + `contains_text`×63 + `contains_regex`×4，**零** `fact` / `ast_pattern` / `syntax_check` / `count_imports` / `dir_contains_file`。而平台**明明实现了**这 11 种（`executor.js` 分派齐全） | 直接决定：只要"token 还在"，缺陷就看不见。L1/L3/L4/L5/H2/S5/S6/S7/S9 全部因此漏检 |
| **2** | **子串匹配没有语义边界** | `a19/a28` 用 `contains_text '/user'` 判"登录成功跳转"，被 `'@/stores/user'` 命中 | L3 全漏（7/7），且这类缺陷（致命/重要）在真实作业里很常见 |
| **3** | **校准目标错位：优化"标准包得满分"，不优化"抓缺陷"** | `generator.js:309` 就绪条件是 `calibScore >= max_score - subSum` 且 `realDeductionSum === 0`——**只要标准包不失分就 ready**。round1 75→round2 77 的"校准"改的是参数，不是覆盖面 | 校准 100% ≠ 检测 100%：本题 **校准满分就绪，真缺陷检出 42.62%** |
| **4** | **负例验证是自证式的，给出了虚假信心** | `ruleMutator.js` 对 `contains_text` 的变异 = "把该 text 替换成干扰串" → 规则必然失分。这是"证明规则接线了"，**不是"证明规则能抓真缺陷"** | 实测 `负例验证：覆盖 75，跳过 0`、weak 0 —— 全绿，却漏掉 70/122 个真错误 |
| **5** | **判定粒度 1 分/条，与评分标准 9 项分值脱钩** | 评分标准九项（教师版合计 110，`rubricItems` 归一为 100）；checker 客观组分值 `项目初始化9 / 路由10 / 登录14 / 注册18 / Pinia9 / 个人信息5 / 管理员12`，与 rubricItems 的 `9/9/18/18/9/5/9` 不一致（路由 +1、登录 −4、管理员 +3） | 分值语义漂移；且大量 1 分项让"致命缺陷只扣 1 分"（如 H1 缺邮箱列扣 1 分 = 次要），严重度与分值不匹配 |
| **6** | **重复 token 白送分** | 7 组同文件同 token 重复计分：`Register.vue` 的 `required` 被 a38/a40/a42/a44 **四次**计分、`notification` 两次；`Login.vue` 的 `required`/ `notification`/`/user` 各两次 | 稀释区分度，抬高标准包与"擦边"提交的分数 |
| **7** | **110 分既有缺陷被"归一化"掩盖，而非修复** | 教师评分标准九项实为 10+10+20+20+10+15+5+10+10=110，题目 `max_score=100`。`summarizeRubricItems` 把它压成合计 100（9/9/18/18/9/14/5/9/9） | 平台**没有暴露**这个不一致，但代价是分值被重排（登录 −4、管理员 +3），教师无法从规则里看出自己的九项分值去哪了 |

**与手写检测器"同项不同质"的提醒**：
误扣 0% / 满分 100% 两个指标两边持平，但**能力不是一回事**——手写检测器识别"语义等价改写"是主动判断，平台的 0% 是**规则覆盖不到所以打不着**。同理，检出率差距（42.62% vs 90.98%/98.31%）不是调参能补的，是**表达力代差**。

## 6. 边界声明（本次"没算"的部分，以及为什么）

1. **主观 23 分未复算**：`主页布局权限 14 + 规范健壮 9` 由 `gradeSubjectiveItems` 调 LLM 评分（温度 0）。它不属于任务指定的 `checker/generator.js + ruleExecutor` 链路，且引入 LLM 非确定性。**因此本报告的"满分正确性 100%"仅指确定性层 77/77。**
2. **重新生成 checker 未执行**：`generateChecker()` 必须写库（≥4 处 `prisma.question.update`）且需要 LLM 调用，与"只读 DB / 不启服务 / 不需要就不调 LLM"约束冲突；且既有 checker 已 `ready`，重新生成只会得到一份**不同的**规则（LLM 非确定性），反而失去"平台既有链路"的语义。
3. **未执行学生代码**：全程纯静态文本读取 + 规则匹配（这与平台 `runRules` 的真实行为一致）。
4. **客观层结果 100% 可复现**：同类注入任意一份上结果完全一致（无一处例外），因为 `runRules` 是纯函数、无随机性。

## 7. 结论：平台能否作为明日灰度依据？

### ❌ **不能——就"检出能力"而言，现状与 96% 相差一个数量级**

1. **致命错误检出 13/49 = 26.53%**：`未挂载 router`、`未挂载 Pinia`、`未注册 Antd`、`import 路径失效`、`onSubmit 首行 return` —— **五类"应用直接跑不起来"的缺陷，平台 100% 漏检**。
2. **12/50 份含致命错误的提交被判客观满分**：这不是"少扣几分"，是"把跑不起来的项目判成没问题"。灰度若基于此，会把最需要人工介入的作业直接放过。
3. **语义层检出 10.71%**（28 项里只抓到 L2 一项）；而真实教学场景中语义缺陷占比最高。
4. **校准绿灯具有误导性**：`ready` + `校准满分就绪 77/100` + `负例验证覆盖 75、weak 0` 会让人以为"检查器质量很好"。**这套自检证明不了检测能力**，必须换成"注入测试集回归"。

### ✅ 可以采信的部分

- **误扣率 0.00%（6/6）与满分正确性 100%（12/12，确定性层）**：平台在"不冤枉"这个方向是安全的，可作为**低风险下限**使用（例如先只用作"扣分提示"而非"最终成绩"）。
- **平台链路可独立复算**：checker 一旦 `ready`，`runRules` 纯函数、零 DB、零网络，62 份全量复算秒级完成 —— **灰度的回归验证完全可以自动化**（`docs/pipeline/scripts/p5-recompute.mjs`）。

### 灰度前的三条硬建议（按优先级）

1. **把注入测试集接进生成流程做回归门禁**：`ready` 之前先跑 122 项注入，**检出率 < 阈值（建议 ≥80%）不许 ready**。现有 `ruleMutator` 的负例验证替换或补强为真实缺陷注入。
2. **强制规则表达力下限**：本题 0 条 `fact`/`ast_pattern`/`syntax_check` 规则，而执行器**全都支持**。至少应强制覆盖：挂载点存在性（`fact`/`ast_pattern`）、import 目标文件存在性、关键函数体非空（首行 return 检测）。同时给 `contains_text` 加 token 边界（如 `'/user'` 不能命中 `'@/stores/user'`）。
3. **修分值映射**：让规则分项与 `rubricItems` 九项分值严格对齐，消除 1 分/条 + 7 组重复 token 的白送分；顺带正面处理 110 vs 100 的既有缺陷（当前是悄悄归一化）。
