# 基于 DSH 的作业级批改方案

> 状态：**设计稿（待用户裁定 + 两项前置验证）** ｜ 依据：源码查证（DSH 检出 + 本仓走查）＋ 实测数据
> 前置文档：`docs/plan/2026-10-11-智能体批改管线走查.md`（`8eaf63d`）
> 一句话：**把评分单位从「一份提交」改成「一份作业」，用一次性的 DSH 无头会话为该作业造一把尺子并量完全班。**

---

## 0. 摘要

### 0.1 核心洞察

```
旧架构：62 份提交 → 62 次独立的 LLM 评分调用  →  跨份不可比（方差 4~6 分）
新架构：62 份提交 → 1 个会话造 1 套检查器    →  一次造尺、62 次量
                    ⇒ 一致性不靠模型稳定，靠【同一把尺子】
```

### 0.2 三个关键设计判断

| # | 判断 | 依据 |
|---|---|---|
| **1** | **评分单位 = 一份作业**（不是一个学生一次提交） | 只有同一会话内才有「同一把尺子」；跨作业不可比且无需可比 |
| **2** | **分数由代码算，LLM 只造尺** | 分数若经 LLM 输出，方差必然回归（实测 temp 0 仅降 1%） |
| **3** | **会话销毁，检查器不销毁** | 会话是 transient（省内存/硬盘），检查器是 artifact（存库，几十 KB） |

### 0.3 ★与用户设想的修正与补充（共 4 处）

| # | 处 | 结论 |
|---|---|---|
| 1 | **成绩返回方式** | 改走**文件**，不走 stdout（见下） |
| 2 | **作业定死 ⇒ 检查器永不失效**（§4.4） | ✅ **采纳** —— 并指出**当前系统尚未保证**，需快照改造（§4.4.1 / V3） |
| 3 | **铁律要生态中立**（§5.1） | ✅ **采纳** —— 改为「原则 + 判据 + 各生态例示」，避免清单式漏洞 |
| 4 | **并发语义澄清 + `ai_concurrency` 不动**（§6.2.1） | ✅ **采纳** —— DSH 批改仅针对实训题，需**独立**并发配置；并补充「并发 = 同时在跑的会话数」的解释（§6.2.2） |

#### 修正 1 详情：成绩返回方式

用户设想「DSH 返回分数和评语，然后会话销毁」——**返回路径要改**：

| | 用户设想 | 建议 |
|---|---|---|
| 成绩返回方式 | 会话结束时输出（stdout 的「最后一段非空助手文本」） | **会话内写结果文件**（`grading-result.json`），平台读文件 |
| 理由 | — | 62 份 × (总分 + 9 项明细 + 评语) ≈ 上万字，**塞进单条消息有截断与格式崩塌风险**；写文件可校验、可重试 |

### 0.4 前置条件（3 项，未完成 —— 决定方案能否落地）

| # | 事项 | 性质 | 为什么是前置 |
|---|---|---|---|
| **V1** | 隔离 `$DSH_HOME` 跑通 `dsh --profile headless` | 验证 | 证明无头模式可用、输出可控、与本机官方 DSH 零冲突 |
| **V2** | ★**实测能否隐藏执行类工具** | 验证 | **铁律合规的唯一决定性问题** —— 若不能隐藏，方案不可用 |
| **V3** | ★**「作业定死」快照改造**（见 4.4.1） | **改造** | ★**当前 schema 不保证作业冻结**，评分实时读活的题库值 —— **不做这一层，「检查器永不失效」不成立**，会出现「标准已改、分数不变」的静默不一致 |

> **V3 是本轮新增的硬前置**。它是产品语义问题（考试公平）而非纯技术问题：
> **考试期间或成绩公布后评分标准发生变化，本身就不公平。**

## 1. 背景与依据

### 1.1 项目目标（既有约束，不可动摇）

1. **教师无脑** —— 教师只上传标准工程包与评分标准，不写规则、不配置检查项。
2. **低服务器负载** —— 小服务器也要能承载。
3. **★铁律**：服务器上**始终不得**执行 `npm install`、构建项目、或直接执行任何代码（含学生代码与仓库业务代码）。

### 1.2 一致性问题的历史（本项目一路试过的方案）

| 方案 | 教师无脑 | 组内一致性 | 结论 |
|---|---|---|---|
| 规则驱动（教师写规则） | ❌ 要写规则 | std 0 | 卡在教师成本（后关闭入口） |
| LLM 直评 | ✅ | **std 4.55** | 卡在方差 |
| TrustJudge（概率期望） | ✅ | std 4.40 | 两头不占，且整体偏高 |
| `temperature 0` | ✅ | **std 6.20** | 无效（仅比 0.3 降约 1%） |
| **DSH 智能体 + 机械证据** | ✅ | **组内 std 0** | ★**首次同时拿到两个目标** |

> `temperature 0` 无效的根因是**服务端批处理规模不确定性**（2025 年已有文献证伪「浮点非结合性」假说），非提示词可解。

### 1.3 决定性实验结论（2026-10-11，注入测试集 62 份）

| 指标 | 结果 | 口径 |
|---|---|---|
| **误扣率** | **0.00%** | 6 份语义等价改写全部满分 |
| **满分正确性** | **100.00%** | 6 份对照 + 6 份无害变体 |
| 检出率（样本级） | **96.00%** | 48/50 |
| 检出率（实例级，剔除不可观测） | **98.31%** | 116/118 |
| 检出率（实例级，严格） | **90.98%** | 111/122 |

**账目闭合**：`111 严格命中 + 5 合并归因 + 4 清单伪影 + 2 真漏检 = 122`。
**唯一真漏检 = 2 处「相对 import 指向不存在的文件」**（属引用完整性，是平台的已知能力缺口）。

> ⚠️ **引用纪律（必须遵守）**：以上数字是**特定测试集 + 手写检测器**的成绩，
> **不得当作平台现状引用**。平台现状须用同一注入测试集**复算**后才能声称。

### 1.4 为什么「读代码 + 机械证据」能消掉方差

一致性事故几乎只发生在三个环节，本方案三个都要结构性消除：

| 环节 | 旧做法（有方差） | 本方案 |
|---|---|---|
| **整体印象分** | 问「这份值多少分」 | **拆成若干二值可判定谓词**（是/否） |
| **跨份比较** | 学生之间互相参照 | **每份只与唯一标准包比对**，互不参照 |
| **交给模型记规则** | 模型记住并应用评分标准 | **缺陷→扣分映射硬编码成表**，模型不参与算术 |

叠加一步关键降维：**先做全量文件哈希比对**，把「要看的代码量」压下来
（实测：62 份 × 29 文件 → 压成 **114 个改动点**），此后所有判断都锚在具体 diff 行上。

## 2. 架构总览

### 2.1 数据流

```
教师发布作业（上传标准工程包 + 评分标准 + 题目描述）
        │
        ▼  作业截止 / 教师点「批改」
平台创建批改任务（队列 + 并发闸 = 1）
        │
        ▼
spawn:  dsh --profile grader "<批改任务提示>"        ← 一次性无头会话
        │   $DSH_HOME 隔离 ｜ 凭据复用 system_configs
        │
        ├─ 会话内：读标准包 → 哈希比对 → 造检查器（谓词集 + 扣分表）
        ├─ 会话内：对全部提交跑检查器 → 逐项对账
        └─ 会话内：写 grading-result.json + checker.json + 打分记录
        │
        ▼  会话退出（跑完即退，不常驻）
平台读取结果文件 → 校验 schema → 写库
        │
        ├─ 检查器入库（持久化，供重评复用）
        ├─ 审计产物入库
        └─ 删除会话目录（释放磁盘）
        │
        ▼
教师看到：分数 + 评语 + 【逐项对账】
        │
        └─ 重评 = 重跑已入库的检查器（零 LLM / 毫秒级 / 逐位一致）
```

### 2.2 评分单位的改变（本方案最本质的一处）

| | 现状 | 本方案 |
|---|---|---|
| **触发** | 提交即评（每份独立触发） | **作业级：截止后（或教师触发）批量** |
| **调用单位** | 一份提交一次 AI 调用 | **一份作业一个会话** |
| **并发** | 信号量 3 | **会话并发 1（最多 2）** |
| **可比性** | 跨份不可比 | ✅ **同作业内天然可比**（同一把尺子） |

### 2.3 两阶段：LLM 的非确定性被关在开发期

```
阶段一 开发期（LLM 在此）          阶段二 运行期（零 LLM）
  读标准包 + 评分标准                平台直接执行已入库的检查器
  → 造检查器（谓词 + 扣分表）   ⇒     （重评走这里：零成本、逐位一致）
  → 跑 → 读报错 → 改 → 校准
  产物 = checker.json（artifact）
```

**关键**：会话是**一次性的**，但产物是**持久的**。这是「会话可销毁」与「重评不必重来」能同时成立的原因。

## 3. DSH 侧设计（均基于源码查证）

### 3.1 无头模式契约（`apps/cli/README.md` + `packages/bundle/headless/README.md`）

```
命令：dsh --profile headless "<task>"
语义：Run one fresh persisted session, print the final answer, and exit.
```

| 契约 | 事实 | 对本方案的意义 |
|---|---|---|
| 组件 | `@deepseek-ai/dsh-headless` = **one-shot bundle**，直接骑在 `dsh-base` 上 | 无需自己裁剪 |
| **不装** | **mounts no Host, HTTP server, Web runtime, or browser plugin** | ★「剔除可视化」**已是官方形态** |
| 端口 | **opens no listening port** | 无端口冲突、无外部暴露面 |
| 输出 | **最后一段非空助手文本 → stdout**；成功时 **stderr 为空** | ⚠️ 见 3.4：**结果改走文件** |
| 退出码 | `turn/end` completed → **0**，否则 **1**；终态 `error` 会把 code/message 写到 stderr | 平台可按退出码判定成败 |
| 会话 | **one fresh persisted session** | ✅ 有 id、可审计 |
| **限制** | **One submitted task only** —— 无交互追问surface | ✅ 与「一个作业一个任务」完全吻合 |
| 依赖 | `ctx.appExit` 由 launcher 提供；脱离 `dsh` launcher 启动会在激活时失败 | 必须用 `dsh` 命令入口，不能直接跑 bundle |

### 3.2 profile 设计（替代「克隆魔改」）

**结论：不需要 fork 源码。** 精简 = 配置 `$DSH_HOME/profiles/grader/`：

```
$DSH_HOME/profiles/grader/
├── package.json      { "dsh": { "profile": { "bundles": [ …只列需要的… ] } } }
└── cordis.patch.yml  用户补丁层（按 row id 覆盖配置；last write winning）
```

**bundle 解析顺序**：`dsh.profile.bundles` 里列出的名字先从 dsh 安装目录解析
（`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`、`@deepseek-ai/dsh-headless`），
再从 profile 自己的 `node_modules` 解析（pnpm 装在树外插件）。

**注意**：补丁是**整行替换**（`config` 不合并）⇒ 模式相关行应由各模式 bundle 完整重述。

### 3.3 凭据：复用管理员配置（用户第 1 点）

平台侧现状（已查证）：

```js
server/src/infrastructure/ai/deepseek/config.js:44
    getApiKey() = getConfig('deepseek_api_key', process.env.DEEPSEEK_API_KEY)
                            ↑ DB 优先（管理员后台配的）    ↑ .env 兜底

exam_system.system_configs:
    deepseek_api_key  = sk-855717966…      ← ★ 管理员账户配置的
    deepseek_model    = deepseek-v4-…
    deepseek_base_url = https://api.…
    ai_concurrency    = 64                 ← ★ 见 6.2：新架构下必须改小
```

**⇒ 单一事实源：DSH 实例的凭据从 `system_configs` 读取（或由平台启动时注入），与平台共用同一 key。**

### 3.4 ★输出契约：结果走文件，不走 stdout

`headless` 只把**最后一段非空助手文本**写到 stdout。62 份的成绩 + 评语 + 逐项对账远超单条消息的安全长度。

**约定**（在任务提示里写死）：

| 产物 | 路径（会话工作目录内） | 内容 |
|---|---|---|
| `grading-result.json` | 必产 | 每份提交：总分、9 项逐项得分、扣分依据、评语 |
| `checker.json` | 必产 | **检查器本体**（谓词集 + 扣分表 + 版本哈希）—— 供入库与重评复用 |
| `grading-log.md` | 必产 | 审计记录（读了什么、遇到什么问题、怎么解决） |
| `reconciliation.json` | 必产 | **逐项对账矩阵**（见 4.5） |

**平台侧**：读文件 → 校验 schema → 不合格则**重试一次** → 仍不合格则降级（见 4.7）。

### 3.5 ★工具限制（铁律合规的唯一抓手）

`packages/core/tools/README.md` 原文：

> **Restrictions that hide tools also remove their schemas before the model can call them.**

⇒ **工具可在 profile 层隐藏，且隐藏后模型连 schema 都看不到**（无法调用）。

**必须隐藏的对象**：任何可执行代码的工具（shell / 进程 / 代码执行）。
**保留的对象**：读文件、列目录、哈希计算、写结果文件。

> ⚠️ **V2 前置验证**：必须实测「隐藏后确实不可调用」，且**验证方式不能是读文档**。

## 4. 平台侧设计

### 4.1 触发时机

| 触发 | 现状 | 本方案 |
|---|---|---|
| 学生提交 | `enqueueProjectGrade` → 每份独立排队（信号量 3） | **不再逐份触发 AI 批改**；只登记提交 |
| 作业级批改 | ❌ 无 | ✅ 截止时间到达 / 教师点「批改本作业」/ 补交后手动 |
| **★何时真正启动** | — | **★仅在 DeepSeek【空闲时段】启动**（见 4.1.1） |

---

### 4.1.1 ★峰谷调度（成本优化）

#### 官方规则（原文，2026-10-11 取自 api-docs.deepseek.com/zh-cn/quick_start/pricing）

> **空闲时段价格为高峰时段价格的一半。北京时间周一至周五（不含中国法定节假日）**
> **9:00 - 12:00、14:00 - 18:00 为高峰时段；**
> **其余时段，包括周末及中国法定节假日全天均为空闲时段。**

**⇒ 时段判定表**：

| 时段 | 判定 | 单价 |
|---|---|---|
| 周一~周五（**非法定节假日**）**9:00–12:00、14:00–18:00** | **高峰** | 基准价 |
| 周一~周五 **18:00–次日 9:00** | 空闲 | **半价** |
| 周一~周五 **12:00–14:00**（午休） | 空闲 | **半价** |
| **周六、周日全天** | 空闲 | **半价** |
| **中国法定节假日全天** | 空闲 | **半价** |

#### ★三点必须澄清

**① 用户提的「工作日 18:00~次日 8:00」偏保守 —— 实际可到次日 9:00。**
且 **12:00–14:00 午休也是空闲**，同样可用。

**② ★中国法定节假日数据是【必需】的，不是可选。**
官方把「**不含中国法定节假日**」写进了高峰的**定义**里。若不识别节假日，
**节假日里的工作日 9:00–18:00 会被误判为高峰** ⇒ **白付一倍价钱**。

**③ 调休（把周末调成工作日）【不需要】识别。**
官方措辞是「**周一至周五**（不含中国法定节假日）」＋「**周末…均为空闲**」
⇒ **周六周日恒为空闲，无论是否调休上班**。**只需法定节假日列表，不需要调休表。**
（建议向 DeepSeek 书面确认调休日判定；按字面实现即可。）

#### ★没有峰谷接口 —— 本地计算

已核实：API 响应的 usage **只有 token 统计，无价格/时段字段** ⇒ **必须本地判定**。

| 做法 | 说明 |
|---|---|
| **内置节假日 JSON** | 推荐。如 holiday-cn 这类每年发布的 JSON，**每年更新一次**，成本极低 |
| 调用外部节假日 API | **不推荐** —— 引入可用性依赖，而数据本身一年只变一次 |

#### ★★调度规则：软截止，不硬切（用户的关键判断，形式化如下）

**用户的顾虑完全正确** —— 到点硬切会漏改。正确形式是「**启动截止**」而非「**强制结束**」：

```
① 仅在【空闲窗口】内启动新批改任务
② 已启动的任务【不打断】，跑完为止          ← 软截止
③ 窗口结束前 T 分钟停止启动新任务            ← ★这就是「预留一小时」的正确形式
     T 默认 60（约等于单任务预估时长，可配）
④ 高峰窗口内若有排队任务 ⇒ 等到下一个空闲窗口
⑤ 教师端显示「预计 X 小时后开始批改」
```

**⇒ 不需要「8:00 没改完就继续改」这种特例逻辑** —— 软截止天然涵盖它：
窗口结束只是**不再开新任务**，运行中的任务**本来就不会被打断**。

#### ★成本的两个杠杆（峰谷只是小的那个）

deepseek-flash 官方价（元/百万 tokens）：

| | 输入（**缓存命中**） | 输入（缓存未命中） | 输出 |
|---|---|---|---|
| **空闲时段** | **0.02** | **1** | 4 |
| 高峰时段 | 0.04 | 2 | 8 |

**★杠杆 1：缓存命中价是未命中的 1/50**（0.02 vs 1 元/M）—— **比峰谷（2 倍）重要 25 倍。**

> **⇒ 提示词前缀稳定 = 省钱的大头。** 62 份提交共享同一前缀
> （标准包 + 评分标准 + 题目描述 + 任务说明），**只有学生代码那一段不同** ⇒ 缓存命中率天然很高。
> **DSH 自身按 prefix-stable 设计**（其 README 多处标注 KV Cache effect）。
> **⇒ 代价极低**：保持前缀不变，不要在前面插入时间戳或随机内容。

**★杠杆 2：平台配的模型名是旧的**

```
server/.env:  DEEPSEEK_MODEL=deepseek-v4-flash      <= 旧模型名
官方注(1)：旧模型名 deepseek-v4-flash 仍可调用，但【对应模型已下线】，
          请求将由 DeepSeek-V4.1-Flash 提供服务，并按 Flash 价格计费。
=> 现名 = deepseek-flash
```

**⇒ 建议改名**（不改也能用，但名字对不上会误导运维排查）。

#### 成本量级估算（一份作业 62 份提交）

| 场景 | 输入 tokens | 单价 | 估算 |
|---|---|---|---|
| 悲观：每份都读全量代码 | ~8.3M | 1 元/M（空闲未命中） | **约 8 元** |
| **乐观：前缀稳定、缓存命中** | ~8.3M | **0.02 元/M** | **约 0.17 元** |
| 输出（假设约 0.1M） | 0.1M | 4 元/M | 约 0.4 元 |

**⇒ 量级：一份作业几元以内。** 峰谷省一半、**缓存省 50 倍** ⇒
**「保证前缀稳定以命中缓存」的优先级高于「峰谷调度」**，但两者都做最好。

#### 时效权衡（必须让教师知情）

| | 立即批改 | 峰谷批改 |
|---|---|---|
| 成本 | 高峰价（2 倍） | **半价** |
| 教师等待 | 即时 | 最长可能等到下一个空闲窗口（如上午 10 点截止 ⇒ 等到 12:00 或 18:00） |

**⇒ 结论（用户裁定）**：

| # | 事项 | 结论 |
|---|---|---|
| 1 | 默认走峰谷 | ✅ **是**（作业截止多在深夜，天然吻合） |
| 2 | 教师端显示「预计 X 小时后开始批改」 | ✅ **是** —— 上线后**必须**有，见下 |
| 3 | **「立即批改」按钮** | ★**上线【不提供】；仅测试阶段保留，上线前取消** |
| 4 | 记录 token 用量与时段 | ✅ 是（从 API 响应取，用于对账与调优） |

#### ★「立即批改」的分阶段策略（用户裁定）

```
测试阶段：保留「立即批改」  →  用于验证 DSH 评分是否正常（不必等到夜间窗口）
上线之前：取消该按钮         →  教师端不出现任何绕过峰谷的入口
```

**★实现方式建议：用配置开关，而不是「记得删按钮」**：

```js
// 与项目既有做法一致（FEATURE_CHECKER_ENTRY 即以此方式关闭）
FEATURE_IMMEDIATE_GRADE = true    // 测试环境
FEATURE_IMMEDIATE_GRADE = false   // 生产环境（上线前置 false）
```

**理由**：按钮删除靠人记，配置开关靠环境；**生产环境的开关默认 false，忘记删也不会漏出**。
开关为 false 时，后端接口也应一并拒绝（**不能只藏按钮**）。

#### ★上线后没有「立即批改」⇒ 教师端必须讲清楚「为什么还没出分」

**这是取消按钮后唯一的体验风险**：教师点了「批改」，发现没反应，会以为系统坏了。

| 必须显示 | 内容 |
|---|---|
| 当前状态 | 「已排队，等待空闲时段」 |
| **预计开始时间** | 「预计 **今晚 18:00** 开始批改」 |
| 原因（可选，简短） | 「夜间批改成本减半」 |
| 预计完成 | 「约 X 分钟后完成」 |

**★边界情形要一并想清楚**：

| 情形 | 结果 | 是否需要在 UI 说明 |
|---|---|---|
| 作业**上午 10 点**截止 | 等到 **12:00**（午休窗口）或 **18:00** | ✅ 是 |
| 学生**补交/迟交** | 排队到下一个空闲窗口 | ✅ 是 |
| 恰逢**法定节假日** | 全天可批 ⇒ **几乎立即** | 可在 UI 上作为「更快」的正面信息 |
| 服务器**正在批别的作业**（并发闸=1） | 排队，显示「前面还有 N 个作业」 | ✅ 是 |

### 4.2 任务队列与并发闸

```
gradingQueue（进程内 or 持久队列）
  ├── 同作业去重（同一作业同时只允许一个批改任务）
  ├── 并发闸 = 1（★服务器 2C4G，见 6.2）
  ├── 超时 = 30 分钟（可配），超时判失败并释放闸
  └── 重试 = 1 次（仅对「生成期失败」重试；「运行期失败」直接报错）
```

**★现状痛点**：走查发现平台当前存在 `fire-and-forget` 模式（生成侧）。
**本方案要求**：**任何 LLM 调用都必须经队列**，不得裸 fire-and-forget。

### 4.3 会话生命周期

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| **创建** | 建临时工作目录，软链/复制标准包与提交，生成任务提示 | 目录异常 → 直接失败 |
| **运行** | `spawn dsh --profile grader …`，捕获 stdout/stderr 与退出码 | 超时 → kill + 标记失败 |
| **取结果** | 读 `grading-result.json` 等产物并校验 | 缺失/非法 → 重试 1 次 → 仍失败则降级 |
| **入库** | 检查器、逐项对账、审计日志写入数据库 | 失败 → 保留工作目录（不销毁），人工介入 |
| **销毁** | 删除会话目录 + 临时工作目录；**保留入库产物** | 删除失败 → 记告警（磁盘监控） |

**销毁顺序很重要**：**先入库成功，再销毁**。禁止「先删后存」。

### 4.4 检查器持久化（新表建议）

```
project_checkers
  id               主键
  project_id       作业 id
  version_hash     检查器版本哈希（内容寻址）
  checker_json     检查器本体（谓词集 + 扣分表）
  rubric_hash      生成时所用评分标准/题目描述的哈希
  standard_hash    生成时标准工程包的哈希
  status           ready / stale / failed
  created_at
```

**★设计前提（用户裁定）：「作业定死」语义**

> **教师布置作业后，该作业不可再修改。** 即使在题库管理页改了题库，**那也只是改了题库**——
> 作业一旦发布，其**标准工程包 / 评分标准 / 题目描述**即被冻结。
>
> **⇒ 在「作业定死」前提下，检查器【永不失效】：一次会话生成一次，此后终生复用。**
> **⇒ 不存在任何「需要重新开会话」的情况。**

| 变了什么 | 检查器状态 | 是否需要新会话 |
|---|---|---|
| 新增 / 修改学生提交（含补交、迟交） | ready（不变） | ❌ **不要** —— 直接对增量跑检查器 |
| 教师重评（怀疑算错） | ready（不变） | ❌ **不要** —— 重跑检查器即可 |
| 题库里改了题目/评分标准 | **不影响已发布作业**（作业冻结） | ❌ **不要** |

### ⚠️ 4.4.1 前置依赖：「作业定死」当前【尚未被系统保证】（待修）

**核实结论**：当前 schema 与代码**不保证**作业冻结，**评分读的是活的 `Question` 行**：

| 证据 | 位置 | 含义 |
|---|---|---|
| `AssignmentQuestion` 是**纯关联表** | `prisma/schema.prisma:226-236`，字段仅 `{assignmentId, questionId, sortOrder}` | **无任何 rubric/题目描述/标准包的快照** |
| 评分实时读 `question.scoringRubric` | `services/projectGrading.js:208 / :283` | 读的是**当前**的题库值，不是发布时的值 |
| `updateQuestion` 对实训题**直接更新**，**无「被作业引用」校验** | `interface/http/controllers/teacher/questions.js:174-190` | 改题库**不会**被拦截或告警 |
| **且这是有意设计** | 同文件注释：`// 2026-08-17：评分标准变化 → 固定分项缓存失效（下次评分重新提炼）` | 作者预期「评分标准会变，评分跟着变」 |

**⇒ 后果**：教师改了题库的评分标准，**已发布作业的评分标准会静默跟着变**。
这对本方案是**致命**的——检查器按发布时的 rubric 生成，rubric 变了而检查器没变，
就会出现**「标准已改、分数不变」的静默不一致**（比现状更隐蔽）。

**建议（二选一，需用户裁定）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）快照** | 发布作业时把 `scoringRubric` / `material` / 标准包**复制进作业**（新增快照字段或快照表），评分只读快照 | 一次 schema 变更 + 评分链路改为读快照 |
| **B（兜底）失效检测** | 保留「可变」语义，但检查器带 `rubric_hash`，不匹配即判 `stale` 并重新生成 | **需要新会话**（与「作业定死」的简化目标相悖） |

**教育公平角度**：A 不只是技术选择——**考试期间或成绩公布后评分标准发生变化，本身就不公平**
（先交的按旧标准、后交的按新标准）。故 **A 是产品上更正确的选择**。

> ★**顺带必须修的既有缺陷（走查 T2）**：`updateQuestion:178-188` 目前**只置 `rubricItems = null`，未清 `checkerScript`**
> ⇒ 改了评分标准后**旧检查器继续对新生效**。
> **采用 A 之后此缺陷影响面缩小（作业冻结），但题库侧仍应修正，避免题库自身的缓存不一致。**

### 4.5 ★逐项对账（防「静默漏检」的核心机制）

**问题**：真实批改**没有答案键** —— 漏检、伪影、归类错误会**静默存在**（实验作者本人的原话）。

**机制**：以 `rubricItems` 为主键、`goal/group/item` 为映射键，产出**覆盖矩阵**，每项四态：

| 状态 | 含义 | 处理 |
|---|---|---|
| `covered` | 有检查项覆盖，且本次有结论 | 正常 |
| `partially_covered` | 只覆盖了部分情形 | 标注缺口 |
| ★`uncovered` | **没有任何检查项覆盖这一项** | ★**必须显式报出** |
| `subjective` | 本就无法机械判定 | 交人工或 LLM 主观评 |

**双端使用**：

1. **生成期**：`uncovered` 作为**校准反馈打回下一轮 prompt**
   （★现状只反馈「失分项」，**不反馈「漏项」** —— 这是要补的）。
2. **评分期**：写入 `aiFeedback.reconciliation`，并带 `ruleVersionHash`；
   **教师界面必须能看到「哪几项没被检查覆盖」**。

> ⚠️ **降级时不许骗人**：若本次未使用确定性检查（走了 LLM 全量），
> **必须把矩阵标注为「本次未使用确定性检查」**，否则会给教师虚假的确定性印象。

### 4.6 ★三种重评语义（回答「要不要取消重评」）

**答案：不取消，但要拆语义 —— 而且重评根本不需要新会话。**

**关键区分**：

```
会话      transient  → 用完即销毁 ✓（省内存/硬盘）
检查器    artifact   → 存库 ✓（几十 KB）
        ⇒ 重评 = 重跑检查器 = 【零 LLM、毫秒级、逐位一致】
```

| 教师意图 | 正确行为 | 新会话？ |
|---|---|---|
| **怀疑算错了，想重算** | **重跑已入库的检查器** | ❌ **不要** —— 幂等、零成本、结果必然一致 |
| **~~改了评分标准 / 题目 / 标准包~~** | ★**在「作业定死」语义下【不存在这种情况】**（见 4.4） | — |
| **就是觉得分不对** | **人工改判**（教师直接调分，写 `finalScore`） | ❌ 不要 —— 这是教师权力，不该靠重刷模型 |

**★UI 措辞建议**：把「重新评分」改为「**复核**」——
点击 = 重跑检查器 + 展示逐项对账。结果必然与上次一致，教师立刻理解「这不是抽奖」。

**为什么必须改措辞**：

```
旧架构（LLM 直评）：分数会变（std 4.55）
      ⇒ 教师反复点，刷到「看起来合理」的那个
      ⇒ ★实质上是在【用重刷掩盖方差】—— 这不是功能，是缺陷的副作用
新架构：同一把尺子量同一份东西，必然同结果
      ⇒ 继续叫「重新评分」会暗示「多刷几次会变好」，是 UX 隐患
```

### 4.7 失败与降级

| 失败点 | 降级 |
|---|---|
| 会话启动失败（DSH 不可用） | 该作业批改任务失败，**不产出任何分数**（宁可没有，不可乱给） |
| 会话超时 | kill + 标记失败 + 释放并发闸 |
| 结果文件缺失/非法 | 重试 1 次；仍失败 → 失败，保留工作目录供排查 |
| 检查器生成失败 | 降级到 LLM 全量批改，**并在对账矩阵标注「未使用确定性检查」** |
| 部分提交未覆盖 | 该部分标记 `uncovered`，教师可见 |

> **原则：宁可显式失败，不可静默给分。** 走查指出的最大风险是「**把『没找到证据』当成『没实现』⇒ 成批误扣**」。

## 5. 合规（铁律）

### 5.1 铁律（★已按「生态中立」完善）

**原表述**（仅覆盖 Node 生态，不足）：

> ~~服务器上始终不得执行 `npm install`、构建项目、或直接执行任何代码。~~

**★问题**：实训项目**不只是 Vue/Node**，还可能是 Java / Python / Go / C++ / PHP / C# 等任意语言生态。
只写 `npm install` 会漏掉 `pip install`、`mvn`、`gradle`、`go mod`、`cargo`、`composer` 等，
**规则会被逐条绕过**。

**★完善后的铁律（原则 + 例示，避免清单式漏洞）**：

> **服务器上不得发生任何「运行别人的代码」或「为运行它做准备」的操作。**
>
> **判据（不必记清单）**：**只要一个操作会启动一个进程去执行代码，即属禁止范围。**
> **允许的是**：读文件、解析（parse）、静态分析、哈希/字符串计算。
>
> **禁止范围（例示，非穷举）**：
>
> | 类别 | 例示（各生态） |
> |---|---|
> | **依赖安装** | `npm/yarn/pnpm/bun install`、`pip/poetry/conda/uv`、`mvn`、`gradle`、`go mod`、`cargo`、`composer`、`nuget`、`bundler`、`apt` |
> | **构建/编译** | `webpack/vite/rollup/tsc/esbuild`、`make/cmake`、`msbuild`、`javac`、`go build`、`cargo build` |
> | **直接执行** | `node/deno/bun`、`python`、`java`、`go run`、`php`、`ruby`、`dotnet`、任何字节码/脚本 |
> | **测试执行** | `jest/vitest/pytest/junit/go test` 等任何测试框架 |
> | **隐式执行** | shell 脚本、`Makefile`、构建钩子、`postinstall`/`prepare` 钩子、CI 流水线 |
>
> **注意**：禁止的是**「执行」这一动作**，不是**「代码本身」**——
> 读学生代码、解析它的 AST、比对它的结构，**全部允许**。

### 5.2 本方案的合规论证

| 环节 | 是否执行代码 | 说明 |
|---|---|---|
| `dsh` 进程本身 | ✅ **是** —— 但这是**运行本方案的服务**，不是执行学生代码 | 等同「运行 Node 服务」 |
| 会话内读文件 / 哈希 / 比对 | ❌ 否 | 纯静态读取与计算 |
| **会话内的 shell / 执行类工具** | ⚠️ **必须隐藏**（3.5） | **这是合规的唯一风险点，V2 必须实测** |
| 平台侧读结果文件、写库 | ❌ 否 | 常规 IO |
| 检查器重跑（重评） | ❌ 否 | 纯静态判定 |

### 5.3 仓内既有执行路径（**不修改，但不得接回评分链路**）

| # | 位置 | 现状 |
|---|---|---|
| 1 | `infrastructure/ai/checker/legacy-script.js` 的 `node -e` | **生产不可达**（调用方仅单测） |
| 2 | `infrastructure/execution/compile-executor.js` 的 `javac`/`python3` | **经体系 B regrade 路由可达**，与实训题链路解耦 |
| 3 | `adminController.js:335` 的 `exec('pm2 jlist')` | 监控 |

> **硬约束（建议写入代码注释与评审清单）：不得将 ① ② 接回评分链路。**

### 5.4 本方案的合规结论

**平台上本方案的评分主链路本身零执行路径**（走查已核实：不 fork、不 eval、不 `new Function`、不跑学生代码），
**唯一需要处理的是 DSH 会话内的工具集** —— 由 profile 配置隐藏（3.5）。

## 6. 资源与容量（目标机：阿里云 Ubuntu 22.04，2 vCPU / 4 GiB / 80 G）

| `$DSH_HOME/attachments` | **203 MB** | ★增长 |

### 6.2 内存估算（最紧的资源）

```
MySQL（现有）                  ~300~500 MB
Express 服务（pm2 两个进程）    ~300~600 MB
──────────────────────────────────────────
留给 DSH                      ~2.5 GB

一个 headless 会话             Node 进程 + code-runtime worker
                             估 ~300 MB ~ 1 GB（取决于上下文规模）
```

**⇒ DSH 批改的并发闸 = 1（最多 2）。**

### ⚠️ 6.2.1 更正：`ai_concurrency = 64` **不要动**（我此前判断有误）

> **用户澄清**：**接入 DSH 改卷目前仅针对【实训题】，编程题的改卷不做任何变动。**
>
> ⇒ `system_configs.ai_concurrency = 64` 是**编程题评分链路**的并发配置（每份提交一次短调用），
> **与 DSH 批改无关，保持原值 64 不变。**
>
> ⇒ **DSH 批改必须有【自己独立的】并发配置**（建议键名 `dsh_grading_concurrency`，默认 1），
> **不得与 `ai_concurrency` 混用**——两者单位不同（一个是 API 调用数，一个是会话/进程数）。

### 6.2.2 ★「DSH 并发闸」是什么意思

**并发单位 = 同时在跑的会话数 = 同时存在的 DSH 进程数。**

```
两位老师各自发布作业、同时触发批改
        ↓
  老师 A 的作业 → 会话 A（1 个 Node 进程 + code-runtime worker）
  老师 B 的作业 → 会话 B（1 个 Node 进程 + code-runtime worker）
        ↓
  ★这就是【并发 2】—— 内存占用约翻倍
```

**回答「两位老师分别同时在两个会话中是并发吗」：★是的，那正是并发。**

| 并发闸 | 效果 | 内存 | 教师体验 |
|---|---|---|---|
| **1** | 同一时刻只跑一个会话，其余**排队** | 最省 | 后到的老师要等（可能数十分钟） |
| **2** | 两个会话并行 | 约翻倍（估 0.6~2 GB） | 明显更快 |
| **≥3** | — | ★**2C4G 下有 OOM 风险，不建议** | — |

**建议默认并发 1，并提供缓解手段**：

1. **错峰**：作业截止时间天然分散（不同老师不同时间）；
2. **队列可见**：教师端显示「前面还有 N 个作业在批改」；
3. **可调**：并发值做成配置项，服务器升配后再调大；
4. **可抢占**：长时间无进展的会话可被 kill 并让位（见 4.7 超时）。

### 6.3 磁盘与清理

| 项 | 量 | 处理 |
|---|---|---|
| runtimes | 363 MB | 一次性 |
| 每次批改的会话目录 | 数 MB ~ 数十 MB（取决于读取量与工具调用次数） | **批改成功后立即删除** |
| 上传的提交包 | 一份作业数十 MB | 保留（学生数据，不随会话删） |
| 审计产物（入库） | 每作业几十~几百 KB | 长期保留 |

**80 G 结论：够用**，但必须有**定期巡检**（`$DSH_HOME` 总量告警）。

### 6.4 超时与重试

| 项 | 建议值 | 说明 |
|---|---|---|
| 单次会话超时 | 30 分钟 | 超时可配；超时即失败 |
| 重试次数 | 1 | **仅对生成期失败**；运行期失败不重试（避免半成品入库） |
| 结果文件校验 | 必做 | schema 校验 + 覆盖份数校验（提交数 vs 结果数） |

## 7. 落地步骤

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** | 隔离 `$DSH_HOME`，跑通 `dsh --profile headless "…"` | 能出结果、能写文件、**与本机官方 DSH 零冲突** |
| **P1** | ★**实测工具隐藏**（V2） | 隐藏后**实测确认无法调用执行类工具**（不是读文档确认） |
| **P2** | 最小闭环：一份作业端到端（建会话 → 跑 → 读文件 → 写库 → 销毁） | 一份真实作业跑通，**全链路无人工干预** |
| **P3** | 检查器持久化 + 三种重评语义 | 重评走「重跑检查器」，**结果与首次逐位一致** |
| **P4** | 逐项对账（四态 + uncovered 显式报出） | 人为制造一个无检查覆盖的评分项 ⇒ **必须被报出** |
| **P5** | ★**用注入测试集在平台复算三指标** | 得到**平台真实基线**（不得引用实验数字），并与手写检测器对比 |
| **P6** | 上线（灰度一份作业） | 教师端可见分数 + 评语 + 对账矩阵 |

**顺序理由**：P0/P1 是可行性门槛（不过则方案不成立）；P5 是**唯一能给出平台真实质量数字**的一步，
应在扩大范围前完成。

## 8. 风险与未决

### 8.1 风险

| # | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| **R1** | **把「没找到证据」当成「没实现」⇒ 成批误扣** | ★★★ | 逐项对账 + `uncovered` 显式报出 + 无害变体回归 |
| **R2** | **没有答案键时错误静默存在**（漏检/伪影/归类错） | ★★★ | 4.5 的对账机制；建议**抽检**（随机抽 N 份人工复核） |
| **R3** | **可判定性是素材给的，不是任务给的** —— 若学生结构差异极大（`<script setup>` vs `setup()`、目录布局各异），哈希比对失效，一致性难题回归 | ★★ | 作业级设计已部分缓解；需**在真实班级数据上验证**，不能只看注入集 |
| **R4** | 会话内工具未完全锁死 ⇒ 违反铁律 | ★★★ | P1 实测；profile 白名单 + 系统提示双保险 |
| **R5** | 2C4G 内存不足 | ★★ | 并发 1 + 超时 + 会话即删；必要时升配 |
| **R6** | 换题需重新生成检查器（一次性 LLM 成本） | ★ | 可接受；检查器可复用 |
| **R7** | 检查器质量无独立验证（自证） | ★★ | P5 复算 + 无害变体回归 + 抽检 |

### 8.2 未决（需用户裁定）

| # | 问题 | 选项 |
|---|---|---|

| **Q2** | 「复核」按钮是否保留在教师界面 | (a) 保留但改名复核 (b) 完全隐藏 (c) 保留且显示「结果必然一致」提示 |

### 9.3 术语

| 术语 | 含义 |
|---|---|
| **检查器（checker）** | 一次会话的产物：谓词集 + 缺陷→扣分映射表；确定性执行 |
| **尺子** | 检查器的比喻：一次造、多次量 |
| **逐项对账** | 评分标准每一项 ↔ 覆盖它的检查 的四态矩阵 |
| **无害变体** | 语义等价改写（重命名/注释/`==`→`===`），**正确行为是不得扣分** |
| **$DSH_HOME** | DSH 实例根目录；不同取值 = 完全独立实例 |

### 9.4 一句话总结

> **本方案不追求「让模型每次都给出同样的分数」，而是「把分数从模型手里拿走」。**
> 模型只在开发期出场一次——为这道题造一把尺子；此后由代码反复量，量多少次都一样。
