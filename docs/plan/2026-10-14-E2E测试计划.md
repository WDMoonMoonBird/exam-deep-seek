## 1. 目标与非目标

**目标**：在**真实运行的系统**上，用**真实角色、真实数据、真实评分链路**，把"教师布置作业 → 学生作答/提交 → 系统评分 → 教师复核 → 发布 → 学生看到结果"整条链**从头到尾跑通并可复现**，覆盖全部路径与主要异常；产出机器可读报告 + 人工可看证据。

**非目标**：①性能/压测（另有专项）②安全渗透（已有既有用例）③不覆盖与本波无关的旧功能（但会跑全量回归兜底）。

**与已有验证的关系**：此前是**分段** E2E（前端真浏览器+mock／后端真 HTTP+真库／Playwright 夹具／云上全栈），本计划补的是**跨角色贯通 + 接缝覆盖**。

## 4. 场景矩阵（模拟真实布置作业；每条都要有"期望 + 证据"）

### 4.1 主链 · 编程题（S1）
```
教师登录 → 建作业【编程题 / 允许重交=开 / 上限=2 / 口径=取最高 / 可见性=发布后】
 → 学生A登录 → 看到作业 → 提交① → 提交② → 提交③被拒【逐字：已达提交次数上限（最多 2 次）】
 → 教师触发批改(POST /teacher/assignments/:id/grade) → 等待评分完成(轮询 status)
 → 教师审核页看到提交与 AI 分 → 改总分 88 + 评语 → 发布
 → 学生A复核：四路径（提交页/详情/列表/成绩页）同口径显示 88；未发布前不得出现分数
```
**期望**：全流程 200/正确文案；`attempt_count=2`；DB `status` 依次 submitted→ai_graded→reviewed→published（改分后**仍为 published**，G3 回归）。

### 4.2 主链 · 实训题（S2，★真评分，不等峰谷）
```
教师建作业【实训题 / 允许重交=开 / 上限=2 / 口径=取最后 / 可见性=发布后】
 → 学生B上传合法工程包 → 入 grading_jobs → worker 执行（造尺/复用尺 → 装置评分 → AI 总评）
 → 轮询至 done → 教师审核页看逐项明细与总评 → 改总分 → 发布 → 学生B四路径一致
 → 学生B 第2次提交【同一份内容】⇒ 期望命中判据复用（RULER_RESOLVE=reuse / CHECKER_REUSE=applied）
```
**期望**：job 状态流转正确、用量记账有值、判据复用命中、四路径一致、**不产生重复造尺费用**（复用证据）。

### 4.3 三开关组合（S3–S7）
| 场景 | 允许重交 | 上限 | 口径 | 可见性 | 要点 |
|---|---|---|---|---|---|
| S3 | 关 | 1 | 取最后 | 发布后 | 第 2 次提交被拒；未发布不可见 |
| S4 | 开 | 3 | **取最高** | 提交后立即 | 两次提交分数不同 ⇒ 审核页"计入分=最高"且**并列展示明细来源**（v1.1 口径）|
| S5 | 开 | 不限 | 取最高 | 发布后 | 学生端**提交后**看不到答案；发布后可看 |
| S6 | 开 | 2 | 取最后 | 提交后立即 | 学生提交并评分后**立即**可见参考答案与解析 |
| S7 | 题型默认 | — | — | — | 建作业时按题型预填；**手改后再换题型不被覆盖** |

### 4.5 状态机与发布可见性（S9）
`draft → submitted → ai_graded → reviewed → published`；**已发布后改分**：状态保持 published、学生端即时可见新分；**撤回/重跑**（若产品支持）不得让学生看到中间态。

### 4.6 异常与边界（S10–S13）
| 场景 | 期望 |

### 4.7 前端交互（S14，真浏览器）
建作业表单（三开关/默认值/成本提示/校验）｜提交页（第 k 次/剩余次数/上限禁用原因/答案可见性）｜审核页（只改评语、只改总分、非法分值拦截、已发布不锁死且有提示、有新提交提示、取最高并列展示）｜批量审核/发布（含**历史 practice 作业**控件可见 = F-C4-2 回归）｜教师手册措辞。

同一学生同一题，在【提交页 / 作业详情 / 作业列表 / 成绩页】看到的分数与状态一致（口径 best/last/教师分 三种情况下各验一次）。

### 4.9 回归兜底（每轮必跑）

> ★v2 强化（源自 t22 实测）：全量回归必须【一套件一个进程】逐套件隔离执行 —— 实测 7 套件合并成批时 `rc-batch-guard-contract` 出现 1 例跨套件干扰假红（单跑 7/7 绿、精简批与全量批均绿）。合并批次虽然更快，但会制造无法归因的假红。

## 5. 评分执行方式（★"不等峰谷"）

- **真跑**：实训题评分直接触发，不等待低峰；预计 **4~6 次实训评分**（S2 两次 + S4/S6 各一次，视组合而定）。
- **成本预估**：造尺 ≈¥1.5/次（命中复用则为 0）＋ AI 总评 ≈¥0.06/人·次 ⇒ **合计约 ¥3~8**（远低于一次人工改卷成本）。
- **超时策略**：单次评分等待上限 15 分钟；超时按"失败"记录并保留日志，**不重试超过 1 次**（避免费用叠加）；失败即触发停止条件评估。
- **可观测**：轮询 `grading_jobs` 状态 + 读取用量记账；关键节点落盘日志供事后核对。

## 6. 验收标准（每条链的"通过"定义）

1. **功能通过**：该场景所有断言的期望值一致（脚本输出 PASS/FAIL 全绿）。
2. **数据一致**：关键表（`submissions` 的 attempt_count/ai_score/final_score/status、`grading_jobs` 状态、`grading_rulers` 复用标记）与期望一致。
3. **安全边界**：未发布不外泄（响应体不含分数与 `aiScore/aiFeedback` 键）、越权 403 且零写入。
4. **文案纪律**：所有错误只上屏服务端可读文案（无 `err.message`、无 Prisma/ADM-ZIP 内部文本）。
5. **零残留**：清理后 `E2E-` 命中 0；生产库无新增测试列/表。
6. **报告**：机器可读报告（每场景 PASS/FAIL + 证据路径）+ 人眼可看的 UI 截图若干（关键 5 屏）。

**阻断判定**：出现任一条 ①真缺陷（非环境）②安全边界破坏 ③生产残留 ⇒ 立即停止，回滚并修，再重跑该链。

# 13. v2.1 追加（源自 C7 贯通验证的实测发现）

## 13.1 真实流程的三处硬事实（计划据此修正）

1. **评分前置 = 必须有可用的 checker**：POST /teacher/assignments/:id/grade 在无 checker 时返回 **409 + code 1011 + requiresChecker: true**（文案「该作业还没有可用的 checker」）。
   - 实测（本地 dev 库）：checkerStatus=ready 仅 2 道**实训（project）题**；默认测试题（code）为 none。
   - ⇒ **S1（编程题）修正为两条断言**：①不带标准包建作业 ⇒ 触发批改应得 **409+1011**（正确拒答）②带标准包/已就绪 checker ⇒ 批改成功并进入评分流转。
   - ⇒ **S2（实训题）正是用户给的场景**：用标准包 + 评分标准构建 checker ⇒ 真评分（zip 上传分支）。
2. **发布必须用真发布端点**：PUT /teacher/submissions/publish { submissionIds: [...] }
   - 反例（此前脚本踩坑）：PUT /teacher/submissions/:id/review { status: published } **不改变状态**（DB 实测仍 reviewed）⇒ 学生端永远看不到分。
   - ⇒ 计划把"发布"显式写成该端点，并断言 status 由 reviewed → published。
3. **接口行的形状**：教师提交列表的行是**嵌套** assignment.id（不是顶层 assignmentId）⇒ 断言与过滤都必须按嵌套字段写（这是此前"匹配 0"的脚本原因，与 O-E2E-1 的产品缺陷是两回事）。
