## 1. 既有链路全貌

### 1.1 一句话链路

> 教师上传标准工程包 + 写评分标准 ⇒（**手动点按钮**）LLM 生成 `objective_items` 规则 JSON ⇒ **在标准包上自举校准**（标准包应得满分，扣分就反馈证据让 LLM 改参数）⇒ 达标进 `review` ⇒ **教师确认** ⇒ `ready` ⇒ 学生提交 ⇒ 异步评分：确定性 `runRules` 学生包 + 主观项 LLM ⇒ 写回 `Submission.aiScore/aiFeedback`。

**与目标架构的对照**：这条链路**已经是**"智能体为这道题生成一套可判定的谓词集，由代码（谓词）算出分数"。差异只在两点：
1. **扣分表形态**：实验是 `缺陷 → (评分项, 扣分, 说明)` 的**显式映射表**；平台是"每条规则自带 `max_score`"，映射表隐含在规则集里（**结构上等价**，但缺"一个缺陷扣多个评分项"的显式声明）。
2. **谓词的表达力**：实验的谓词是**手写的 Python 函数**（可写任意逻辑）；平台的谓词被**限制在 11 种 `rule_type` 的白名单内**。§3 的全部差距都在这里。

### 1.3 状态机：`questions.checkerStatus`

真源：`server/prisma/schema.prisma:149`（注释只写了 `none|generating|ready|failed`，**实际代码里还有 `calibrating` 与 `review`**，schema 注释过时）。

~~~
none ──generate──▶ generating ──(第1轮跑完)──▶ calibrating ──┬─ 客观项满分且无真实失分 ─▶ ready
                    │                                        ├─ calibScore ≥ 90 且无真实失分 ─▶ review ──教师确认──▶ ready
                    │                                        └─ 3 轮未达标 ─▶ failed（保留最优规则在 checkerScript）
                    │

~~~ `review` 态四条出路（`review.js:23-100`，全部走同一个 `confirmChecker`）：
- `confirm` → 最新版本 `active`，`activeVersionId` 落库，`ready`；
- `to_subjective` → 把失分客观项搬进 `subjective_items`（改规则 JSON）；
- `exempt` / `accept` → 只改体检报告状态（豁免/接受失分），**规则不变，仍对学生生效**；
- `update_rules` → 教师手工改规则 JSON（重新 `validateRules`，失败返回 error 不改库）；
- `regenerate` → 再次 fire-and-forget `generateChecker`。

## 2. `ruleExecutor` 的表达力边界

### 2.1 规则契约与校验

规则 JSON（生成目标 = 存储内容 = 执行输入）：

~~~json
{
  "max_score": 100,
  "objective_items": [{ "id": "a1", "group": "评分标准分项名", "item": "规则中文描述",
                        "rule_type": "file_exists", "params": { "path": "package.json" }, "max_score": 2 }],
  "subjective_items": [{ "id": "s1", "item": "主观项中文描述", "max_score": 5 }]
}
~~~

`validateRules`（`domain/services/rule/validate.js:22-100`）硬约束：
1. 每项必有 `id` / `item`（**不是 name**）/ `max_score`（正有限数，允许小数）；objective 项还需 `rule_type` ∈ 白名单、`params` 为对象；
2. `fact` 额外校验 `fact/op/value`（`op` ∈ `>= > <= < == != includes not_includes`；数值比较要求 `value` 是有限数字）；
3. **总分守恒**：`Σobjective.max_score + Σsubjective.max_score === rules.max_score`（防"103 分问题"）；
4. 校验失败 → `runRules` **直接抛错拒绝执行**（不静默）。

执行期强制（`infrastructure/rule/executor.js:72-132`）：
- 每项 `score = max(0, min(max_score, 计算得分))`，**永不超上限**；
- `totalScore = Σ客观项`，再兜底 `≤ Σ max_score`；
- `fact` 规则每次 `runRules` **只提取一次事实**，失败 → 该项 0 分 + 证据，**绝不抛错**；
- 路径全部经 `resolveWithinRoot`（`file-access.js:58`）防穿越；遍历跳过 `SKIP_DIRS = {node_modules,.git,dist,build,.idea,.vscode,target}`（`constants.js:26`）。

### 2.2 11 种 `rule_type` 逐条判定式与能力上限

真源：`domain/services/rule/constants.js:10-23`；分派 `executor.js:21-50`。

| # | rule_type | 参数 | 判定式（源码事实） | 给分形态 | 能力上限 / 坑 |
|---|---|---|---|---|---|
| 1 | `file_exists` | `path` | `fs.existsSync(abs) && isFile()` → 满分 | 全或无 | 只看存在，不看内容；只支持**确定路径**（不支持通配） |
| 2 | `dir_contains_file` | `dir`,`pattern` | 目录递归收集文件，**简化 glob**（`*` 不跨 `/`，`?` 单字符）匹配 ≥1 → 满分 | 全或无 | 无内容判定；pattern 含 `/` 时按相对路径匹配，否则按 basename |
| 3 | `contains_text` | `path`,`text` | `content.includes(text)` → 满分 | 全或无 | 逐字节，**空白/引号/换行差异即失分**（P0-2 语义级规则就是为治它而加） |
| 4 | `count_regex` | `path`,`regex`,`min`,`partial?` | `new RegExp(regex,'g')` 的匹配次数 ≥ min → 满分；`partial===true` 时按 `round(max*count/min)` 比例给分 | 全或无 / 比例 | **单文件**；计数是"出现次数"而非"去重命中" |
| 5 | `contains_regex` | `path`,`regex` | `re.test(content)` → 满分 | 全或无 | **单文件单路径**；正则非法 → 0 分（不抛错） |
| 6 | `file_count_in_dir` | `dir`,`pattern`,`min`,`partial?` | 匹配文件数 ≥ min → 满分；`partial` 同比例 | 全或无 / 比例 | 只数文件个数，不看内容 |
| 7 | `syntax_check` | `dir`,`pattern` | 目录内匹配且扩展名 ∈ `{js,mjs,cjs,ts,jsx,tsx,vue}` 的文件逐个 tree-sitter 解析；**任一 ERROR/isMissing → 该项 0 分**；无可检查文件 → 0 分 | 全或无（**跨文件合取**） | 唯一"跨文件全或无"；只覆盖 JS 家族，**Java/Python 文件会被扩展名过滤掉**；进程内解析，**零 child_process** |

### 2.3 三条结构性上限（比单个类型的坑更重要）

1. **只有正向存在性断言**：11 种类型全部是"有 X ⇒ 得分"。**没有任何一种能表达"不得包含 X / 必须排除 Y"**。而本题评分标准里就写着反向要求：「未用 Pinia、用局部状态或 localStorage 代替的，此项不得分」。当前只能靠"正向规则全不满足"间接表达，或丢给主观项。
2. **单文件/单目录**：除 `syntax_check`（跨文件全或无）与 `fact`（预制聚合字段）外，**所有匹配都在一个 `path`/`dir` 内**。跨文件的合取/析取/计数**无法表达**。
3. **规则之间无依赖、无互斥**：每条规则独立判定，**没有"若 A 缺失则跳过 B"的条件规则**。这直接导致 §3.4 的"连带重复扣分"风险（实验里靠人工合并归因解决）。

| **P2** | 归一化模式可配置（c301/c302） | 扩展 `normalized_text`：`normalize: ["whitespace","backslash","quotes"]` | — | 实验第一版注释就写"修正误报：正则比较做**去反斜杠**归一化"，平台没有这个开关 |
| **P2** | 跨文件合取（c203/c901） | 新 `rule_type: all_of`（引用多条子规则 id，全满足才给分） | `{rules:["a1","a2"], mode:"all"}` | 现在只能拆条 → "全或无"退化成"各半"，**与评分标准"每处扣 3 分"的口径不一致** |
| **P3** | 条件/互斥规则（连带扣分） | 新 `rule_type` 或规则级 `when` 前置条件 | `{when:{rule:"a1", pass:false}, action:"skip"}` | 实验为"5 处 S5 是 S1/S4 的连带结果"专门做了**合并归因**；平台无此机制会**重复扣分**（对学生的方向是偏严，风险可控但不精确） |
| **P3** | 反斜杠/引号无关的"语义级"匹配 | 已有 `ast_pattern`，需补 **内容谓词** | 如 `ast_pattern` 增加 `node_text_regex` | 现在是"节点类型链匹配"，检查不到"某个节点里写的是什么" |
| — | **无害变体回归（实验误扣率 0% 的真正来源）** | **不是规则类型，是校准流程改造**：在自举校准里加入"语义等价变体 ⇒ 必须仍满分"的**正向回归**（与 `ruleMutator` 的负例验证互补） | 由 LLM 生成 N 个等价改写（改名/加注释/`==→===`/`let→const`/补 name），跑 `runRules` 要求全满分 | 没有它，"误扣"只能在真实学生身上被发现 |

### 3.5 无法用规则表达的（必须写代码 / 必须转主观）

1. **语义等价性**（程序等价性一般不可判定）：`F2` 改名、`app→myApp` 这类 —— 只能靠"规则不写死标识符名"来规避（实验被 `myApp` 咬过一次：初版硬编码 `app.use(createPinia())` → 误判 16 分，改为 `\.use\(createPinia\(\)\)` 才修好）。
2. **运行时/行为正确性**："登录成功后跳转目标对不对""按钮点了有没有反应""接口字段与 Pinia 是否一致" —— 静态只能判"写了跳转语句"，判不了"跳对了"。实验也是这么认的（`打分记录.md:198`"控制台无报错只能静态推断"）。
3. **跨文件因果归因**："这个文件的缺失导致那个功能不可用" —— 实验靠**人工合并归因**（5 处 S5 并入 S1/S4），平台无机制。

### 5.2 结论

> **本题评分主链路（checker 生成 → 规则执行 → projectGrading → 写回）上，零执行路径。**
> - 不 fork 子进程、不 `eval`、不 `new Function`、不加载学生代码、不 `npm install`、不构建；
> - tree-sitter 是**进程内原生解析**（`syntax.js`/`factExtractors`），不产生子进程（与同日《静态确定性检查方案》§1.2 结论一致）；
> - 唯一的"执行学生代码"能力（`compile-executor.js`）位于**另一条已解耦的旧体系（体系 B）**，且需要教师重评路由显式触发；
> - 唯一的"执行 LLM 生成脚本"能力（`legacy-script.js`）**已经是孤岛**，仅测试引用。
> **建议（本轮不做）**：给 `legacy-script.js` 与 `compile-executor.js` 加"禁止从评分链路 import"的架构约束（如 ESLint 边界规则或注释级 ADR），把"不合规但无人用"固化成"不合规且不得引入"。

## 6. 逐项对账的设计（输出契约）

### 6.1 目标

> **评分标准里的每一项，都要能回答："哪条检查覆盖了它？它发现了什么？"**
> 并且：**没有任何检查项覆盖的评分项，必须被显式报出来**（不能静默当作满分/不评）。

### 6.2 契约草案（在现有 `aiFeedback.breakdown` 之上扩展，向后兼容）

~~~json
{
  "breakdown": [ /* 现状不变：{item, score, maxScore, comment, kind:'checker'|'ai'} */ ],
  "reconciliation": {
    "rubricItemCount": 9,
    "covered": 7, "partiallyCovered": 1, "uncovered": 1, "subjective": 0,
    "items": [
      {
        "rubricItem": "第二项，路由与页面跳转",
        "group": "第二项，路由与页面跳转",
        "maxScore": 10, "score": 7,
        "coverage": "covered",              // covered | partially_covered | uncovered | subjective
        "rules": [
          { "id": "a7", "ruleType": "fact", "params": {"fact":"routePaths","op":"includes","value":["/login","/register","/user"]},
            "maxScore": 3, "score": 3, "pass": true,  "evidence": "路由路径 包含 /login,/register,/user" },
          { "id": "a8", "ruleType": "contains_regex", "maxScore": 3, "score": 0, "pass": false,
            "evidence": "未匹配（正则：push 到 /user）", "file": "src/views/Login.vue" }
        ],
        "uncoveredReason": null
      },
      {
        "rubricItem": "第四项，注册功能",
        "coverage": "uncovered",
        "uncoveredReason": "评级标准要求但未生成任何客观规则，且未列入 subjective_items",
        "action": "block"                    // block | warn：由教师决策
      }
    ],
    "source": { "ruleVersion": "v3", "ruleVersionHash": "a1b2c3d4e5f6", "checkerStatus": "ready" }
  }
}
~~~

### 6.3 覆盖矩阵怎么算（不需要 LLM，纯结构化）

1. **主键 = `rubricItems`**（已存在：`[{item, maxScore, automation_level}]`，由 `summarizeRubricItems` 提炼并落库，评分标准变更时置 null 重新提炼）。
2. **规则侧的归属** = `objective_items[].group`（生成 prompt 已强制"评分标准每个分项用 group 关联，group 内 max_score 之和必须等于该分项满分"，`prompts.js:130`）＋ `subjective_items[].item`。
3. 对账算法：按 `group` 分组求和，与 `rubricItems` 逐项比对——
   - 分值相等且有 ≥1 条规则 ⇒ `covered`；
   - 分值不等（缺额 > 0）⇒ `partially_covered`（缺额必须写进 `uncoveredReason`）；
   - 组不存在且该分项未进主观项 ⇒ `uncovered`；
   - 出现在 `subjective_items` ⇒ `subjective`（**必须标注"由 LLM 打分，不参与确定性口径"**）。
4. **对账在"生成时"和"评分时"各跑一次**：
   - 生成时（`generator.js` 达标判定前）：把 `uncovered` 作为校准反馈的一等公民打进下一轮 prompt（现在只反馈"失分项"，**不反馈"漏项"**）；
   - 评分时（`projectGrading.gradeWithChecker`）：把矩阵写进 `aiFeedback.reconciliation` 落库，教师审核页可展开逐条看。

### 6.4 与既有设施的关系（不重复造）

| 已有 | 作用 | 对账怎么用 |
|---|---|---|
| `meta.report`（`meta.js:53`） | 标准包体检报告：失分项 → 教师转主观/豁免/接受 | 复用其 `items[].{id,group,ruleLabel,deduction,status,note}` 结构 |
| 规则路径白名单（`package-inspect.js:71`） | 标准包缺失文件的"缺陷候选" | 对账时标 `coverage: covered but 标准包未实现`，避免把标准包缺陷算成漏项 |
| `inputsSnapshot` + 前端保存守卫 | 输入变更 → 规则过期 | 对账矩阵落库时带 `inputsSnapshot` 指纹；指纹不符 ⇒ 标 `stale` |
| `ruleVersionHash`（`projectGrading.js:687`） | 冻结本次评分用的规则版本 | 对账 `source.ruleVersionHash` 与之同源，保证"历史分数可解释" |

### 6.5 降级时的对账（必须一起降级，否则会骗人）

| 评分路径 | 对账状态 |
|---|---|
| checker `ready` + `runRules` 成功 | 完整矩阵（如上） |
| checker `ready` 但 `runRules` 抛错 → LLM 全量 | `reconciliation.source = "fallback_llm"`，**矩阵置空并显式标注"本次未使用确定性检查"** |
| checker 非 `ready`（none/generating/review/failed） | 同上，且附 `checkerStatus` 原值 |

### 6.6 教师侧呈现（最小）

一个折叠面板："评分标准 9 项 → 规则 27 条 → 覆盖 8 项 / 漏 1 项（第四项）"，漏项给"去确认/生成"按钮。**未覆盖项必须在保存题目与发布成绩两个节点各提示一次**。
