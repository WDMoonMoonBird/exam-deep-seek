## 1. 铁律与边界（先立规矩）

### 1.1 三条硬约束（用户最终裁定，逐字遵守）

1. **服务器上「始终不得」执行 `npm install`、构建项目、或直接执行任何代码** —— 理由是显著增加服务器负载。适用范围 = **实训题**。
   ⇒ 确定性层**只能是纯静态解析**：读文件 / tree-sitter 解析 / 正则 / AST / 文件存在性 —— **零执行、零依赖（新装）、零网络、零构建**。
2. **教师尽量无脑**：不得要求教师写规则、写测试用例；**教师只审核**是可接受的。
3. **不碰**：`server/src/infrastructure/execution/compile-executor.js`、`server/src/infrastructure/ai/checker/legacy-script.js`。
   本方案**不把它们作为手段，也不提议修改它们**（全文零引用、零改造建议）。

### 1.2 本方案的静态手段清单（穷举，无第 4 项）

| 手段 | 是否需要执行 | 是否需要新装依赖 |
|---|---|---|
| 文件存在性 / 目录遍历（`node:fs`） | 否 | 否 |
| 文本包含 / 正则匹配（`new RegExp`） | 否 | 否 |
| 归一化文本匹配（去空白） | 否 | 否 |
| tree-sitter 解析（AST / 语法检查） | 否（进程内解析，无 child_process、无 shell） | **否**——`server/node_modules` 已含 `tree-sitter` + `tree-sitter-javascript/java/python/vue`，且 `tree-sitter/prebuilds` 覆盖 darwin-arm64/x64、linux-arm64/x64、win32-arm64/x64，**无需构建、无需 npm install** |

### 1.3 本轮实测口径（可审计的诚实声明）

铁律禁止"直接执行任何代码"，而成本核算要求"实测毫秒数"。本轮采用的合规口径是：

> **把 `ruleExecutor` / `defectPrecheck` / `defectScoring` 的判定式逐字转写为独立的纯计算脚本**（`/tmp/dsh-static/*.mjs`），
> **仅 import `node:fs` / `node:path`**，**不 require 仓库任何模块**，不加载 tree-sitter，不执行学生代码，不联网，不安装，不构建。
> 计时即在该转写脚本上进行（同一 V8、同一正则引擎、同一 `readFileSync` I/O 形态）。

**转写保真度的自校验**：转写结果与仓库自带单测 `server/test/unit/infrastructure/defect-precheck.test.js` 的断言**逐条吻合**——
A 组（1066）`issues = []`、B 组（1067）`issues = []`、C 组（1068）含 `missing_import` 且 `file` 含 `App.vue`、`target` 含 `Login.vue`，`scoreDefects` 硬扣 ≥30 且第一项 `deduct === 10`。
实测在**真实 uploads 目录**（`server/uploads/project-submissions/353/1066|1067|1068/1`）与 **/tmp 物化目录**上结果完全一致。

**未实测项（如实标注）**：`syntax_check` / `ast_pattern` / `fact` 三类规则需要 tree-sitter 原生模块，本轮**未加载**（属"直接执行代码"边界内的第三方原生二进制），故其耗时与判定结果全部标注 **【待实测】**。

## 2. 现有静态能力盘点

### 2.1 `ruleExecutor` 11 种规则——真实判定式与能力边界

真源：`server/src/domain/services/rule/constants.js:10-23`（`RULE_TYPES` 11 项）
分派：`server/src/infrastructure/rule/executor.js:21-50`｜执行体：`executors.js`（8 种）+ `syntax.js`（`syntax_check`/`ast_pattern`）+ `evaluators.js:109`（`fact`）

| # | rule_type | params | **判定式（源码事实）** | 能力边界 |
|---|---|---|---|---|
| 1 | `file_exists` | `{path}` | `fs.existsSync(abs) && statSync(abs).isFile()` → 满分，否则 0 | 只能判"存在"；判不了"内容对不对" |
| 2 | `dir_contains_file` | `{dir,pattern}` | 递归收集 `dir` 下全部文件，glob→`^…$` 正则；**pattern 含 `/` 按相对路径、否则按 basename**；命中 ≥1 → 满分 | 不能判"哪个文件才对"；不递归进 `node_modules/.git/dist/build/target/.idea/.vscode` |
| 3 | `contains_text` | `{path,text}` | `content.includes(text)` → 满分 | 逐字敏感：引号/空格/换行任一不同即失分（**脆弱**） |
| 4 | `count_regex` | `{path,regex,min,partial?}` | `new RegExp(regex,'g')` 计数；`count ≥ min` → 满分；`partial:true` → `round(max*count/min)` | 计数型可给部分分；`min` 缺省按 0（**恒满分陷阱**） |
| 5 | `contains_regex` | `{path,regex}` | `new RegExp(regex).test(content)` → 满分 | **无 `m` 标志** ⇒ `^`/`$` 只锚定整串，**不能按行匹配** |
| 6 | `file_count_in_dir` | `{dir,pattern,min,partial?}` | 同 #2 的匹配语义，取命中**文件数**与 `min` 比较 | 同上；可 `partial` |
| 7 | `syntax_check` | `{dir,pattern}` | 目录下匹配 `pattern` 且扩展名 ∈ {js,mjs,cjs,ts,jsx,tsx,vue} 的文件逐个 tree-sitter 解析；**任一 `ERROR`/`isMissing` 节点 → 整项 0 分**；无可检查文件也 0 分 | **全有全无**，无部分分；vue 因 ABI 冲突恒走 `<script>` 提取回退（`syntax.js:32-34`）【耗待实测】 |
| 8 | `fact` | `{fact,op,value}` | 由 `extractFacts(projectRoot)` 取字段，按 `>= > <= < == != includes not_includes` 比较（`evaluators.js:109-153`）；字段缺失/非数字 → 0 分 | 依赖 `factExtractor`（tree-sitter）；每次 `runRules` 只提取一次并缓存【耗待实测】 |
| 9 | `ast_pattern` | `{path,pattern}` | tree-sitter 解析后按 `>` 分隔的**节点类型链**做"祖先→后代"匹配，命中 ≥1 → 满分；**忽略空白/引号/顺序** | 只认语法节点类型，不认标识符名/字面量值【耗待实测】 |
| 10 | `count_imports` | `{path,module,min,partial?}` | **逐行**扫描：行 trim 后以 `import|require|from|include` 开头 **且** `line.includes(module)` 的行数 ≥ `min` | 行级字符串包含，**不是真正的 import 解析**（注释里的 import 也计数） |
| 11 | `normalized_text` | `{path,text}` | 两侧都 `replace(/\s+/g,'')` 后 `includes` → 满分 | 解决缩进/换行差异；**不解决引号差异** |

**整体执行契约**（`executor.js:72-131`）：先 `validateRules`（不通过直接抛错拒绝执行）；每项 `score = max(0, min(max_score, 计算分))`；`totalScore` 为客观项之和；含 `fact` 时单次提取、失败降级为该 0 分而不抛错。

### 3.1 ★必须交给 LLM 的清单（静态明确不碰）

1. **行为正确性**：路由跳转是否到了对的地方、接口调用是否成功、返回数据是否写进了对的状态字段；
2. **语义等价性**：「用简单比较代替自定义 validator 的该项不得分」——静态只能看到"有没有 `validator` 这个词";
3. **完整性与恰当性**：「校验规则不完整按条扣分」「酌情扣分」「按严重程度扣分」中的"程度"；
4. **第九项全部主观子项**：命名清晰度、注释必要性、组件拆分合理性（后者只能判"文件是否存在"）；
5. **第一项「能正常安装启动」**：需执行，**静态永不涉足**；
6. **任何需要"跑一下才知道"的结论**。

### 3.2 ⚠️ rubric 自身的缺陷（实测发现，须先修）

**rubric 9 个分项分值实测合计 = 110，但 rubric 首行自称「总分 100 分」。**
10+10+20+20+10+15+5+10+10 = **110**。
⇒ 若按 rubric 逐项折算，任何"分项全满足"的学生都会得到 110 分（再由上层 clamp 到 100）——**分项权重与总分不自洽**。
本方案的所有折算表都以此为前置风险：**建议先修 rubric 再上线折算**，否则折算比例天然失真。

## 5. LLM 生成静态规则的可行性

### 5.1 已有链路（**这条路由已经铺好，无需新建**）

`server/src/infrastructure/ai/checker/` 已实现完整闭环：

```
题目 rubric + 标准包文件树
   ↓ ① LLM 生成 JSON 规则（GENERATE_SYSTEM，prompts.js:75）
   ↓    prompt 硬约束：「rule_type 只能使用白名单类型」
   ↓                  「params 必须真实可执行（路径必须来自标准包文件树，不得猜测）」
   ↓                  「不要改写成代码，也不要新增评分标准未提及的检查项」
   ↓ ② parseCheckerRules 宽容解析 + 归一化（id 补全 / 白名单过滤 / 总分归一化）
   ↓ ③ runRules(规则, 标准包) → 满分则 ready；≥ DEFAULT_THRESHOLD(90) 则 review
   ↓ ④ 未达标 → 构造校准反馈让 LLM 只改 rule_type/params/max_score（≤ MAX_ROUNDS=3 轮）
   ↓ ⑤ validateNegativeTests（ruleMutator）派生变异体，要求每条规则「必须失分」
   ↓ ⑥ 教师 review：confirm / to_subjective / exempt / accept /（可选）update_rules / regenerate / rollback
   ↓ ⑦ ready → 学生评分走确定性的 runRules（0 LLM）
```

**与铁律的相容性**：全链路**没有一处执行代码**——LLM 只输出 JSON；`runRules` 只读文件/正则/tree-sitter 解析；`review.js` 只改数据库。
**唯一需要的依赖（tree-sitter）已在 `server/node_modules` 且带 6 平台 prebuilds ⇒ 无需 `npm install`、无需构建。**

**⚠️ 需要登记的不一致**：`parsers.js:7-16` 给 LLM 的白名单只有 **8 种**（缺 `ast_pattern` / `count_imports` / `normalized_text`），而 `constants.js` 的 `RULE_TYPES` 是 **11 种**。
⇒ **三种"语义级、抗写法差异"的新规则类型，LLM 现在根本用不到**。这是**零执行、纯配置**的低风险改进项（把白名单对齐到 11 种）。

### 5.3 教师审核负担：**轻，且"只审核"已经被产品化**

教师需要做的**唯一事情**是看一张"标准包体检报告"（`meta.js:53-69` 的 `buildReport`），对每个失分项点一个按钮：

| 教师动作 | 含义 | 教师需要写规则/测试吗 |
|---|---|---|
| `confirm` | 确认启用（草稿转 active） | ❌ 不需要 |
| `to_subjective` | 该项静态判不了 → **转 AI 主观评分**（自动搬进 `subjective_items`） | ❌ 不需要 |
| `exempt` | 标准包自己没做到 → 豁免（不计入校准失分，规则仍对学生生效） | ❌ 不需要 |
| `accept` | 接受失分（保留扣分） | ❌ 不需要 |
| `regenerate` / `rollback` | 重新生成 / 回滚到历史版本 | ❌ 不需要 |
| `update_rules`（高级，可选） | 手工改规则 JSON | ⚠️ 唯一需要"懂规则"的入口，**可以永远不点** |

**实测的教师负担量级**：以本方案 25 条映射规则为例，标准包体检报告只会有 **1 条待处理项**（`R9b` 兜底 catch，见 §5.4）——教师点一次 `to_subjective` 或 `exempt` 即可。
**结论：符合"教师尽量无脑"约束；不需要教师写规则、写测试用例，只需要审一次体检报告。**

### 5.4 规则质量风险：**假阳性会误扣分 ⇒ 必须保守**（含本轮实测反例）

| 风险 | 实测证据 | 缓解 |
|---|---|---|
| **规则在标准包上就不成立**（把 rubric 里标准包自己没做到的要求写成硬规则） | 我写的 `R9b contains_regex{path:'src/components/UserList.vue',regex:'\\.catch\\s*\\('}`（rubric 第九项「对接口失败有兜底」1 分）**在标准包上 0 分**——**标准包根本没写 `.catch(`** | 这正是 `DEFAULT_THRESHOLD=90` + `markDefectReportItems`（"标准包未包含该文件（缺陷候选：评分标准要求但标准包未实现，可转主观/豁免/接受失分）"）要处理的情形。**校准失败 ⇒ 该规则不得上线硬扣** |
| **过扣**（计数型全扣把"少一个字段"打成"整项全失"） | B 组 V2：全扣口径净失 **7 分**，`partial:true` 净失 **4 分**（差 3 分） | 计数型强制 `partial:true` |
| **脆弱正则**（引号/别名/空格差异即误判） | `@/views/Login.vue` 别名 import 被 `defectPrecheck` 完全跳过（§4.2 脆弱点）；`contains_text` 逐字敏感 | 优先 `count_regex`/`count_imports` 等**引号无关**判据；**禁用 `contains_text` 写业务断言** |
| **恒满分假规则**（`count_regex` 漏写 `min` ⇒ `min=0` ⇒ 永远满分，白送分） | 源码事实：`executors.js:100-101` `minValue = Number.isFinite(min) ? min : 0` | 已有护栏：`ruleMutator.validateNegativeTests` 要求每条规则在变异体上**必须失分**；建议再加"必须显式写 `min`"的静态校验 |
| **口径误判**（`/` 路由算不算"三条路由"之一） | V2 删了 `path:'/'`，三条点名路由都在 | **交教师拍板**（体检报告里显式列出该规则的判定口径） |

## 6. 保守折算规则与折算表

### 6.1 三条原则（沿用 `defectScoring` 的既有哲学）

1. **只扣 rubric 明确对应的项**：文件/功能与 rubric 分项的映射必须有**原文依据**；
2. **未映射不扣**：映射表外的缺陷只作为"事实"注入 LLM prompt，**不做硬扣**；
3. **只有 fatal 才整项全扣**：`import` 断裂 = 项目不可运行 ⇒ 第一项全扣；其余一律**按比例**或按子项分值扣。

| **L0 预检** | 其它未映射文件 | — | **不扣**（只注入事实） | 保守原则 |
| **L1 规则** | 计数型子项未达标（六字段 / 必填项 / Pinia 字段） | 对应分项子项 | **`partial:true` 按比例**：`round(max*count/min)` | V2 实测：1 分（比例）vs 4 分（全扣） |
| **L1 规则** | 布尔型子项未命中（无 `clearUser`、无 `pageSize:10`） | 对应分项子项 | **全扣该子项** | V3 实测：`R5c-3` ✓ |
| **L1 规则** | `syntax_check` 失败（语法不可解析） | 第一项（"启动报错"） | **建议全扣 10 分**（待实测确认 tree-sitter 判定） | V2 的截断 import **【待实测】** |
| **L2 探针** | `from 'axios'` 不存在（截断 import 的诊断探针） | 无 rubric 锚点 | **不扣分**，仅作事实注入 + 触发"转人工" | V2 实测：命中 |
| **合并** | 同 rubric 分项被 L0 与 L1 同时命中 | — | **取 max，不叠加**（避免双重扣分） | 例：V3 的登录项 L0 已扣 20，L1 的 `R3a/R3b/R3c/R3d/R3e` 不再叠加 |

### 6.3 折算后的分数形态（供 LLM 使用）

```
确定性硬扣 D（0~100）
剩余空间 M = 100 − D
→ prompt 注入：缺陷事实清单 + "已扣 D 分，请在剩余 M 分内评估未受影响的功能项"
→ LLM 输出 R（0~M）
→ 最终分 = (100 − D) − R   // 等价于 D + R 的反向表达
```
**上限保护**：最终分 `clamp(0, 100)`。**注意 rubric 分项合计 110 的缺陷（§3.2）会让 `D` 与 `M` 的基数失真，建议先修 rubric。**

## 10. 局限与残留风险

### 10.1 结构性局限

1. **★静态检查只能"扣分"不能"给分"。**
   它回答的是"**有没有**"，回答不了"**对不对、好不好**"。一个把所有 rubric 关键词都抄进代码但逻辑全错的学生，会在静态层拿到接近满分。**因此静态层永远只能做"前置扣分/事实注入"，不能取代 LLM，更不能给出最终分。**

2. **★对 B 组（完整实现，33.9% 的学生）近乎无能为力。**
   实测：B 组 21 人里静态只能锁定 4 分（V2）。B 组的一致性 std（4.55~8.8）**在静态路线上不可压缩**。这是本方案最重要的负面结论——**"用静态检查解决一致性问题"这个命题，在 B 组上不成立。**

3. **rubric 自身不自洽**：分项合计 110 ≠ 自称 100（§3.2）。折算基数失真。

4. **标准包与 rubric 不一致的项，静态写不出规则**：
   rubric 第九项「Axios 封装统一基础地址 3 分」，**标准包自己就没有封装**（`UserList.vue` 直接用 `axios.get('http://203.0.113.10:3000/users')`）。
   以"标准包必须满分"为校准原则 ⇒ 该规则**必然校准失败** ⇒ 只能转主观。实测的 `R9b`（`.catch(` 兜底）是同类第二个例子。

### 10.2 已知脆弱点（建议加固，均为**零执行**）

| # | 脆弱点 | 影响 | 零执行加固 |
|---|---|---|---|
| F1 | `defectPrecheck` **不解析 `@`/`~` 别名 import** | V3 的 `fatal` 全靠 `App.vue` 恰好写了相对路径；若学生全用别名 → `missing_import` 全漏 | 加 `@ → src`、`~ → src` 的纯字符串映射（读 `vite.config.js` 的 `resolve.alias` 亦可，仍为纯解析） |
| F2 | import 正则会把**未闭合引号**吞成非相对引用 | V2 的截断 `import` 被静默放过（实测 issues=0） | 加"引号无关"探针 `from\\s*['\"]axios['\"]`，或接 `syntax_check`（【待实测】） |
| F3 | `count_regex` 漏写 `min` ⇒ `min=0` ⇒ **恒满分** | 白送分 | 生成端强制要求 `min`；已有 `ruleMutator` 负例验证可兜底 |
| F4 | LLM 规则白名单只有 8 种（`parsers.js`） | 3 种抗写法差异的新类型用不到 | 白名单对齐 `constants.js` 的 11 种（纯配置） |
| F5 | `defectPrecheck`/`defectScoring` **从未接线** | 本方案的所有 L0 折算**都要新建调用点**才算生效 | 明确按"接线改造"排期，不要当成"打开开关" |
| F6 | 折算与规则可能**双重扣分** | 同一 rubric 分项被 L0 + L1 各扣一次 | 按 rubric 分项 id 取 `max` 不叠加（§6.2 合并行） |

### 10.3 待核实清单（本轮未实测，不做假设）

1. `syntax_check` 对 V2 截断 `import axios from 'axi` 的判定结果与耗时 —— **【待实测】**（高置信会失败，但未验证）；
