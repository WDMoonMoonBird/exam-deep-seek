## 0. 结论速览

| 问题 | 实测结论 |
|---|---|
| 输入该分几层 | **4 层**：L-0 静态（零 LLM）/ L-1 短路（零 LLM）/ L-2 差异清单（LLM）/ L-3 关键文件全文（LLM）；再外加 1 类**不可判**（须转人工/教师拍板） |
| 分层后各占多少分（基数 110 分，rubric 分项实测合计） | **A 静态可判 48 分（43.6%）** ｜ **B 差异清单 15 分（13.6%）** ｜ **C 关键文件全文 37 分（33.6%）** ｜ **不可判 10 分（9.1%）** |
| ★确定性短路覆盖率 | **21/62 人 = 33.9%**（与标准包规范化后逐字节相同 ⇒ 确定性满分、**零 LLM**） |
| ★路径规范化是否必要 | **是，且是决定性的**。不做规范化 ⇒ 只有 **20** 人可短路（V6/10327 因外层目录 `UserManagement/`→`3/` 被误判为"有差异"，Δ−377 全部来自目录改名）；规范化后 ⇒ **21** 人。**漏判 1 人 = 漏省 134K tokens**，且该生会被无谓送进 LLM 评分 |
| ★★"差异即扣分"的误扣规模（B 组） | B 组（20 人，完整实现）真实差异 = **2 文件 / 4 hunk / 10 行**。其中**真缺陷只占 2 hunk / 4 行**；**2 hunk 无 rubric 锚点或属格式噪声**（删 `path:'/'` 路由、行尾逗号位移）。⇒ **hunk 级过扣比例 = 2/4 = 50%**；**行级 = 6/10 = 60%**。按 partial 口径，B 组真实应扣 **4 分**，而"差异即扣分"会扣到 **7 分**（净多扣 3 分，**+75%**） |
| ★现有倒挂（本方案最硬的证据） | **A 组（逐字节=标准包，diff=0）t03 mean = 98.0** vs **B 组（完整实现，10 行差异）t03 mean = 80.2**。**抄的比写的已经高 17.8 分**。任何"差异即扣分"只会把这个倒挂**放大** |
| ★差异清单会不会比全量代码更大 | **会（最坏情况）**。最坏界 = 每个文件整篇重写 ⇒ `2 × 1896 行 = 3792 行` ≈ **120,392 tokens**，是**学生全量代码（58,904 tok）的 2.04 倍**、**业务代码（8,458 tok）的 14.2 倍**。⇒ **必须设降级闸门**（变更行 > 标准包总行 40% ⇒ 退回"关键文件全文"输入）。本批 62 人最大 changedLines = 10，**触发降级的 = 0 人** |
| token 加权节省比例 | 现状 **118,555 tok/份**（仓库自带 `estimateTokens` 口径）→ 分层后 **6,251 tok/份**（A 组 0、B 组 9,664、C 组 9,236，加权）⇒ **节省 94.7%**。对照任务书实测基准 **134K tok/份** ⇒ **节省 95.3%**；62 人全量：7,350,410 → 387,595 tok（或 8,308,000 → 387,595） |
| 用户反例（`int i = 0;` vs `int i = 1 - 1;`）的处置 | **判 A 类（等价改写），不得扣分**。且本方案已用同型反例证明：**`int i = 0;` vs `int i = 1;` 的 diff 形状逐字节相同（1 hunk / 2 行），但一个是等价、一个是真缺陷** ⇒ **diff 规模本身对正确性零信息量** |
| 主要风险 | ① 短路层的正确性依赖"标准包=满分"这个**校准假设**（rubric 第九项"Axios 封装"标准包自己就没做 ⇒ 该假设已被实测证伪一次）；② 差异清单最坏情况比全量还大；③ rubric 分项合计 **110 ≠ 100**，折算基数失真；④ 本方案的收益全部是 **token/延迟/一致性**，**不是**"解决 B 组一致性"（B 组 std 4.55 不在本方案射程内） |

## 2. 现状与问题（含实测编号）

### 2.1 现状链路（事实，出自 `docs/defects/scoring-scheme-3way.md` §1）

```
提交 → enqueueProjectGrade → gradeProjectSubmission
  ├─ getProjectContextMode()          默认 'filter'（L0 过滤）；'off' | 'filter' | 'two-stage'
  ├─ buildGradingContext()            L0 白名单过滤 → (two-stage 时) L1 selectImportantFiles
  │                                   → enforceBudget（预算 120000 tok，学生 7 : 标准包 3，超限骨架化）
  ├─ buildProjectGradePrompt()        【项目题目】+【项目要求】+【评分标准】+【标准答案源码】+【学生提交源码】+ OUTPUT_SPEC
  └─ gradeProject()                   单次 LLM 调用，temp 0.3，max_tokens 16000，最多重试 3 次
     分数 = LLM 输出的 totalScore（clamp 到 [0, maxScore]，四舍五入）
```

**关键事实**：`gradeProject` 把**标准包全文**与**学生全文****同时**塞进同一段 prompt，让 LLM 自己"对比"。这正是本方案要改造的输入形态。

### 2.2 问题 1 —— 输入里 85.4% 是第三方库（实测）

作业 353 标准包（29 文件 / 204,916 字节 / 1,896 行）按 `estimateTokens` 拆解：

| 分类 | 文件数 | tokens | 占比 |
|---|---|---|---|
| **第三方库**（`assets/js/{jquery,bootstrap.min,bootsnav,modernizr,jquery.easing,jquery.sticky}.js` + `assets/css`） | 7 | **50,325** | **85.4%** |
| **业务代码**（vue/js/json/html/css + README） | 22 | **8,458** | **14.6%** |
| 合计 | 29 | 58,904 | 100% |

⇒ **每份提交里，8.5 万 token 是学生原样复制的 jQuery/Bootstrap**。它们对 9 个 rubric 分项**一个都不贡献**，
却占据了 prompt 的绝大多数，且是"与标准包逐字节相同"的部分 —— 也就是**最不需要 LLM 看的部分**。

### 2.3 问题 2 —— 学生之间 94% 的代码是完全相同的（实测）

62 份提交按**规范化后文件树 sha256** 去重 = **5 种**（比既有结论的 6 种更少，见 §4.1）：

| 变体 | 人数 | 与标准包的关系 | 差异规模 |
|---|---|---|---|
| V1 | 20 | **逐字节相同** | 0 |
| V6 | 1 | **逐字节相同**（仅外层目录改名） | 0（规范化后） |
| V2 | 20 | 完整实现，2 文件有改 | 4 hunk / 10 行 |
| V5 | 1 | 完整实现，缺 1 文件 + 1 文件有改 | 2 hunk / 3 行 |
| V3 | 19 | 缺 2 文件 | 0（缺文件，非行差异） |
| V4 | 1 | 缺 1 文件 + 1 文件有改 | 2 hunk / 4 行 |

⇒ **62 份提交里，只有 4 个变体、共 22 行不同**。
**把 62 份 20 万字节的全文反复送给 LLM，是在为 22 行的差异重复付费。**

### 2.4 问题 3 —— "对比标准答案"这个动作被交给了 LLM 自己

现状 prompt 的最后一句是隐式的："对比标准答案和学生提交的项目代码"。
LLM 必须**先在 20 万 token 里自己找出差异、再自己判断差异的性质**。
这两件事被混在一步里 ⇒

- **成本**：每份都要重新"找差异"；
- **一致性**：实测 A 组 std 2.74 / B 组 std 4.55 / C 组 std 10.85~13.15（`exp353`），
  即**同一份代码 5 次评分能差 12 分**；
- **激励反转**（§5.1 硬约束）：A 组 98.0 > B 组 80.2 —— **抄的比写的高 17.8 分**。

**本方案要做的三件事**：把"找差异"从 LLM 手里拿走（改成确定性程序）、把"判差异"逐条约束（改成契约）、
把"不需要看"的部分彻底不发（短路 + 分层）。

## 3. ★① 输入分层表

### 3.1 四种输入 + 一种"不可判"

| 输入层 | 需要什么输入 | 适用项 | 手段 | 谁判 | 零 LLM？ |
|---|---|---|---|---|---|
| **L-0 静态** | **不需要内容**（只看文件树/语法） | 结构性客观项：缺文件、引用断裂、语法不可解析、字段计数、字面量存在性 | `defectPrecheck` + `ruleExecutor`（源码已存在，**但从未接线**） | **程序** | ✅ **是（零 LLM）** |
| **L-1 短路** | 标准包 + 学生包（用于**判等**） | 「与标准包一致」 | 路径规范化 → 规范化文件树 sha256 比对 | **程序** | ✅ **是（零 LLM）** |
| **L-2 差异清单** | 标准包 vs 学生的**差异片段**（文件级 + 行级） | 「是否偏离标准答案」——跳转正确性、接口调用、字段与接口一致性、活动/参数语义 | LCS diff → 渲染成清单 → **LLM 逐条判定（A/B/C/D 四分类）** | **LLM** | ❌ 否 |
| **L-3 关键文件全文** | 学生**业务代码关键文件**全文（可选 + 标准包对应文件） | 代码规范 / 设计合理性 / 美观度 / 命名 / 注释 / 组件拆分 | 确定性文件选择（按 rubric 关键词 + 权重）→ 全文注入 | **LLM** | ❌ 否 |
| **⛔ 不可判** | **不投入任何输入** | 「能正常安装启动」「无控制台报错」「对接口失败有兜底」 | 需**执行**才能判定 ⇒ 铁律禁止 | **教师/转人工** | ✅ 是（且**不假装能判**） |

> **为什么"不可判"必须单列**：静态层与 LLM 层都能"编"一个答案（"看起来应该能跑"），
> 但那不是判定、是猜测。诚实做法是把这 10 分**显式标注为未判定**，由教师口径决定（见 §10.3）。

| 对接口失败有兜底、无未捕获异常 | 1 | **⛔ 不可判** | 实测标准包**没有 `.catch(`** ⇒ 同上 |

### 3.3 分层汇总（分值口径，基数 = 110）

| 层 | 分项归属 | 分值 | 占比 | 人数加权（62 人） |
|---|---|---|---|---|
| **L-0 静态（零 LLM）** | 一(部分) 二(部分) 三(部分) 四(部分) 五(部分) 六(大部分) 八(部分) 九(部分) | **48** | **43.6%** | 全覆盖，但**对 B 组只能锁定 4 分**（上游实测） |
| **L-1 短路（零 LLM）** | 与标准包一致 ⇒ 全部分项 | **110（整卷）** | — | **21 人 / 62 = 33.9%** |
| **L-2 差异清单（LLM）** | 二(跳转目标) 三(接口/字段/错误) 四(接口/validator 语义) 五(退出调用) 六(退出) 八(接口/兜底) | **15** | **13.6%** | B 组 + C 组 = 41 人 |
| **L-3 关键文件全文（LLM）** | 七 + 一(注册) + 九(命名/注释) | **37** | **33.6%** | 同上 41 人（与 L-2 合并为同一次调用） |
| **⛔ 不可判（转教师）** | 一(启动) + 九(Axios 封装/兜底) | **10** | **9.1%** | 全部 62 人 |

上游实测已证明：**静态层对 B 组（33.9% 的学生）只能锁定 4 分**，且它**只能扣分不能给分**。
因此 L-0 在本方案中的定位是 **"前置事实注入 + 前置扣分"**，**不是**分数的最终来源。

## 4. ★② 确定性短路（deterministic short-circuit）

### 4.1 路径规范化规则（★本方案的关键实现细节）

**问题**：`10327` 与标准包**逐字节相同**，但 Δ = −377 字节 —— 差异**全部**来自外层目录改名
（`UserManagement/` → `3/`，29 文件 × 13 字符 = 377）。
若直接按字节比对，它会**被误判为"有差异"**，失去短路资格，被无谓送进 LLM 评分。

**规范化规则（3 条，全部纯字符串操作）**：

| # | 规则 | 说明 |
|---|---|---|
| **N1** | 对每个文件的路径，**删除第一个路径分段**（即第一个 `/` 之前的部分），保留其余部分作为**项目相对路径** | `UserManagement/src/views/Login.vue` → `src/views/Login.vue`；`3/src/views/Login.vue` → `src/views/Login.vue`；`UserManagement_副本/src/App.vue` → `src/App.vue` |
| **N2** | **忽略**路径分隔符风格差异：`\\` → `/`；折叠重复的 `/`；**忽略大小写以外的空白**（路径内不 trim 语义字符，但 ` ` 与 `\t` 的尾随空白删除） | Windows 解压产物、手改路径 |
| **N3** | 若某路径**不含 `/`**（根级文件），**不删任何分段**，原样保留 | 避免把 `package.json` 这类根文件误删成空串 |

**保留哪些层**：**只删第一段**（那一段是"学生自己起的工程目录名 / 学号 / 解压目录名"，**不承载评分语义**）。
**忽略哪些层**：`UserManagement`（标准包外层目录名）、`UserManagement_副本`、`1`、`2`、`3`（学号或解压序号）
—— 这些在数据集中**实测全部是单段噪声**（见附录 B）。

> **为什么不"智能推断"**：例如"如果第一段等于标准包的第一段就删"——那对 `3/` 这种**不等**的情况会失效。
> **统一删第一段**是唯一在 5 个变体上全部正确的规则，且**不依赖任何白名单**。

**规范化后的比对方法**：
```
1. 解析 submission 的「// 文件名: <path>」转储 → Map<path, content>
2. 对每个 path 施加 N1~N3 → Map<relPath, content>（若规范化后 key 冲突 ⇒ 视为不可短路，降级 L-2）
3. 排序 key，拼 hash： sha256( Σ (relPath + '\0' + content + '\1') )
4. 与标准包的同法 hash 比对 ⇒ 相等即「规范化后逐字节相同」
```

### 4.2 ★短路覆盖率（实测）

| **不做路径规范化**（原始转储 sha256 / md5） | **20 / 62** | 32.3% | 只有 V1；V6 因外层目录改名被误判为"有差异" |
| **做路径规范化后**（本方案） | **21 / 62** | **33.9%** | V1（20）+ V6（1） |

**验证**：规范化后 5 个变体的 sha256 前 8 位与人数：

### 4.3 短路动作（确定性满分）

命中短路的提交：
1. **不再调用 LLM**（0 token、0 延迟、0 方差）；
2. 分数 = **该题 `maxScore`**（本批 = 100），并在 `breakdown` 里逐分项给出满分与证据

**A 组零假阳性的实证**（上游双跑一致）：`precheckProject` 在 STD / V1 / V6 上 issues = 0、`totalHardDeduct` = 0；

## 5. ★③ 差异聚焦（diff focus）

### 5.1 ★★硬约束：「差异」绝不能直接当作「错误」

**这是一条不可协商的约束。**

**论证 1 —— 程序等价性判定在一般情况下不可判定。**
"两份代码是否等价"等价于"两个程序是否在所有输入上输出相同"，这是**图灵不可判定**问题（Rice 定理）。
因此**不存在**任何"差异 ⇒ 扣分"的机械映射能保证正确。任何这样的机制**必然**误判。

**论证 2 —— 同一 diff 形状，两种相反结论（本方案给出的最小反例，实测）**

| 标准包 | 学生提交 | diff 形状 | 语义 | 正确判定 |
|---|---|---|---|---|
| `  int i = 0;` | `  int i = 1 - 1;` | **1 hunk / 2 行** | **相同**（`1-1 == 0`） | **A 类等价改写，不得扣分** |
| `  int i = 0;` | `  int i = 1;` | **1 hunk / 2 行**（**逐字节相同的 diff 形状**） | **不同** | **D 类真实缺陷，扣分** |

⇒ **diff 的规模、位置、行数对"是否正确"携带零信息量**。两行的 diff 可能完全等价，也可能完全改变行为。
**唯一能区分的只有逐条语义判定。**

**论证 3 —— "差异即扣分"会形成激励反转（实测数字，本方案最硬的证据）**

| 组 | 定义 | 差异 | 实测 t03 分数（5 次均值） |
|---|---|---|---|
| **A** | 与标准包**逐字节相同** | **0** | **98.0** |
| **B** | **完整实现**（自己写的，功能齐全） | 2 文件 / 10 行 | **80.2** |

**抄的已经比写的多 17.8 分。**
如果再加"差异即扣分"：**A 组 diff=0 ⇒ 不扣；B 组 diff=10 行 ⇒ 扣**。
⇒ 每一行"自己写的代码"都变成**负资产**；**越认真写、扣得越多**。
⇒ 学生的**最优策略变成原样复制标准包**。这**直接摧毁**实训题的考核目标。

**论证 4 —— 标准包本身可能有缺陷，此时"差异"可能是改进。**

实测已证伪"标准包=完美"这一假设至少一次：rubric 第九项要求「Axios 封装统一基础地址 3 分」，
而**标准包自己就没有封装**（`UserList.vue` 直接 `axios.get('http://203.0.113.10:3000/users')`，上游 §5.4/§10.1）。
⇒ 若学生**真的做了 Axios 封装**，他的 diff 会很大，而**他做对了 rubric 明确要求的事**。
⇒ "差异即扣分"会**惩罚符合评分标准的正确行为**。

### 5.2 ★安全的用法：diff = 注意力引导（attention steering）

**diff 的唯一合法用途**：把 LLM 的注意力**收敛到真正不同的地方**，避免它在 20 万 token 里自己找差异（成本 + 方差来源）。
**diff 不产生分数**；**分数必须由逐条语义判定产生**。

### 5.3 ★逐条判定契约（A/B/C/D 四分类，必须写进 prompt）

对差异清单里的**每一条 hunk**，LLM **必须**给出恰好一个分类：

| 类 | 名称 | 定义 | **是否影响分数** | 输出要求 |
|---|---|---|---|---|
| **A** | **等价改写** | 语义与标准包**相同**，只是写法/结构/名字不同 | **❌ 不得扣分** | 必须给出"为什么等价"的一句话 |
| **B** | **更好的实现** | 语义正确，且比标准包**更清晰/更规范/更健壮** | **❌ 不得扣分**，**写入 `highlights`** | 说明"好在哪里" |
| **C** | **无关差异** | 格式、缩进、引号、命名、注释、空行、文件顺序、外层目录名 | **❌ 不得扣分** | 一句话即可 |
| **D** | **真实缺陷** | 语义**错误**，或**缺失** rubric 要求的内容 | **✅ 扣分** | **必须**说明：① 影响**哪一个 rubric 分项**（逐字引用分项名）② 缺失/错误的具体内容 ③ 扣几分（不得超出该分项满分） |

**四条写入 prompt 的硬规则**：

1. **只有 D 类影响分数。** A/B/C 三类**一律不得扣分**，且 **A/B/C 的条数不得作为任何扣分依据**。
2. **先给证据（文件 + 行号 + 原文），再给结论。** 顺序不可颠倒。禁止"看起来有问题"这类无证据结论。
3. **分类不确定时（拿不准是 A 还是 D）⇒ 必须选 A（等价/不扣分），并在 `uncertain` 字段标记。**
   理由：漏判一个缺陷 = 该生多拿几分；错判一个等价 = **惩罚正确行为**。二者代价不对称，**必须偏向不扣分**。
4. **每条 D 类必须绑定一个 rubric 分项**。绑定不上任何分项的差异 ⇒ **自动降级为 C（无关差异），不得扣分**。
   （这条把上游"未映射不扣"的保守原则搬进了 prompt。）

### 5.4 ★用户反例的处置（必须被用作最小测试用例）

**反例**：标准包 `int i = 0;` vs 学生 `int i = 1 - 1;`

| 项 | 判定 |
|---|---|
| 程序判定 | **不等**（字节不同，LCS 出 1 hunk / 2 行） |
| 语义判定 | **等**（`1 - 1 == 0`） |
| **契约分类** | ★**A 类（等价改写）** |
| **是否扣分** | ★**不得扣分** |
| **为什么** | 学生的写法与标准包**语义相同**，只是用了不同的表达式求值路径 |

**契约里靠什么措辞把它固定住**（这三句必须逐字进 prompt）：

> 1. **「差异 ≠ 错误」**：清单中的每一条差异都是**待判定的候选**，不是缺陷。**未判定为 D 类的条目不得扣分。**
> 2. **「语义等价的改写属于 A 类」**：即使代码在文本上**完全不同**（例如把常量替换为等价的表达式、
>    把 `if/else` 改写为三元表达式、把内联值改写为等价的计算），只要**行为相同**，即为 A 类，**不得扣分**。
> 3. **「不确定时必须按 A 类处理」**：若无法确信某条差异会改变行为，**不得**判定为 D 类
>    （参见 §5.3 规则 3 的代价不对称论证）。

**并把这个反例本身作为 1~2 个 few-shot 锚点之一放进 prompt**（见 §6.4）。
同时必须放**第二个锚点**：`int i = 0;` vs `int i = 1;` —— **同形状、判 D 类**。
**两个锚点必须成对出现**，否则模型会学到"凡差异皆 A"或"凡差异皆 D"的单边策略。

### 5.5 差异清单的构造（文件级 + 行级）

```
输入： stdMap: Map<relPath, content>（标准包，规范化后）
      stuMap: Map<relPath, content>（学生，规范化后）

① 文件级分类：
   same      : relPath ∈ 两者 且 content 逐字节相同      → 【不进清单】（这是 token 节省的主体）
   modified  : relPath ∈ 两者 且 content 不同            → 进清单，做行级 diff
   onlyStd   : relPath ∈ std 且 ∉ stu                    → 进清单（"学生未提交"，缺文件类）
   onlyStu   : relPath ∈ stu 且 ∉ std                    → 进清单（"学生新增"）
   注：只含空白差异的文件也走 modified，由 LLM 判 C 类（或由程序预判为 C，见下）

② 行级 diff：LCS（本方案用 DP；生产建议用 Myers O(ND) 以省内存）
   输出 hunk：{ stdLines[aLo,aHi), stuLines[bLo,bHi) }

③ 渲染（★格式即接口）：
   【差异清单】
   - <relPath> : 学生未提交（标准包有）        ← onlyStd，文件级
   - <relPath> : 学生新增（标准包无）          ← onlyStu，文件级
   ## <relPath>  (标准包 N 行 / 学生 M 行)      ← modified
   @@ 标准包 a-b → 学生 c-d
   <上下各 2 行的上下文，前缀 ' '>
   - <标准包原文>                               ← 删除行，前缀 '- '
   + <学生原文>                                 ← 新增行，前缀 '+ '

④ ★降级闸门（见 §7.4）：若 Σ changedLines > 0.4 × 标准包总行数
   ⇒ 弃用清单，改走 L-3「关键文件全文」输入（清单在最坏情况下比全文还大）
```

**程序可预判的 C 类（零 LLM 剔除，进一步压清单）**：只含空白差异（`replace(/\s+/g,'') ` 后相等）→
直接标 C 类**不进 LLM 清单**。上游已实测该手段的等价物（`normalized_text` 规则）。
**注意它不抗引号差异**（`'a'` vs `"a"` 规范化后仍不等）—— 那类留给 LLM 判 C。

## 6. ★④ Prompt 当接口（prompt as interface）

### 6.1 设计原则

把 prompt 当**接口**（schema 的一部分）设计，而不是当聊天写：

| 原则 | 具体做法 |
|---|---|
| **固定结构** | 各段**固定顺序 + 固定标题**（`【输入类型】`→`【评分标准】`→`【差异清单】`→`【关键文件全文】`→`【输出契约】`）。**任何一段缺失也要保留标题并写"（无）"** —— 保证两种输入形态的 prompt 前缀逐字节一致（可缓存、可对比、可回归） |
| **分数带锚点** | 明确写出各分数带的定义（§6.3）—— 针对实测失效模式「**双峰·解释摇摆**」（LLM 在"严格解释"与"宽松解释"间跳，中位数聚合失效，见 `selfconsistency-report`） |
| **先证据后结论** | 每条判定必须 = `evidence`（文件 + 行 + 原文）在前，`verdict` 在后 |
| **输出契约** | 固定 JSON schema（§6.5），含**逐条判定结果** |
| **few-shot 锚点** | 1~2 个（本方案用 §5.4 的**成对反例**） |

### 6.2 改造点（基于现有 `buildProjectGradePrompt` + `PROJECT_ROLE`）

**改哪几处（共 5 处，全部集中在 `server/src/domain/services/deepseek/prompts.js`）**：

| # | 位置 | 现状（`prompts.js` 行号） | 改造 |
|---|---|---|---|

### 6.3 ★分数带锚点（针对「双峰·解释摇摆」）

```
【分数带锚点】
对每一个评分分项，只允许落在以下五个带之一；不得给出带外的分数。
  满分带    ：该分项要求全部满足，且未发现任何 D 类差异。        → 取该分项满分
  轻微带    ：存在 D 类差异，但只影响该分项的装饰性/次要子项。    → 该分项 80%~99%
  中度带    ：存在 D 类差异，影响该分项的一个主要子项。           → 该分项 50%~79%
  严重带    ：存在 D 类差异，该分项的主要功能缺失或错误。         → 该分项 1%~49%
  缺失带    ：该分项的载体完全不存在（文件/组件缺失）。           → 0 分
判定纪律：在同一份提交内，你必须对所有分项使用同一套严格程度；
不得对同一类差异在不同分项上给出不同的宽严判断。
若你发现自己在两个相邻带之间摇摆，必须选择【较低】的带，并在 uncertain 中记录该项。
```

**为什么这样写**：`selfconsistency-report` 实测 `10326` 是**双峰/模式切换**样本
（LLM 在"严格解释"与"宽松解释"两套标准间跳），`×5` 中位数聚合组间 std 仍有 4.65（仅缩减 1.1×）⇒ **聚合对双峰无效**。
分数带锚点把"连续打分"离散成"5 选 1 的带"，**降低解释自由度**，是**直接针对该失效模式**的手段。
（**残余风险如实登记**：这**不保证**消除双峰，只是收窄；是否有效必须实测 —— 建议按 §12 的顺序做 A/B。）

### 6.4 ★Few-shot 锚点（成对，必须同时出现）

```
【判定示例】（两个示例的差异形状完全相同，结论相反 —— 用于校准你的判定标准）

示例 1（A 类，不得扣分）
  @@ 标准包 1-1 → 学生 1-1
  -   int i = 0;
  +   int i = 1 - 1;
  判定：{"class":"A","evidence":{"file":"<path>","stdLine":1,"stuLine":1},
        "reason":"1-1 求值为 0，与标准包语义相同，仅写法不同","scoreImpact":0}

示例 2（D 类，扣分）
  @@ 标准包 1-1 → 学生 1-1
  -   int i = 0;
  +   int i = 1;
  判定：{"class":"D","evidence":{"file":"<path>","stdLine":1,"stuLine":1},
        "rubricItem":"<必须逐字引用 rubric 分项名>","reason":"初始值由 0 变为 1，行为不同",
        "scoreImpact":<扣分，不得超过该分项满分>}

注意：示例 1 与示例 2 的差异【行数、位置、形状完全相同】，但一个是等价改写、一个是真实缺陷。
因此你【不能】依据差异的大小或数量判断，只能逐条阅读差异内容本身。
```

### 6.5 ★输出契约（JSON schema 固定）

```jsonc
{
  "inputMode": "DIFF",                    // "FULL" | "DIFF"  ← 新增，用于审计输入形态
  "totalScore": 78,                       // 保留：语义不变（= breakdown 之和，见下）
  "breakdown": [                          // 改：必须与 rubric 分项一一对应（顺序/名称/满分完全一致）
    { "item": "第三项 登录功能", "score": 16, "maxScore": 20,
      "band": "轻微带",                   // 新增：五个带之一
      "comment": "…" }                    // ≤60 字（保留既有约束）
  ],
  "diffJudgements": [                     // ★新增：逐条判定结果（差异清单里每一条都要有且仅有一条）
    { "id": "h1",                         // 清单里的 hunk 编号
      "class": "A",                       // "A" | "B" | "C" | "D"
      "evidence": { "file": "src/router/index.js", "stdLines": [8,11], "stuLines": [8,8],
                    "stdText": "- {\n-     path: '/',", "stuText": "+ (删除)" },
      "reason": "…",                      // A/B/C：为什么不算缺陷；D：错在哪
      "rubricItem": "第二项 路由与页面跳转", // D 必填；A/B/C 为 null
      "scoreImpact": 0,                   // A/B/C 必须为 0；D 为扣分数（≤ 该分项满分）
      "uncertain": false }                // 拿不准时 true（且 class 必须为 "A"）
  ],
  "uncertain": [                          // 新增：低置信度条目（供转人工探针消费）
    { "id": "h3", "why": "无法确定删除 path:'/' 是否影响 rubric 点名之外的路由要求" }
  ],
  "highlights": ["…"],                    // 保留：≤5（B 类差异必须写进这里）
  "issues": ["…"],                        // 保留：≤5（只允许来自 D 类）
  "overallComment": "…"                   // 保留：≤300 字
}
```

**三条校验（解析端硬校验，失败即重试/降级）**：
1. `diffJudgements` 的 `id` 集合 **必须等于** 差异清单的 hunk 集合（**不得遗漏、不得新增**）；
2. `class ∈ {A,B,C,D}` 且 **`class !== 'D' ⇒ scoreImpact === 0`**；
3. `class === 'D' ⇒ rubricItem ∈ rubric 分项名集合`（**绑定不上 ⇒ 判为 C，scoreImpact 归 0**）。

### 7.4 (e) ★差异清单的规模（会不会比全量代码更大？）

**答案：会。最坏情况下比全量代码大 2 倍。**

## 10. 风险与局限

### 10.1 ★「diff 不能作为扣分依据」的完整论证（本节是方案的安全边界）

**结论：差异（diff）可以用来决定"给 LLM 看哪里"，绝对不可以用来决定"扣多少分"。**

| # | 论证 | 依据 |
|---|---|---|
| **1** | **程序等价性一般不可判定**。判定两份代码是否等价 ≡ 判定两个程序在所有输入上是否等价 —— **图灵不可判定**（Rice 定理的推论）。因此**不存在**正确的机械映射 `diff → 扣分` | 理论 |
| **2** | **同一 diff 形状 ⇒ 相反结论**（实测反例）：`int i = 0;` vs `int i = 1 - 1;`（等价）与 `int i = 0;` vs `int i = 1;`（缺陷）的 diff **逐字节同形**（1 hunk / 2 行）⇒ **diff 规模对正确性零信息量** | 本方案 §5.1 论证 2 |
| **3** | **实测过扣规模 50%~60%**（下界）：B 组 20 人、4 hunk / 10 行差异中，**2 hunk / 6 行无 rubric 锚点或纯格式** ⇒ hunk 级过扣 50%、行级 60% | §7.2 |
| **4** | **激励反转（实测）**：A 组（diff=0，抄）**98.0** vs B 组（10 行差异，写）**80.2**。加"差异即扣分"后 B 组降到 **73.2** ⇒ 倒挂由 17.8 扩大到 **24.8 分** ⇒ **学生最优策略 = 抄标准包** | `exp353` + §7.2 |
| **5** | **标准包本身有缺陷时，"差异"可能是改进**：rubric 第九项「Axios 封装」标准包**自己没做** ⇒ 真做了封装的学生的 diff 会变大，却被扣分 | 上游 §5.4/§10.1 |
| **6** | **无法区分的三件事**：diff 工具**不能**区分「等价改写」「更好实现」「格式噪声」「真实缺陷」—— 这四类的**文本表现完全重叠**。只有逐条语义判定能分开 | 本方案 §5.3 |

**⇒ 因此本方案把 diff 严格限定在"注意力引导"这一用途**，并用 §5.3 的四分类契约 + §6.5 的三条硬校验把
"只有 D 类影响分数"变成**可自动校验的机器约束**（而不是一句提示词里的祈使句）。

### 10.2 结构性局限（承自上游，本方案无法解决）

| # | 局限 | 影响 |
|---|---|---|
| 1 | **rubric 分项合计 110 ≠ 自称 100**（10+10+20+20+10+15+5+10+10） | 折算基数失真。本方案 §3.3 已按 110 对账；**建议先修 rubric 再上线分层** |
| 2 | **静态层只能扣分不能给分** | L-0 不能作为分数来源，只能是"前置事实 + 前置扣分" |
| 3 | **静态层对 B 组只能锁定 4 分** | B 组剩余 96 分仍由 LLM 决定；**本方案不声称能压缩 B 组的 std 4.55** |
| 4 | **"短路 = 满分"依赖"标准包 = 满分"这一校准假设** | 该假设**已被实测证伪 ≥1 次**（第九项 Axios）。若教师的标准包本身不满分，短路会给"原样复制缺陷"的学生满分。**缓解**：短路前必须过 L-0；且**教师体检报告**（checker review）须与短路层联动 —— 若标准包体检有未豁免的失分项，**该题禁用短路** |
| 5 | 数据集与真实 uploads 的一致性只在 3 份上验证过 | 见 §7.7 |

## 12. 实施顺序建议

> 原则：**每一步都可独立回退、都可影子运行、都不改变默认行为**。
> 排序依据：**收益/风险比** 与 **依赖关系**（后面的步骤依赖前面的产物）。

| 阶段 | 内容 | 产出 | 风险 | 依赖 |
|---|---|---|---|---|
| **S0** | **修 rubric 的 110≠100**（§10.2 局限 1）+ 教师拍板 §10.3 的 4 个口径 | 自洽的 rubric | 低 | — |
| **S1** | **纯计算层**：路径规范化 + 规范化文件树 sha256 + LCS 差异清单生成（**不接入评分链路**，只写日志） | 每份提交的差异清单（影子） | **极低**（零 LLM、零执行、毫秒级） | S0 |
| **S2** | **影子验证 S1**：在真实提交上跑，人工核对 ① 短路判定是否 100% 正确 ② 差异清单是否漏/错 ③ 降级闸门（F3）触发率 | 影子报告 | 低 | S1 |
| **S3** | **L-1 短路上线**（独立开关，默认关）：命中 ⇒ 确定性满分 + 写 `breakdown` 证据 | 33.9% 的学生零 LLM | **中**（"满分"是强承诺，须先确认标准包体检无未豁免失分；见 §10.2 局限 4） | S2 |
| **S4** | **加固 L-0**：F1（别名 import）、F2（未闭合引号），并把规则白名单对齐 11 种 | 更少漏检 | 低 | — |
| **S5** | **接线上游 L-0**：`defectPrecheck`/`defectScoring` 新建调用点（**这是接线改造**）+ 影子模式先跑 | L-0 硬扣 + 缺陷事实注入 | **中**（硬扣会改变分数分布，需教师知情） | S4 |
| **S6** | **L-2/L-3 上线**：新增 `getProjectContextMode = 'layered'`，接入 `buildProjectDiffPrompt` + 四分类契约 + 输出契约校验（§6.5 三条硬校验） | 94.7% token 节省 + 判定可审计 | **中高**（改变 prompt ⇒ 改变分数，**必须 A/B**） | S3、S5 |
| **S7** | **低置信度探针接线**（三条判据取并集，§9.2） | 转人工队列 | 低 | S6 |
| **S8** | **A/B 实测**：同一批提交，`filter`（现状）vs `layered`，比较 ① std ② 教师人工评分的一致性 ③ token 实耗 | 是否继续放量的判据 | — | S6 |

**★必须做 A/B 的一条**：S6 改变的是 prompt ⇒ **分数一定会变**（哪怕是同一个模型）。
**没有 A/B 就不上线**。A/B 的判据不是"分数变高还是变低"，而是**"分层后的分数与教师人工评分的相关性是否更好、std 是否更小"**。

**推荐的最小起步**：**S1 → S2 → S3**。
**理由**：这三步**零 LLM、零执行、不改默认行为**，却能拿下 **33.9% 的 LLM 调用**与 **35% 的 token 节省**，
且**短路是确定性的、不可争议的**（逐字节相同就是相同）。这是全方案**风险最低、收益最确定**的一段。
