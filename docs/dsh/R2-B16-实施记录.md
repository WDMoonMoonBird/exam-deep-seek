## 摘要（≤10 行）
1. **现场**：job 5 的 `ANCHOR_MATERIALIZED=yes frozen_sha256=sha256:2deb9f73…`，但装置 `ASSIGNMENT_FAIL_REASON=frozen-tampered(precheck)` + `TAMPER frozen_sha256_mismatch` ⇒ `RUN_EXIT=3`（fail-closed，311 分数逐位未变）。
2. **真因**：DB `checker_json`（MySQL JSON 列）**再序列化**回填 ⇒ 键序/空白变化 ⇒ 回填后 `out/checker/checker.json` = `29aa6805…`（19562 B）而冻结原文 = `2deb9f73…`（同 19562 B，字节不同、语义相同）⇒ 装置字节级预检正确地判 tampered。**装置行为正确，缺陷在 worker 的再序列化回填**。
3. **①新增字节级字段**：迁移 `20261012050000_r2b16_anchor_checker_raw` 给 `grading_assignment_anchors` 加 `checker_raw LONGBLOB NULL`（含 `rollback.sql`），**仅测试库**应用；`schema.prisma` 同步声明 `checkerRaw Bytes?`。
4. **②入库持久化 raw**：`readAnchorFromRunRoot` 读 `out/checker/checker.json`（缺失回退 `checker.frozen.json`）的原始字节；`persistAnchor` 写入该列（`COALESCE` 保留已有 raw，避免二次入库把 raw 抹掉）；两条路径（r2b7 / worker）都打 `ANCHOR_RAW_PERSISTED=yes bytes=<n> sha256=<…>`。
5. **③回填写原始字节**：`materializeAnchor` 直接 `writeFileSync(raw)` 到 `out/checker/checker.json` 与 `out/assignment/checker.frozen.json`（**不经过 JSON.stringify**），manifest 的 `frozen_sha256` 保持锚点原值 ⇒ 装置 `frozen_intact` 通过、`ASSIGNMENT_FROZEN_SHA256` = 原值。
6. **④历史锚点无 raw ⇒ 拒绝回填**：`ANCHOR_MATERIALIZED=no reason=raw_bytes_unavailable` 且**不写任何文件**（manifest/checker 都不写）⇒ 装置不会出现「字节不一致的 frozen vs manifest」⇒ 不会判 tampered；装置按既有行为自行重建（队长历史实测该路径 exit 0），消费侧走 materials-manifest 兜底。
7. **★实测（w40）**：入库 raw bytes/sha 与源文件一致；回填后 `sha256(out/checker/checker.json) == 锚点 frozen_sha256`（`shaMatchesAnchor=true`）、两份文件与源**逐字节相同**（`Buffer.equals`）、且**不等于** `JSON.stringify(JSON.parse(raw), null, 2)`（反例断言 ⇒ 证明没有再序列化）；`checker_id` 语义不变；manifest 的 `frozen_sha256` 保持原值。

## 4 未验证项（单列）
1. **真实装置端到端未跑**（不跑真实装置）：字节级不变式用**文件级/字节级断言**（w40-2）+ 装置读码（`lib_assignment.sh` 的 frozen_intact 口径）覆盖；job 5 现场已由队长实测确认装置行为正确、worker 缺陷在再序列化。
2. **生产迁移未执行**（契约：仅测试库）：生产 `grading_assignment_anchors.checker_raw` 列不存在 ⇒ 历史锚点全部走 `raw_bytes_unavailable` 分支（不回填、由装置自行重建 + 兜底映射），行为安全但无字节级回填。
3. **LONGBLOB 大尺子**：单把尺子约 19.5KB（现场）⇒ LONGBLOB 余量充足；未做超大尺子（MB 级）压测。
4. **`checker_raw` 与 `checker_json` 的漂移**：两者若来自不同 ingest（例如同一 (assignment, checker) 二次入库且 raw 用 COALESCE 保留旧的）可能出现「JSON 新、raw 旧」的组合 ⇒ 现场口径：`checker_json` 由 `consumeChecker` upsert（按 checker_id 唯一），同一 checker_id 意味着同一份尺子，风险低；未做专门的漂移检测。

## 5 自纠清单
1. **Prisma 无法表达 BLOB 的“原始字节”读写语义**：新列仍走**原始 SQL**（`?` 绑定 Buffer），并显式写 `created_at/updated_at`；`schema.prisma` 只声明类型（供未来 generate 使用），客户端未生成（禁 build）。
2. **COALESCE 保留已有 raw**：`ON DUPLICATE KEY UPDATE checker_raw = COALESCE(VALUES(checker_raw), checker_raw)` ⇒ 二次入库时若本次 run-root 没有 checker 文件，不会把已有 raw 抹成 NULL（否则会把可回填的锚点降级为历史锚点）。
3. **无 raw 时“不写任何文件”比“写一半”重要**：初版设计里 manifest 与 checker 是分开写的 ⇒ 若只写 manifest（frozen_sha256 指向旧字节）而 checker 用旧 JSON 再序列化，就会重现 job 5 的 tampered ⇒ 本轮把两件事绑成同一分支：要么都写（有 raw），要么都不写（无 raw）。
4. **`frozen_sha256` 取值优先级**：优先锚点原值（`anchor.frozen_sha256`），仅在缺失时回退到对 raw 求 sha ⇒ 保持「锚点是唯一真源」的口径。
