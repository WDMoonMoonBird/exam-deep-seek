# R2-B42 修复记录：回填源三处缺口（数组展开 / slug 姓名兜底 / 复用运行归档缺 grading-results.json）

> 摘要（≤10 行）：① **CAP-BF-1**：`--job/--from` 读到数组归档（云端实测 `grading-results.json` = array[40]，每条含 `submission_id`/`items`）时，
> 旧实现把**整个数组当一份的 items** ⇒ 只出 1 行、无 slug ⇒ `UNMAPPED`；现按条展开（`classifyArray` + `expandSubmissionArray`），
> slug 取 `submission_id` → `submission.id` → `slug`，都判不出则记 **`UNMAPPED_EXPAND source=… index=… reason=no_slug_field`** 明细。
> ② **CAP-BF-2**：映射顺序改为 ①`--map` 显式（最高）②源文档 `studentName`/`student_name` ③**slug 作 realName 兜底** ④slug 作 username 兜底 ⑤数值 slug 兜底
> ⇒ 云端「文件名=学生姓名」形态可**零人工映射**直接命中（via=`slug_as_realName_or_username`）。
> ③ **CAP-BF-3**：复用运行（measure-only、零 LLM）装置不写 `out/grading-results.json` ⇒ 归档缺逐份分项；现 `archiveRun` 在 device 未写时
> 用 `aggregateDetailResults()` 把 `out/grading-result/<slug>.json`（+ `out/grading-result.json`）聚合为**同形** `grading-results.json`（稳定排序、可逐字节对拍）；
> device 已写则**一行不改**（逐字节保留）⇒ build 与 reuse 两条路径产物一致。④ 测试 7 例全绿（含三项缺陷回归锁）；变异 M1–M3 全部「改回缺陷即失败」且还原逐字节一致。
> ⑤ 生产回填已由**队长用 `--map` 人工映射完成**（80/80 命中）；本批修复只让「无需人工映射」成为常态，未对生产执行任何写操作。

## 1. 三处根因与修法
| 缺口 | 根因（读码） | 修法（`server/scripts/backfill-ai-feedback.mjs` / `dshRunArchiver.js`） |
|---|---|---|
| CAP-BF-1 | `normalizeDoc(array)` 无条件返回 `{items: array}` ⇒ array[40] 被当「一份的 40 个 items」 | `normalizeDoc` 只认对象；新增 `classifyArray()`（条目含 `items`/`submission_id`/`submission`/`student_name` ⇒ `per_submission`）与 `expandSubmissionArray()`（逐条展开、slug 四级回退、缺 slug 记 `expandMissing` + 打印 `UNMAPPED_EXPAND`） |
| CAP-BF-2 | 映射只走「源文档 studentName」与「数值 slug」，**slug 本身没参与姓名匹配** | 映射顺序重排：`--map` → 文档姓名 → **slug 作 realName/username 兜底** → 数值 slug；`via` 取值可审计 |
| CAP-BF-3 | `archiveRun` 只 `copy(out/grading-results.json)`；复用运行没有该文件 ⇒ 归档缺逐份分项 | 新增 `aggregateDetailResults(runRoot)`（`out/grading-result/<slug>.json` > `out/grading-result.json`；条目含 `submission_id/student_name/totals/items/source`，按 `submission_id` 稳定排序）；`archiveRun` 在归档**尚无**该文件时写入，并记 `RUN_DETAIL_AGGREGATED=yes count=N`；失败只记日志不阻断归档 |
