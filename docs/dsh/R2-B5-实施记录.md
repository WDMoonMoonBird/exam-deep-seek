## 3 闸的多进程口径：选 (a) DB 级闸（理由）
- **为什么不选 (b) 单实例守卫**：单实例把「不能多开」变成运维纪律，而平台目标形态是「无人值守 + 可水平扩展」；守卫只能防重复，表达不了并发上限。
- **为什么能在不加列的前提下做 (a)**：grading_jobs.status = running 本身就是一个 DB 级并发计数。把闸写进同一条 UPDATE 即可原子生效：
```sql
UPDATE grading_jobs SET status = 'running', attempts = attempts + 1, last_error = NULL, updated_at = CURRENT_TIMESTAMP(3)
WHERE id = ? AND status = 'pending'
  AND (SELECT COUNT(*) FROM (SELECT id FROM grading_jobs WHERE status = 'running') AS r) < ?;
```
  - MySQL 不允许 UPDATE 的子查询直接引用目标表 ⇒ 用派生表包一层（合法写法，buildClaimSql 固定生成）。
  - limit 默认取 dsh_grading_concurrency（批 1 getter），可用 DSH_WORKER_DB_LIMIT 覆盖。
- **两层闸**：进程内 createGate(limit)（挡住同进程并发，快）+ DB 级闸（挡住跨进程）⇒ 任一层都不会让装置并发数超过 limit。

## 6 自纠清单
1. **一次 shell 事故**：set -e 下 Python 补丁断言失败 ⇒ 同一脚本里随后的两个新建文件根本没执行，测试直接报「Could not locate module」。教训：**补丁脚本与新建文件分两次执行**（随后单独重发了两份服务文件）。
2. **Python 字符串转义**：锚点里含 JS 的转义单引号，Python 普通字符串会把反斜杠吃掉 ⇒ 断言失败；改用 r 原样串后一次通过。
3. **测试自身的两处 bug**：w19 的 split 换行字面量被写成真实换行（改为 String.fromCharCode(10)）；w18 的 select 漏了 writtenCount（断言拿到 undefined）。
4. **睡眠实现**：sleepInterruptible 用 setInterval 轮询停止标志（10–50ms），保证 SIGTERM 后不必等满退避；unref() 避免阻塞进程退出。
