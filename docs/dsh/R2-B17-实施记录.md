# R2-B17 实施记录（僵尸 running 行回收：启动即回收 + 阈值可配 + 留痕）

## 摘要（≤10 行）
1. **缺口**：并发闸是 **DB 级**（按 `status='running'` 行数 < `dsh_grading_concurrency`）。进程被中断/断电/重启会留下 running 行 ⇒ 后续每个窗口都**领不到 job 且不报错**（静默停摆，最危险的失败模式）；本团队已在生产实测到一次（失败记账撞旧唯一键 ⇒ job 卡 running，队长手工清理）。
2. **①启动即回收**：新增 `server/src/services/dshStaleJobReclaimer.js`：worker 在**领取第一个 job 之前**调用 `reclaimStaleRunning()`，把 `status='running'` 且 `updated_at` 早于阈值的行回收——`attempts < maxAttempts` ⇒ 置回 `pending`（`last_error=stale_running_reclaimed`）；`attempts` 用尽 ⇒ `failed`（`stale_running_exhausted`）。
3. **★不误伤**：更新语句带 `WHERE id=? AND status='running' AND updated_at < 阈值` ⇒ 正在跑的真实 job（`updated_at` 新）**不可能**被回收（w42-2 实测保持 running 且无 last_error）。
4. **②留痕**：每次回收打印摘要行 `STALE_RECLAIMED n=<总数> to_pending=<n> to_failed=<n> conflicts=<n> stale_ms=<阈值>`（不得静默），并 `logger.warn` 结构化记录；`WORKER_START` 增打 `stale_running_ms=<阈值>`。
5. **③活动键语义**：回收后同 (assignment, checker) 仍**至多一条活动行**——DB 层活动键（R2-B12）本就禁止 pending+running 共存（w42-3 实测第二条活动行 P2002）；若真有历史/异常数据造成冲突，该僵尸行置 `failed`（`stale_running_active_key_conflict`）并计入 `conflicts`（w42-3b 用假 prisma 直测该防御分支）。
6. **④阈值可配并文档化**：`DSH_WORKER_STALE_RUNNING_MS`（毫秒；缺省 **15 分钟** = `DEFAULT_STALE_RUNNING_MS`），非法值回退缺省（w42-0 实测）；`parseWorkerConfig` 同步暴露 `staleRunningMs`。
7. **★端到端实测（w42-4）**：僵尸行（20 分钟前、attempts=1）⇒ 回收为 `pending` ⇒ `runOnce` 领取并**完成** ⇒ job `done` / `written_count=1` / 提交 `ai_score=77` ⇒ 证明该机制真正解开了 DB 级闸。
8. **⑤定时形态运维配方**：见 §3（systemd timer + `--once`/`--max-iterations`/`--timeout-ms` + 为什么需要本机制）。
9. **verify（串行）**：check-layers 0 违规；unit **54 套件/715 例**；contract **3/50**；三重度 17/61/21；integration **55 套件/416 例**；smoke **8/8**；生产库指纹 before/after **逐位相同**。
10. 未验证项与自纠见 §4/§5。

## 3 定时形态运维配方（systemd timer）
**为什么需要本机制**：定时窗口形态每次只跑有限时间（`--max-iterations`/`--timeout-ms`），进程随时可能被 timeout/重启/断电打断；而闸是 DB 级计数 ⇒ 一条僵尸 running 行就会让**后续所有窗口**静默领不到 job。启动即回收把「静默停摆」变成「可自愈 + 有日志」。
```ini
# /etc/systemd/system/dsh-grader-worker.service
[Unit]
Description=DSH 作业级批改 worker（单窗口）
After=network-online.target mysql.service

[Service]
Type=oneshot
WorkingDirectory=/path/to/Exam-DeepSeek/server
# 生产：显式双开关 + 显式真实装置 + 复用已入库尺子（零 LLM）
Environment=DSH_WORKER_DB_LIMIT=1
Environment=DSH_WORKER_STALE_RUNNING_MS=900000
ExecStart=/usr/bin/node scripts/r2b5-worker.mjs --once \
  --db-url mysql://<user>:<pass>@<host>:3306/exam_system \
  --allow-db exam_system --allow-prod \
  --reuse-checker \
  --device bash --device-arg scripts/dsh-grader/run.sh \
  --device-arg --submissions --device-arg 63 --device-arg --allow-identical
# 退出码语义：0 正常/收到信号；3 连续失败超上限；2 守卫拒绝（授权/装置防呆）；4 用法错误
Restart=no

[Install]
WantedBy=multi-user.target
```
```ini
# /etc/systemd/system/dsh-grader-worker.timer —— 按峰谷窗口定时拉起（示例：每 5 分钟一次，避开上课高峰）
[Unit]
Description=DSH 批改窗口调度

[Timer]
OnCalendar=*-*-* 00,02,04,06,08,10,12,14,16,18,20,22:00/5
Persistent=true
AccuracySec=30s

[Install]
WantedBy=timers.target
```
- 用法要点：`--once`（单窗口，配 timer）或 `--max-iterations N`（窗口内最多消费 N 个 job）+ `--timeout-ms`（单 job 上限）⇒ 窗口不会无限占用；
- 每次窗口启动都会先回收僵尸行并打印 `STALE_RECLAIMED …`，可直接进日志/告警（`to_failed>0` 或 `conflicts>0` 值得人工看一眼）；
- 手工排障：`journalctl -u dsh-grader-worker -n 200`、`node scripts/r2b5-worker.mjs --once --db-url … --allow-db … --allow-prod --device bash --device-arg scripts/dsh-grader/run.sh --dry-run`（r2b7 侧有 dry-run；worker 侧可用 `--once` + 看 `STALE_RECLAIMED`/`WORKER_EXIT`）。

## 4 未验证项（单列）
1. **真实生产环境执行未做**（本轮不写生产）：机制在测试库端到端验证（W42-4）；生产首次窗口的日志请核对 `STALE_RECLAIMED` 与 `stale_running_ms=900000`。
2. **真正断电/强杀**未演练：本轮用「回填 updated_at 到 20 分钟前」模拟僵尸行；进程被 SIGKILL 后的实际 `updated_at` 停留时间未实测（机制不依赖具体杀法 ✓）。
3. **多窗口并发**：回收语句是条件更新（并发安全 ✓），但未做「两个 worker 同时启动回收」的并发压测。
4. **`--max-iterations` 与回收的交互**：回收发生在循环之前、不计入 iterations；未专门测「窗口内回收后剩余次数」的边界（语义上无影响 ✓）。

## 5 自纠清单
1. **冲突场景在 DB 层不可构造**：初版 W42-3 想造「同 (assignment,checker) 的 pending + running」⇒ 直接被活动键拒绝（P2002）。改为两条断言：①DB 层本就禁止（证明不变式）②用**假 prisma** 直测回收器的防御分支（真实数据若违背不变式时的行为）。
2. **时间戳字面量**：MySQL 侧比较用 `DATE_FORMAT` 兼容的 `YYYY-MM-DD HH:MM:SS.fff` 字面量（由 `toISOString().slice(0,23)` 生成），避免驱动时区/JSON 序列化差异；测试里回填也走同一格式。
3. **回收失败必须 fail-soft**：初版把 `reclaimStaleRunning` 直接 await（未包 try/catch）⇒ 连不上库时（w26-3/w29 的死 URL 场景）worker 在循环之前就抛错 ⇒ 破坏了既有「连库失败计 failures 后正常收尾」的语义（w26/w29 两个既有套件立刻失败）。已改为 try/catch：打印 `STALE_RECLAIMED n=0 … skipped=reclaim_failed:<msg>` 后继续，**窗口不被拦**。
4. **不引入新列**：本机制用 `updated_at` 作为「心跳」载体（既有的 `@updatedAt` 语义天然满足：每次领取/记账都会刷新）⇒ 不需要迁移；若未来要做**长任务心跳**，可另加心跳列（`--timeout-ms` 已限制单 job 上限，当前足够）。
