## 7. "使既有 token 失效"独立评估（不实现）
- **现状（实测 + 读码）**：JWT 无状态（`jwt.sign` 时不带版本），中间件 `jwt.verify` 后 `req.user = user`；改密**不会**使已签发 token 失效（C43/E10 与 B58 记录一致）。
- **方案 A（B 推荐；我同意优先）**：User 增 `password_changed_at`（nullable），中间件在拿到用户后比较 `payload.iat < password_changed_at` 则 401。成本=**1 个迁移（加列，不改表数指纹）** + 中间件一次比较（若中间件已查库则零额外查询；若否，加 60s 级缓存即可）；**不动 JWT_SECRET**（避免全员强制重登）。
- **方案 B（B 备选）**：User 增 `token_version`，签发时写入、中间件比对；改密自增 ⇒ 语义更强（可"一键全端下线"），但需签发/校验两侧改动 + 迁移。
- **我的补充（方案 A 落地注意）**：①**所有设密路径**（自助改密 / 管理员重置 / 教师重置学生 / 批量建号）都要写 `password_changed_at`，否则"重置后旧 token 仍有效"的新窗口；②用**秒级** `iat` 与秒精度列比较，避免同秒边界误踢；③若中间件当前不查库，需评估每请求一次查询的代价（缓存或把 iat 对比下推到需要的接口）；④配套测试：改密后旧 token 401、新 token 可用、他人 token 不受影响。
- **结论**：A 成本最低且与现有结构契合，优先；B 仅在需要"强制全端下线/多端会话管理"时值得。
