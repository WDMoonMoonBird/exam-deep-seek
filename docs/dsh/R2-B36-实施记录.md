## 2. 探针结论（2026-10-13 实测；"取不到就如实写 null" 的依据）
1. **projcache 是 token 唯一权威来源**：`home/storages/session_projcache/sessions/*.json`（`{version, record:{identity, rows}}`）里
   `rows.tokenUsage.val = {totals:{uncachedInputTokens,outputTokens,cacheReadTokens,cacheWriteTokens}, last:{turn,step,buckets}}`；
   另有 `rows.sessionStats.val = {turns,steps,llmMs,toolMs,ttftMs,decodeTokens,lastTurn,pendingCalls}`、`rows.sessionListMetadata.val.lastPromptAt`。
   兼容聚合文件 `session_projcache.json` 的 `tables.sessions['session-<id>']`。
2. **逐次分桶不可得**：`tokenUsage.val.last.buckets` 只是**最后一次**调用的分桶（不是数组）；会话 jsonl 的记录族
   （`step/start|step/end|request/header|assistant/message|tool/call|tool/result|…`）**没有** per-call usage/usageDelta 字段
   （两种格式实测：旧 `session.jsonl.zstd` 与 `session.v4.jsonl.zstd` 皆无）。
   ⇒ `calls: null` + `calls_note` 说明；`model_calls` 取 `sessionStats.steps`（每 step≈一次模型调用），可在记录中复核。
3. **工具调用可从会话 jsonl 取到**（**可取即落**）：`tool/call{callId,name}` + `tool/result`（时间差=顶层工具耗时）；
   run_code 内层工具：旧版 `tool/code-dispatch-start`/`tool/code-dispatch`、v4 `tool/ptc-dispatch-start`/`tool/ptc-dispatch`
   （`name`、`isError`、时间差=耗时）⇒ 聚合 `tools:[{name,count,ms,errors}]`，`tools_source=session_jsonl`。
   实际模型取 `request/header.data.header.config.model`（本批实测 `deepseek-v4-flash` ⇒ 命中 flash 档）。
4. **`.zstd` 是多帧拼接**：Node 的 `createZstdDecompress()` 只吃第一帧（实测报 `ZSTD_error_prefix_unknown`）
   ⇒ 本模块按帧魔数 `28 B5 2F FD` 切分**逐帧解压**（带 `JSONL_MAX_FRAMES=20000`/`JSONL_MAX_BYTES=64MiB` 上限，teardown 绝不拖死）。
   实测：3.3MB 会话日志抽取耗时 ~90ms（12 个工具名）。
5. 干扰产物（`out/coverage-*.json`/`out/matrix-*.json`/`out/results/*.json`）**不参与**用量口径（测试夹具已含 4 份并断言不受影响）。

## 3. session-usage.json 结构（schema `session-usage/1`）
```jsonc
{ "schema": "session-usage/1", "run_root": "…", "computed_at": "…", "price_version": "2026-10-13:db",
  "price_effective_from": "2026-10-13", "price_tier": "idle|peak|mixed", "cost_basis": "session_reference_time",
  "reference_time": "…", "model": "deepseek-v4-flash",
  "sessions": [ { "session_id", "model_calls", "turns", "totals": {四个 token 字段}, "last_buckets", "session_stats": {llm_ms,tool_ms,decode_tokens,ttft_ms,last_step}, "created_at", "last_prompt_at" } ],
  "totals": { "uncached_input_tokens","output_tokens","cache_read_tokens","cache_write_tokens","input_tokens","model_calls","turns","llm_ms","tool_ms","cache_hit_rate" },
  "tools": [ {"name","count","ms","errors"} ] | null, "tools_source": "session_jsonl|session_jsonl_truncated|unavailable",
  "cost": { "currency":"CNY", "cost_total": 0.27899, "model_key":"deepseek-flash", "breakdown":{input_hit,input_miss,output}, "per_call": null },
  "no_model_session": false, "calls": null, "calls_note": "逐次分桶不可得…" }
```
- 命中率 = `cache_read/(cache_read+uncached_input)`（无输入 ⇒ `null`，不写 0/1 假值）——与任务口径逐字一致。
- 实测样本（真实 projcache 会话，只读拷贝）：totals `63015/36521/3494528/0` ⇒ 命中率 **0.982287**、idle 档费用 **0.278990 元**。

## 4. 价目表（`system_configs.llm_prices`，可配置）
- 默认值（代码内 `DEFAULT_LLM_PRICES`，**官网口径**）：flash `cache_hit 0.02(idle)/0.04(peak)`、`cache_miss 1/2`、`output 4/8`；
  pro `0.15/0.30`、`4.5/9.0`、`13.5/27.0`；`currency=CNY`、`unit=per_1m_tokens`、`effective_from=2026-10-13`。
- 高峰窗口：`peak_windows=[{weekdays:[1..5],09:00-12:00},{weekdays:[1..5],14:00-18:00}]`（**北京时间**，不依赖宿主时区）；
  `holidays:[]`（按官方公布填入；命中即全天按空闲计）。其余（含周末）⇒ 空闲（高峰半价）。
- 读取永远是「默认值 + DB 覆盖」的**完整有效表**（DB 坏配置 ⇒ 记 `invalid_reason` 并回退默认，不崩）。
- 管理接口（沿用既有 AiConfig 形态，**不需要新路由**）：`GET /api/admin/settings` 返回 `llm_prices`（有效表）+
  `llm_prices_source=default|db`；`PUT /api/admin/settings {llm_prices}` 校验通过即写库并即时生效，校验失败 ⇒ 400 + `data.reason`
  且**不改库**。两接口都在既有 `/api/admin` 之下 ⇒ **鉴权由 admin 路由层统一承担**（`auth + requireRole('super_admin')`，
  未登录实测 401/403）。

## 8. 边界与已知限制（明确声明）
1. **逐次分桶不可得** ⇒ `calls=null`；费用按会话参考时刻单档（保守），纯函数支持跨时段但本批无逐次时间戳可用（若未来 DSH 在
   projcache/jsonl 暴露 per-call usage，只需在 `captureSessionUsage` 里改传 `calls[]`，计费与落库结构不变）。
2. 费用模型：价目表未覆盖的型号 ⇒ `cost_total=null` + `reason=model_not_priced:<model>`（不猜价）；无模型会话 ⇒ 0 元且
   `no_model_session=1`。
3. `holidays` 默认空：只做查表，不内置日期（避免猜错官方安排）；填入即生效（含测试覆盖）。
4. 会话日志解析有上限（帧数/字节）⇒ 超限时 `tools_source=session_jsonl_truncated` 如实标注（不静默截断）。
5. 本批不接线只读 API/页面（P1 后半：`GET /api/admin/grading-runs/:id` 的 usage 面板由后续任务做；`grading_job_runs.teardown_json.usage`
   与 `grading_run_usage` 已就绪可直接读）。
6. 生产迁移未执行（仅测试库）；生产由队长在授权窗口执行（先备份 + rollback.sql 就绪）。
