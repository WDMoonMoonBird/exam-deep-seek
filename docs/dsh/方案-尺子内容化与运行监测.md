## 1. 你问的「尺子是否应该入数据库」——**应该，而且现在已经在库里**
现状（已在库）：
- `grading_checkers`：尺子脚本（`checker_script`）+ 元信息（`checker_meta`）+ 状态（`status=ready`）
- `grading_assignment_anchors`：冻结尺子（`frozen_sha256`）+ **原始字节**（`checker_raw LONGBLOB`）+ `rubric_snapshot`/`material_snapshot`/`standard_hash`
要改的只是**键**：从「按 assignment_id」改为「按 content_key」，并保留「作业 → 它当时用的尺子」的绑定。

入数据库的四条理由：
1. **可复现/可审计**：谁、何时、用哪个模型、哪份输入造出这把尺（含 input 的 hash 与原文快照）；
2. **跨班/跨教师复用**必须有一个全局索引（文件系统没有事务与唯一约束，会并发造两把）；
3. **可比性分组**必须长期指向同一把尺（分数可比性 = 同一 checker_id）；
4. **文件不可靠**：我们已实测 run-root 会被剪枝/清理，靠文件存尺子必然丢。

## 2. 数据模型变更（纯增量，含 rollback）
```sql
-- ① 新表：内容指纹 → 尺子（全局唯一）
CREATE TABLE grading_rulers (
  id               BIGINT AUTO_INCREMENT PRIMARY KEY,
  content_key      CHAR(64)  NOT NULL,          -- sha256(标准工程包sha + 评分标准全文 + 题目描述全文)，规范化后
  status           VARCHAR(20) NOT NULL,        -- building | ready | failed
  checker_id       VARCHAR(80) NULL,            -- = frozen ruler sha256（ready 时）
  standard_sha256  VARCHAR(80) NULL,
  rubric_sha256    VARCHAR(80) NULL,
  description_sha256 VARCHAR(80) NULL,
  model            VARCHAR(64) NULL,            -- 造尺使用的模型（审计）
  source_run_id    BIGINT NULL,                 -- 哪次运行造的（审计）
  frozen_sha256    VARCHAR(80) NULL,
  checker_raw      LONGBLOB NULL,               -- 锚点原始字节（复用现有锚点机制）
  created_at       DATETIME(3) NOT NULL,
  updated_at       DATETIME(3) NOT NULL,
  UNIQUE KEY uniq_grading_rulers_content_key (content_key),
  KEY idx_grading_rulers_checker (checker_id)
);
-- ② 绑定表：某作业的某题【当时】用哪把尺（历史分数不可变的锚）
CREATE TABLE assignment_question_rulers (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  assignment_id INT NOT NULL, question_id INT NOT NULL,
  ruler_id      BIGINT NOT NULL,
  bound_at      DATETIME(3) NOT NULL,
  UNIQUE KEY uniq_aqr (assignment_id, question_id)
);
-- ③ grading_jobs 增列：content_key（便于审计与复用命中统计），保留 assignment_id（提交集）
ALTER TABLE grading_jobs ADD COLUMN content_key CHAR(64) NULL, ADD KEY idx_grading_jobs_content (content_key);
```
兼容性：现有 `grading_checkers`/`grading_assignment_anchors` **不动**（老数据继续可用）；新表先双写，回滚 = DROP 新表 + DROP 新列（有 rollback.sql）。

## 3. 解析流程（关键行为）
```
教师点「立即批改」/ 定时触发（作业 A，题目 Q）
  1) 算 content_key = sha256(标准工程包 sha + 评分标准 + 题目描述)      ← 只读，零成本
  2) 查 grading_rulers：
       ready  → 直接复用（★零 LLM，跨班/跨教师都命中）
       building → 等待/加入（并发去重，见 §4）
       无      → 建一条 building ⇒ 造尺一次（1 次模型会话）⇒ 置 ready 并写 checker_raw
  3) 绑定 assignment_question_rulers(A,Q) = 该 ruler（首次绑定；已有绑定则校验一致）
  4) 量尺（零 LLM），分数写入时记录 submissions.checker_id = 该尺
★ 后续任何时候改了评分标准/题目 ⇒ content_key 变 ⇒ 只有【新布置】会走新尺；
   老作业的绑定不变 ⇒ 老班级分数【永不变化】（满足你的第 3 条裁定）
```

## 4. 并发与竞态（必须处理）
- 两个作业同内容**同时**触发 ⇒ 用 `UNIQUE(content_key)` + `status=building` 抢占：抢到者造尺，另一者**轮询等待**（复用等待者不写库）；
- 造尺失败 ⇒ `status=failed` + 记录原因（可重试）；等待者超时后按失败处理（fail-closed，不产出分数）；
- 与既有"1 个并发作业"闸（`dsh_grading_concurrency=1`）兼容：闸只限制**同时运行数**，不阻止复用命中。

## 5. 运行监测（你的第二项需求）
### 5.1 取数（★必须在销毁会话之前）
在 teardown 的**取证阶段**（销毁前）从 `<run-root>/home/storages/session_projcache/sessions/session-*.json` 抽取：
```json
// <run-root>/out/session-usage.json  （与 run-teardown.json 并列落盘并归档）
{"schema":"session-usage/1","sessions":[
  {"session_id":"…","model_calls":N,"totals":{"uncached_input_tokens":114015,"output_tokens":38271,
   "cache_read_tokens":4518528,"cache_write_tokens":0},
   "calls":[{"seq":1,"uncached_input_tokens":…,"output_tokens":…,"cache_read_tokens":…,"ts":…}],
   "tools":[{"name":"read","count":3,"ms":1200}],
   "cost":{"currency":"CNY","input_miss":…,"input_hit":…,"output":…,"total":…,"price_version":"…"}}]}
```
实测依据（装置造尺会话真实值）：`tokenUsage.val.totals` = {uncachedInputTokens:114015, outputTokens:38271, cacheReadTokens:4518528, cacheWriteTokens:0}；`last.buckets` 提供逐次分桶。
命中率 = cache_read / (cache_read + uncached_input)。
**待确认（开工前 5 分钟探针）**：工具调用清单的字段名（会话 rows 里已见 `plan/todos/llmRetry/turnBoundary` 等；若无直接字段，则解析会话 jsonl 的 tool 记录，或退化为"工具调用不可得"并如实标注）。
### 5.2 价目表（可配置）
`system_configs` 增 `llm_prices`（JSON）：`{currency, cache_hit_input, cache_miss_input, output, effective_from, note}` + 管理端可读写（沿用 AiConfig 页形态）；费用=按桶乘单价，**价目版本随记录落库**（便于日后复核）。
### 5.3 元信息（你列的全部字段）
从库关联：老师（`assignments.teacher_id`→`users`）、**班级（`assignment_classes`→`classes`，多班全取）**、作业名/ID、标准工程包（`assignment_questions.material_snapshot` 的 sha）、题目描述、评分标准（`rubric_snapshot`）；一并落进运行记录（快照），保证日后作业改名/改标准也能还原当时的元信息。
### 5.4 落库与展示
- 新表 `grading_run_usage`（run_id, model_calls, input/output/cache tokens, cost, price_version, tools_json, sessions_json）+ 迁移；
- 只读 API 扩展 `GET /api/admin/grading-runs/:id`（新增 usage/meta/tools 三块）+ 列表增列（费用、缓存命中率）；
- 页面：在既有「批改记录」详情抽屉加三块面板（用量 / 元信息 / 工具调用）；**零 LLM 运行显示「本次无模型会话（零 token）」**。

## 7. 风险与边界（先说清）
1. **老数据兼容**：本期不做数据回填（老 `grading_checkers` 行保留）；新作业走新路径；老作业再次批改时若内容未变 ⇒ 命中新表（首次会补建一次尺子，可从老锚点复用，避免重复造尺）；
2. **教师跨用**：尺子只由「标准工程包 + 评分标准 + 题目描述」生成，**不含任何学生数据** ⇒ 跨教师复用不涉及隐私；
3. **造尺失败**：fail-closed（不产出分数），`status=failed` + 原因留痕，可重试；
4. **成本**：复用命中时 **0 token**；只有内容首次出现才花 1 次造尺（实测样本约 11.4 万未命中输入 + 3.8 万输出 + 451 万缓存读）；
5. **本期不做**：跨班对比视图（你否掉）、「重新造尺」UI（保留设计，供教师复审后续议题）。
