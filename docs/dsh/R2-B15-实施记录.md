## 摘要（≤10 行）

## 2 清理顺序与理由（FK 依赖序，依据测试库实测外键）
| 序 | 语句（新增/原有） | 理由 |
|---|---|---|
| 1 | `projectSubmission.findMany(projectId∈教师 projects)` → `submissionFile.deleteMany(submissionId∈…)` → `projectSubmission.deleteMany` | `submission_files.submission_id → project_submissions.id`；先把project 域子表清空 |
| 2 | `projectFile.deleteMany` / `projectClass.deleteMany` | 二者 `project_id → projects.id` |
| 3 | `project.deleteMany(id∈…)` | `projects.teacher_id → users.id` ⇒ **旧代码缺这条，正是 FK 失败源** |
| 4 | `team.deleteMany(createdBy=教师)` | `teams.created_by → users.id`（原有只按学校名删 team，可能漏教师自己建的） |
| 5 | `submission.deleteMany` → `assignmentClass.deleteMany` → `assignmentQuestion.deleteMany`（原有） | 三者分别 `assignment_id → assignments.id` |
| 6 | `assignment.deleteMany(teacherId=…)`（原有） | `assignments.teacher_id → users.id` |
| 7 | `subQuestion.deleteMany`（原有）→ **新增** `assignmentQuestion.deleteMany(question.teacherId)`、`submission.deleteMany(question.teacherId)` → `question.deleteMany(teacherId)`（原有） | `assignment_questions.question_id → questions.id`、`submissions.question_id → questions.id`（若某题只挂在别的作业下，原按 assignmentId 的清理会漏） |
| 8 | 学生侧：`submissionFile`（按 `submissionId∈学生 project_submissions`）→ `projectSubmission.deleteMany(studentId)` → 原有 `submission`/`studentClass`/`user.delete` | `project_submissions.student_id → users.id` 同样会挡删用户 |

1. **`student_classes`/`team_teachers` 等其它表的极端遗留**未构造：本轮按实测外键清单覆盖了会挡 `user.delete` 的全部路径，但未逐一造数据验证（理论依据 = `information_schema` 实测清单）。

## 6 自纠清单
1. **首版对「真因」的判断需要修正**：现行 setup.js **已有** assignments/questions 的清理（105-115 行），所以 t56 的 FK 失败并非「完全没清题/作业」，而是**漏了 projects（与 teams.created_by）**这类同样引用 `users.id` 的表。本轮以 `information_schema` 外键清单为准逐表核对后修正结论，并保留了原作业/题清理。
