## 1 判定口径（先说清"凭什么判"）
- **BCNF 定义**：关系 R 上每个非平凡 FD `X → Y` 都满足 `X` 是 `R` 的超键。
- **FD 的两个来源**（本文分别标注级别）：
  - **L1 声明级**：由 schema 声明的键/唯一约束直接保证（`schema.prisma` 的 `@id/@unique/@@id/@@unique` 与 migration 的 `PRIMARY KEY/UNIQUE KEY`）。
  - **L2 语义级**：由**代码契约**保证的 FD（含跨表"导入 FD"，如 `checker_id` 全局唯一 ⇒ 它决定 `assignment_id`）。L2 不满足 BCNF 的后果是**可消除冗余**与**更新异常风险**（一列两处、可能漂移），不是"数据立刻错"。
- **判定**：L1 违反 = 形式违反（必须修）；L2 违反 = 语义违反（应修，可排期）；其余判 ✓。
- **不作为 FD 依据的东西**：时间/状态演进带来的可变值（如"当前 rubric 是否变了"）本身不是稳定 FD，需明确其"快照 vs 当前"语义后再判（§3.3）。

### 2.3 疑点 A 的正面论证（为什么不是部分依赖）
- 写入证据：发布后在 `assignments.js:378-391` 逐题回填快照列（`buildPublishSnapshot(q)` 在 `:384`，失败只告警不阻断）；构造函数 `services/assignmentSnapshot.js:19-31` `buildPublishSnapshot(question)` —— 快照取**当次** `question.scoringRubric / rubricItems / material`，并写入 `capturedAt: new Date().toISOString()` 与 `rubricSha256`；`standardHash = standardPackSha256(question.id)`（读**当时**的标准包目录）。
- 决定因素分析：`capturedAt` 使 `rubric_snapshot` **随时间变化**；因此删掉 `assignment_id` 后 `question_id` 不能唯一决定它 ⇒ `question_id → rubric_snapshot` 不成立。同理 `standard_hash` 冻结的是"发布那一刻"的包哈希，而标准包目录可被后续替换（`questions.js` 编辑/重传路径）⇒ `question_id → standard_hash` 不成立。
- 同一作业内不同题目快照不同（每条链接一行）⇒ 也不存在"由 `assignment_id` 单独决定"的 FD。
- ⇒ 唯一决定因素是**整个复合键**：**无部分依赖、无传递依赖（L1/L2 均无），BCNF ✓**。
- 补充（非关系级）：`rubric_snapshot` JSON 内含 `rubricItems`/`rubricSha256` 等**派生值**——它们在同一属性内部，不构成关系 FD；但若将来把它们**提升为独立列**，就必须连同 `rubric` 一起放进以 `rubric` 为键的表，否则会引入 L2 违反（记录给后人）。
- 数据旁证（当前无样本）：`exam_system_test.assignment_questions` 的 `standard_hash` 分组查询返回空（R2-B1/B2 尚未写入快照行）⇒ 该论证目前靠代码语义，迁移后可用一条 SQL 复核（§8 命令 3）。

### 3.3 疑点 B：有没有传递依赖？
- **`canonical_sha256` 不是尺子的属性**（结论：无传递依赖）。证据链：装置把它定义为**整份结果**的规范化哈希——`check.py:54-57` `canon_sha256(result)` 对除 `run_meta/canonical_sha256` 外的全部字段取哈希，而结果含 `submission.digest / file_count / items`（`check.py:342-347`，见 R1-C 的 `submission.digest` 说明）；平台侧也是逐份结果里取值（`dshCheckerConsumer.js:168`、`:209`）。⇒ `canonical_sha256 = f(checker_id, 提交内容)`，去掉提交内容不能决定它 ⇒ **F7 不成立**。
- **`grading_stale` 的两种解读**（必须写清楚，否则判定会随时间口径漂移）：
  - 解读 1（**本行的逐次审计快照**）：值是"这一次量尺时，尺子声明的 rubric/标准包哈希与**当时**物料是否一致"，由 device 的结果 `stale` 直接抄写（`dshCheckerConsumer.js:77`）。同一份提交在不同时刻重写可不同 ⇒ 它不是稳定 FD ⇒ **BCNF ✓**，但列名会误导（建议改名 `stale_at_grading`）。
  - 解读 2（**该作业+该尺子当前是否陈旧**）：这是 `(assignment_id, checker_id)` 的属性（与哪份提交无关），而它在 `submissions` 里**被复制了 N 遍**（每份提交一行）⇒ `(assignment_id, checker_id) → grading_stale` 是 L2 FD，左部不是 `submissions` 的超键 ⇒ **BCNF 违反**（可消除冗余；若某次只重写了部分行，还会出现同一对里真假并存的不一致）。
- **判定**：按解读 2（推荐口径，也更贴合"陈旧=尺子过期"的产品语义）**违反 ⇒ 整改 J2**；按解读 1 则只是命名/冗余风险。两种口径下的整改动作相同（把该事实放到尺子/任务级），故不影响结论。

### 5.2 FD 与判定
| # | FD | 级别 | 判定 |
|---|---|---|---|
| F13 | `id → 全部列` | L1 | ✓ |
| F14 | `(assignment_id, checker_id, status) → 全部列` | L1 | ✓（是超键） |
| F15 | `checker_id → assignment_id` | **L2 违反** | `grading_checkers.checker_id` 全局唯一且每行只属一个 `assignment_id`（`schema.prisma:503-504`；消费点把 checker 的作业写入检查器：`dshCheckerConsumer.js:112-113` 的 `assignmentId` 来自触发时的 `job.assignmentId`，`dshGradingJobWorker.js:145`），而 `grading_jobs` 里 `checker_id` **不是超键**（同一对可有 `done` 与 `pending` 两行，见 5.3）⇒ 左部非超键 ⇒ 违反 |

### 5.3 疑点 C：status 入键 ⇒ 键随状态迁移而"换键"
- **是不是 BCNF 破坏？** 不是。任一时刻 `(assignment_id, checker_id, status)` 仍是超键，且 F14 决定全行 ⇒ 形式与语义都没有"非超键决定因素"。
- **真正的缺陷是键稳定性 + 约束表达力**（异常风险）：
  1. **键值随状态变化**：领取时 `UPDATE grading_jobs SET status='running' WHERE id=? AND status='pending'`（`dshGradingJobWorker.js:48-49`）、完成时 `finishJob` 写 `done/failed/needs_rerun`（`:76-80`、`:151-155`）；唯一键的取值三元组随之变化。把"状态"放进被唯一化的键，等于让"这条记录的键"承载业务状态——外部引用/审计用它做身份时会失稳。
  2. **幂等语义不完整（时序反例，纯代码可推）**：t1 触发创建 `(A,C,pending)`（`assignmentGradingController.js:30-38`）→ t2 worker 领取，该行变 `(A,C,running)` → t3 教师再触发：幂等查询只找 `status='pending'`（`:31`）⇒ 查不到 ⇒ 插入**第二条** `(A,C,pending)`（唯一键不冲突）⇒ 同一 `(A,C)` 同时存在 `running` 与 `pending` 两行，第一次结束后第二次会再跑一遍整作业。⇒ 业务规则"每对至多一个活动任务"**未被约束表达**。
  3. 附带：表被当作"隐式历史表"使用（每次重触发新增一行），但没有任何列能区分"活动/历史"（`pending/running` 之外的 `done/failed/needs_rerun` 也都只是状态字符串）。
- **替代设计（三选，按推荐排序）**：
  - **方案 1（推荐，改动最小）**：保留历史行，新增**生成列**表达活动键：`active_key = IF(status IN ('pending','running'), CONCAT(assignment_id,':',checker_id), NULL)` + `UNIQUE(active_key)`（MySQL 唯一索引允许多个 NULL）⇒ "每对至多一个活动任务"成为**数据库级约束**，历史行不限。
  - **方案 2（最干净）**：拆两表——`grading_jobs`（历史/审计，PK `id`，无状态唯一键）+ `grading_active_jobs`（活动任务，`PRIMARY KEY (assignment_id, checker_id)`）。
  - **方案 3（最小语义改动）**：`UNIQUE(assignment_id, checker_id, is_active)`，`is_active` 用 `NULL/1`（NULL 不参与唯一）表示非活动/活动；效果同方案 1，但不依赖生成列语法。
- **同时建议**：删掉 `grading_jobs.assignment_id`（F15 的冗余列），查询改为经 `grading_checkers` 关联；若为查询性能保留，则必须写明"它是 checker 的冗余副本"并在写入路径禁止两者不一致（至少加一条一致性断言测试）。
