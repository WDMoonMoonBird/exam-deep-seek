# R2-C17 独立验证（僵尸 running 回收 + 定时形态运维配方）

## 结论摘要（10 行）
1. **verdict = needs_revision（status=failed）**：t64 的回收机制在"按 w42 测试口径回填的时间戳"下成立，但在**生产真实领取路径**下**不成立**——领取语句写的是 `CURRENT_TIMESTAMP(3)`（数据库会话本地时区），而回收阈值用的是 `toISOString()`（UTC）⇒ **真僵尸行不会被回收**，DB 闸持续被占（实测：stale_ms=1000 时 `STALE_RECLAIMED n=0`、job 保持 `running`、worker `consumed=0`）。
2. **★F-T65-1（高/阻断级）时区错配**：本机/DB 会话 `time_zone=SYSTEM`=UTC+8；实测**领取路径行**的 `TIMESTAMPDIFF(SECOND, updated_at, UTC_TIMESTAMP(3)) = -28799`（即 `updated_at` 比会话 UTC **超前 28,799 s ≈ +08:00**）⇒ 回收阈值（UTC）永远追不上，僵尸要等 **约 8 h15 min** 才可能被回收（本环境 8 h 偏移 + 15 min 阈值）。机制的核心目的（崩溃后快速自愈）在生产口径下**落空**。
3. **★测试假绿（同因）**：w42 的 `backdate()` 用 `new Date(...).toISOString().slice(0,23).replace('T',' ')`（**与回收器同一 UTC 口径**）⇒ 夹具与判据同错相消，测试全绿而真实路径失效。最小复现见 §3。
4. **①两向回收（UTC 口径夹具下）【成立】**：`stale_ms=900000` ⇒ `n=2 to_pending=1 to_failed=1 conflicts=0`；attempts=1 ⇒ `pending/stale_running_reclaimed`、attempts=3 ⇒ `failed/stale_running_exhausted`；摘要行数字与 DB 行数一致；`STALE_RECLAIMED` 幂等（二次调用 `n=0`）。
5. **②不误伤【成立】**：`updated_at` 新的 running 保持 `running`、`last_error` 仍 `null`、不在 `details` 中（CLI 亦实测 `n=0` 时不误动）。
6. **③活动键防御【成立】**：假 prisma 直测 ⇒ 目标 `failed` + `stale_running_active_key_conflict`、`to_failed=1 conflicts=1 to_pending=0`；DB 层实测同对第二条活动行 ⇒ **P2002**、活动行恒为 1 条。
7. **④解锁闸【UTC 口径下成立、生产口径下失败】**：UTC 口径僵尸 ⇒ 回收后 worker 正常领取并消费（`consumed=1`）；**生产口径僵尸 ⇒ 回收 `n=0`、worker 在 limit=1 的闸下 `consumed=0`（库中存在其他 pending job 也领不到）⇒ 闸仍被占**（对应 F-T65-1）。
8. **⑤fail-soft【成立】**：不可达 DB（`127.0.0.1:19399/exam_system_test`）⇒ `STALE_RECLAIMED n=0 … skipped=reclaim_failed:`，随后 `STAGE=connect` 正常尝试、`WORKER_EXIT=0 iterations=1 consumed=0 failures=1`、rc=0 ⇒ 既有"连库失败计 failures 后正常收尾"语义未被破坏。
9. **⑥配置【成立，附两条建议】**：`resolveStaleMs({})=900000`（15 min）、`'60000'`⇒60000、`'abc'/'0'/'-1'`⇒回退 900000；`parseWorkerConfig` 暴露 `staleRunningMs`（env 45000/'xx'⇒45000/900000）；`WORKER_START … stale_running_ms=60000` 实测打印 ✓；**默认约定安全**：worker `--timeout-ms` 缺省 **600000 ms** < 阈值 **900000 ms** ✓，配方文档显式写 `DSH_WORKER_STALE_RUNNING_MS=900000` ✓（但**未**对"操作者把 --timeout-ms 调到 > 阈值"给出警告/断言 ⇒ 建议加一条告警，见 O-2）。
10. **⑦回归**：见 §6（unit/contract/integration + 生产零写入 + 残留）。**未改动任何 server/** 与装置侧**；本轮仅新增报告与证据。

## 1 方法
- **直测回收器**：测试库夹具（pending/running/attempts/age 各种组合）+ 直接调用 `reclaimStaleRunning`，逐行比对 DB 终态与摘要数字。
- **口径对照**：一类夹具按 `toISOString()`（UTC，= w42 的 backdate 口径）回填；另一类按**领取路径真实写法** `CURRENT_TIMESTAMP(3)`（本地）回填 ⇒ 对照回收是否发生。
- **CLI 端到端**：worker `--max-iterations 1 --reuse-checker` + 自建记录/复制型装置（零 LLM）观察 `STALE_RECLAIMED`/`WORKER_START`/`consumed` 与 job 终态。
- **fail-soft**：`--db-url` 指向不可达端口（库名仍为测试库，禁指真实生产实例）。
- 安全：仅测试库；未启动真实装置（零模型调用）；生产库零写入；探针自清理。

## 2 ★F-T65-1：时区错配（阻断级）
**证据（已实测）**
```
DB 会话: @@session.time_zone=SYSTEM；NOW(3)=15:20:04(+08) vs UTC_TIMESTAMP(3)=07:20:04 ⇒ 偏移 +28800 s
领取路径（dshGradingJobWorker.js:155-156）: UPDATE grading_jobs SET status='running', attempts=attempts+1,
    last_error=NULL, updated_at = CURRENT_TIMESTAMP(3) WHERE id=? AND status='pending'
回收阈值（dshStaleJobReclaimer.js:mysqlDateTime）: new Date(nowMs-staleMs).toISOString() ⇒ UTC 字面量
实测（领取路径产生的行）: TIMESTAMPDIFF(SECOND, updated_at, UTC_TIMESTAMP(3)) = -28799 ⇒ updated_at 超前 UTC 约 8 h
回收实测（stale_ms=1000/15000）: STALE_RECLAIMED n=0 ⇒ 该行保持 running、last_error 空
CLI 端到端（limit=1）: 该僵尸占闸 ⇒ WORKER_EXIT=0 iterations=1 consumed=0（库中另有 pending job 也领不到）
对照（UTC 口径回填的同类行）: STALE_RECLAIMED n=2 to_pending=1 to_failed=1 ⇒ 正常回收
```
**判定**：`updated_at` 在同一列里存在**两种时钟基准**（领取/回收语句写本地时间；Prisma `@updatedAt` 写 UTC）⇒ 回收器只对 UTC 基准行有效；生产真实僵尸（领取后崩溃）需等 `TZ 偏移 + 阈值`（本环境 ≈ 8 h15 min）才可能被回收。
**最小复现（可直接粘贴）**
```bash
# 1) 造一条"领取路径"僵尸（用 worker 自己的 claim SQL）
mysql ... -e "INSERT INTO grading_jobs(assignment_id,checker_id,status,attempts,created_at,updated_at)
  VALUES(<任一作业 id>,'sha256:probe','pending',0,NOW(3),NOW(3));
  UPDATE grading_jobs SET status='running',attempts=attempts+1,updated_at=CURRENT_TIMESTAMP(3) WHERE checker_id='sha256:probe';"
# 2) 看偏移（本环境应为 -28799 ≈ +08:00）
mysql ... -e "SELECT TIMESTAMPDIFF(SECOND,updated_at,UTC_TIMESTAMP(3)) FROM grading_jobs WHERE checker_id='sha256:probe';"
# 3) 用极小阈值回收（应回收却不会回收）
node -e "import('./src/services/dshStaleJobReclaimer.js').then(async m=>{const {PrismaClient}=await import('@prisma/client');
  const p=new PrismaClient();console.log(JSON.stringify(await m.reclaimStaleRunning({prisma:p,staleMs:1000})))})"
# ⇒ n=0 且该行仍为 running（若把 nowMs 减去 TZ 偏移，同一行即可被回收 ⇒ 偏移量即因）
```
**要求修复（任选其一，但必须让"判据与写入口径一致"）**
1. **判据侧统一到 DB 时钟**（推荐）：阈值比较改为数据库时间，如
   `WHERE status='running' AND updated_at < (NOW(3) - INTERVAL ? SECOND)`（`staleMs/1000`），并去掉 JS `toISOString()` 折算；或
2. **写入侧统一到 UTC**：把领取语句/回收语句的 `CURRENT_TIMESTAMP(3)` 改为 `UTC_TIMESTAMP(3)`（须同时审视 Prisma 侧写入与所有读 `updated_at` 的逻辑）；或
3. **会话时区固定**：在连接串/连接池上固定 `time_zone='+00:00'`（并回归全部时间字段语义），使 `CURRENT_TIMESTAMP` 与 `toISOString()` 同基准。
   无论选哪种，**必须**补一条"以真实领取 SQL 造僵尸"的回归用例（替换/补充 w42 的 `backdate()` 口径），否则仍是假绿。

## 3 ①两向回收与摘要一致性（UTC 口径夹具）
| 夹具 | attempts | 回填口径 | 回收后 | last_error |
|---|---|---|---|---|
| stale-pending | 1 | UTC(20 min 前) | `pending` | `stale_running_reclaimed` |
| stale-exhausted | 3 | UTC(20 min 前) | `failed` | `stale_running_exhausted` |
| fresh | 1 | 不回溯 | `running`（未动） | `null`（不在 details） |
摘要：`STALE_RECLAIMED n=2 to_pending=1 to_failed=1 conflicts=0 stale_ms=900000`；DB 复核（按 assignment 统计）与摘要一致；二次调用 `n=0`（幂等）。

## 4 ②不误伤 / ③活动键防御 / ④闸
- 不误伤：fresh running 保持 running、`last_error=null`、`details` 不含该 id；CLI 场景 `n=0` 时无任何行被改。
- 防御分支（假 prisma 直测）：候选僵尸 + 同对已有 pending ⇒ `status=failed`、`reason=stale_running_active_key_conflict`、`to_failed=1 conflicts=1 to_pending=0`，UPDATE 参数为 `('failed','stale_running_active_key_conflict')` ✓。
- DB 层：同对第二条活动行插入 ⇒ **P2002**（`uniq_grading_jobs_active_key`）⇒ 活动行恒为 1 条 ✓（回收不会造出第二条活动行）。
- 闸：UTC 口径僵尸回收后 worker `consumed=1`（正常领取/消费）；**生产口径僵尸**回收 `n=0` ⇒ `consumed=0`（limit=1 下其它 pending job 也领不到）⇒ 闸未解锁（F-T65-1 的后果）。
