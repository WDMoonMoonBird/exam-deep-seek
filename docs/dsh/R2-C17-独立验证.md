# R2-C17 独立验证（僵尸 running 回收 + 定时形态运维配方）

## 结论摘要（10 行）
1. **verdict = needs_revision（status=failed）**：t64 的回收机制在 "w42 测试口径" 的时间戳下成立，但在**生产真实领取路径**下**不成立**——领取语句写 `CURRENT_TIMESTAMP(3)`（DB 会话本地时区 +08:00），回收阈值却用 `toISOString()`（UTC）⇒ **真僵尸不会被回收**，DB 闸持续被占（实测 `STALE_RECLAIMED n=0`、job 保持 `running`、worker `consumed=0`）。
2. **★F-T65-1（阻断级）时区错配**：实测**领取路径行**满足 `TIMESTAMPDIFF(SECOND, updated_at, UTC_TIMESTAMP(3)) = -28799`（`updated_at` 超前 UTC 约 8 h）⇒ 判据永远追不上，僵尸需等 **≈ TZ 偏移 + 阈值（本环境 ≈ 8 h15 min）**；机制的核心目的（崩溃后快速自愈、解除静默停摆）在生产口径下**落空**。
3. **★测试假绿（同因）**：w42 的 `backdate()` 用与回收器**同一** `toISOString()` 口径写夹具 ⇒ 夹具与判据同错相消、测试全绿而真实路径失效；最小复现见 §2。
4. **①两向回收（UTC 口径夹具下）【成立】**：`STALE_RECLAIMED n=2 to_pending=1 to_failed=1 conflicts=0`；attempts=1 ⇒ `pending/stale_running_reclaimed`、attempts=3 ⇒ `failed/stale_running_exhausted`；摘要数字与 DB 行数一致；二次调用 `n=0`（幂等）。
5. **②不误伤【成立】**：`updated_at` 新的 running 保持 `running`、`last_error=null`、不在 `details` 中（CLI 亦实测 `n=0` 时无改行）。
6. **③活动键防御【成立】**：假 prisma 直测 ⇒ `failed` + `stale_running_active_key_conflict`（`to_failed=1 conflicts=1 to_pending=0`）；DB 层同对第二条活动行 ⇒ **P2002**、活动行恒 1 条。
7. **④解锁闸【UTC 口径成立 / 生产口径失败】**：UTC 口径僵尸回收后 worker 正常领取消费（`consumed=1`）；**生产口径僵尸 ⇒ `n=0` ⇒ `consumed=0`（limit=1 下其它 pending job 也领不到）⇒ 闸未解锁**（F-T65-1 的直接后果）。
8. **⑤fail-soft【成立】**：不可达 DB ⇒ `skipped=reclaim_failed:` + `STAGE=connect` 正常尝试 + `WORKER_EXIT=0 … failures=1`、rc=0 ⇒ 既有语义未破坏。
9. **⑥配置【成立；两条建议】**：缺省 900000 ms（15 min）、`'60000'`⇒60000、`'abc'/'0'/'-1'`⇒回退；`parseWorkerConfig` 暴露（env 45000/'xx'⇒45000/900000）；`WORKER_START … stale_running_ms=60000` 实测打印 ✓；**默认约定安全**（worker `--timeout-ms` 600 s < 阈值 900 s）且配方显式写 900000 ✓；但**未对 `--timeout-ms > 阈值` 告警**（O-2）。
10. **⑦回归【不可判定 + 1 项失败】**：本轮 verify 运行时 B 正于 15:24 起改同一模块（R2-B18，含 w42/w43）⇒ unit 运行中断（2 套件失败）、integration 21 套件失败（30 处 `PrismaClientKnownRequestError`，DB 层）；**w42 单跑 3/6 失败** ⇒ 判据不可判定；生产零写入 ✓、装置侧零改动 ✓、探针残留 0 ✓（详见 §6/§7）。

## 2 ★F-T65-1（阻断级）时区错配：证据 + 最小复现 + 要求修复
**已实测**
```
DB 会话: @@session.time_zone=SYSTEM；NOW(3)=15:20:04(+08) vs UTC_TIMESTAMP(3)=07:20:04 ⇒ 偏移 +28800 s
领取路径（dshGradingJobWorker.js:155-156）: ... updated_at = CURRENT_TIMESTAMP(3) WHERE id=? AND status='pending'
旧判据（t64 版 dshStaleJobReclaimer.js）: new Date(nowMs-staleMs).toISOString().slice(0,23).replace('T',' ') ⇒ UTC 字面量
实测（领取路径产生的行）: TIMESTAMPDIFF(SECOND, updated_at, UTC_TIMESTAMP(3)) = -28799 ⇒ 超前 UTC ≈ 8 h
回收实测: STALE_RECLAIMED n=0（stale_ms=1000）⇒ 该行保持 running、last_error 空
CLI 端到端: STALE_RECLAIMED n=0 ⇒ WORKER_EXIT=0 iterations=1 consumed=0（闸仍被占）
对照（UTC 口径回填）: STALE_RECLAIMED n=2 to_pending=1 to_failed=1 ⇒ 正常回收
```
**最小复现（可直接粘贴；`<id>` 换任一测试库作业 id）**
```bash
mysql … exam_system_test -e "INSERT INTO grading_jobs(assignment_id,checker_id,status,attempts,created_at,updated_at)

```
**要求修复（三者取一，但必须"判据与写方同源"）**：① 判据下推到 DB 时钟（`updated_at < NOW(3) - INTERVAL ? SECOND`，推荐）；② 写方改用 `UTC_TIMESTAMP(3)`（并复核所有读写该列的逻辑）；③ 连接层固定 `time_zone='+00:00'`。**并必须**补一条"以真实领取 SQL 造僵尸"的回归用例替代/补充 w42 的 `backdate()` 口径，否则仍为假绿。
**修复现状（披露）**：B 于 15:24 起在工作树实现 ①（R2-B18：`STALE_CLOCK_SQL='NOW(3)'`、`buildStale{Select,Update}Sql`、`staleSeconds`、`checkTimeoutVsStale`，注释明确引用"t65 判定的阻断缺陷"），并新增 `w43-stale-clock-parity.test.js`；但**当前 w42 单跑 3/6 失败**（W42-2 未超阈值被误回收、W42-3b 假 prisma 期望不符）⇒ 修复在飞、尚不可验收。

## 4 ②不误伤 / ③活动键防御 / ④闸
- 不误伤：fresh running 保持 running、`last_error=null`、不在 `details`。
- 防御（假 prisma）：目标 `failed` + `stale_running_active_key_conflict`，UPDATE 参数 `('failed','stale_running_active_key_conflict')`，`conflicts=1` ✓。
- DB 层：第二条活动行 ⇒ P2002 ⇒ 活动行恒 1 条 ✓（回收不会造出第二条活动行）。
- 闸：UTC 口径僵尸回收后 worker `consumed=1`；**生产口径僵尸回收 `n=0` ⇒ `consumed=0` ⇒ 闸未解锁**（F-T65-1）。
