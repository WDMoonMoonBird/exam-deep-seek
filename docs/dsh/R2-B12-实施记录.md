## 2 ②schema 变更与 BCNF 说明
### 2.1 为什么是「状态入键」的问题
- 原键 `(assignment_id, checker_id, status)` 想表达「同一 (作业, 尺子) 只能有一个 pending」；但它把**状态**这一非键属性并入了候选键 ⇒ 副作用是**任何状态**都只能一行 ⇒ 与「终态要留历史（重跑多次各留一行）」这一业务语义冲突，且第二次失败记账直接 P2002。
- 规范表述：业务不变式是「**活动态**下每 (assignment, checker) 至多一行」，即对**子集**（status ∈ 活动态）的函数依赖 `(assignment, checker) → 活动行`，而非对全集唯一 ⇒ 用**部分唯一索引**（partial/active key）表达才保真。
### 2.2 实现（迁移 SQL 要点）
```sql
ALTER TABLE `grading_jobs` ADD COLUMN `active_key` VARCHAR(96)
  GENERATED ALWAYS AS (CASE WHEN `status` IN ('pending','running')
    THEN CONCAT(`assignment_id`, ':', `checker_id`) ELSE NULL END) STORED;
DROP INDEX `uniq_grading_jobs_assignment_checker_status` ON `grading_jobs`;
CREATE UNIQUE INDEX `uniq_grading_jobs_active_key` ON `grading_jobs` (`active_key`);
```
- 终态 → `active_key = NULL`；MySQL 唯一索引对 NULL **不去重** ⇒ 终态天然可多行 ✓（无需 partial index 语法）。
- `rollback.sql`：删索引 → 删列 → 还原旧三列唯一索引；⚠️ 回滚前需先归并**同状态**重复行（脚本注释给出 DELETE SQL）。
- **迁移前检查**：`SELECT assignment_id, checker_id, COUNT(*) FROM grading_jobs WHERE status IN ('pending','running') GROUP BY 1,2 HAVING n>1;` 测试库实测 **0 行** ⇒ 直接建索引；若命中需先归并（SQL 写在迁移注释里）。
- **Prisma 边界（已写进 schema.prisma 注释）**：生成列无法用 Prisma 语法表达 ⇒ 未写进 `schema.prisma`，由原始 SQL 迁移管理；`schema.prisma` 里只**移除**了旧的 `@@unique`（保持模型与 DB 的其余部分一致）。
