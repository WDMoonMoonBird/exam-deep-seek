## 6. 运维结论（部署后旧标签页）与云上只读命令
**核对方式（旧标签页为什么会坏）**：旧标签页请求的是**旧哈希** asset；若服务端已 `rsync --delete`，该文件不存在 ⇒ 返回 **404 + text/html**（而不是 JS）⇒ 动态 import 拒绝 ⇒ 旧版无接管 ⇒ 空白（本批自愈前）。
```bash
# ① 缺失 chunk 的真实状态（把 <旧哈希文件> 换成旧标签页 Network 里报 404 的那个）
curl -s -o /dev/null -w 'missing_chunk: %{http_code} %{content_type}\n' https://<host>/exam/assets/<旧哈希文件>.js
# ② 当前 index.html 引用的入口（版本探测锚点；与页面内构建号比对）
curl -s https://<host>/exam/ | grep -oE '/exam/assets/index-[A-Za-z0-9_-]+\.js' | head -1
# ③ 云上生产表数应为 29（含批次4 的 grading_summaries）
mysql -N -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=DATABASE();" <云上库>
mysql -N -e "SHOW TABLES LIKE 'grading_summaries'; SELECT COUNT(*) FROM grading_summaries;" <云上库>
# ④ 会话内自愈是否真的救了旧标签页（近端日志/前端上报若接入）
grep -c 'R2-B52' /var/log/nginx/access.log 2>/dev/null || true
```
**建议**：①发布时**保留上一版 assets**（版本化目录或 `rsync` 不带 `--delete` 于 assets，仅替换 index.html）⇒ 旧标签页仍可加载旧 chunk；②入口加**版本探测**（轮询 `/exam/index.html` 的入口哈希，变化即提示"有新版本，点此刷新"）；③保留 B52 的自愈作为最后一道防线（reload-once + 防循环 + 边界 + 全局提示）；④云上按 §5.2 核对表数 29。
