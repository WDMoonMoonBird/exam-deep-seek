# 已知实现坑 01：`$var` 紧跟多字节（全角）字符 ⇒ unbound variable ⇒ 覆盖退出码

## 现象
- 装置在**应当以非 0 退出**的场景（例：`R3.5-B S3` 篡改 frozen ⇒ 应 `exit 3`）反而以 `exit 1` 结束 ⇒ 上层断言报「篡改未被拦」。
- 日志里出现 `line N: <奇怪的名字>: unbound variable`（名字里含着全角标点，如 `rc）`）。
- 变量**其实已设置**也会中招；`|| true`、`2>/dev/null`、`if …` 都拦不住（bash 直接中止，不是普通命令失败）。

## 最小复现（零写入，A 提供，已实测）
```bash
bash -c 'set -euo pipefail; cleanup(){ local rc=$?; echo "boom=$zz）" || true; exit "$rc"; }; trap cleanup EXIT; echo RUN_EXIT=3; exit 3'
# 实测 observed_rc=1（把全角括号去掉 ⇒ 3）
```

## 机制
- macOS 自带 bash 3.2 + `LC_CTYPE=C.UTF-8`：变量名扫描按字节进行，遇到多字节字符不会停下 ⇒ `$rc）` 被当成变量名 `rc）`（把全角字节吞进名字）⇒ 在 `set -u` 下触发 unbound ⇒ bash **立即以 1 退出**。
- 危险形态：`$name` **非** `${name}`，且紧跟的字节 ≥ 0x80（全角标点、中文、emoji、`、`、`）`、`，`、`：` 等）。
- 典型位置：**日志/证据字符串**（`echo "… exit=$rc）…"`）、`local x=$?` 后的 `echo`、`printf` 拼接。

## 修法（行为不变，仅定界）
```bash
echo "exit=$rc）"      # ✗ 危险
echo "exit=${rc}）"    # ✓ 定界
```
- 清理/收尾代码的加固三步：trap 内先 `local rc=$?` 保存原码 → 内部 `set +u` → 全程 `|| true` → 末尾 `exit "$rc"`；**任何非 0 路径必须原样返回该码**。

## 静态防线（防复发）
- 脚本：`scripts/dsh-grader/scan-unbraced-vars.sh`（只读）
  - 无发现 ⇒ `SCAN_OK files=<n>` 退 0；有发现 ⇒ 逐条 `SCAN_FINDING <file>:<line> …` + `SCAN_FINDINGS n=<x>` 退 1。
  - 扫描范围缺省 `<repo>/scripts/**`；`--path <目录>` 供正/反例自测。
- `scripts/dsh-grader/selftest.sh` 已加一条断言调用它（正例全仓 + 反例注入夹具 ⇒ rc=1）。
- 实现细节：正则 `(?<![$\\{])\\$[A-Za-z_][A-Za-z0-9_]*([\\x80-\\xff])`（只挑 `$name` 形式；`${name}` 安全）。

## 四轮误诊教训（t76→t84）
1. **症状会指向错误方向**：表现是「防篡改失效」，真因却是「退出码被 bash 中止覆盖」⇒ 先对拍**退出码**与 `unbound variable`，再谈业务断言。
2. **别在同一层反复试**：teardown 先内联（t76 61/21）、再收敛为 trap 函数（t79 83/2）、再改销毁粒度（t80 仍红）——三轮都在装置层打转；fork 实验（`DSH_GRADER_PURGE_HOME=0` 完全不销毁仍红）才证明与销毁无关。
3. **测试改动要「逐条判必要性」**：w15 的假 prisma 用**位置参数猜语义**，被新增的汇总 INSERT 误判为「领取」⇒ 真因是夹具判别力，非产品回归。
4. **把坑固化成防线**：一条字节级扫描 + 一条 selftest 断言，比任何一次口头提醒都可靠。

## 坑 2：`prisma migrate diff --to-schema-datamodel` 生成的 SQL **不能**直接打到已有库

**现象**：对本地开发库跑 `npx prisma migrate diff --from-url <库> --to-schema-datamodel prisma/schema.prisma --script`，产出的差量里包含：
```sql
DROP INDEX `uniq_grading_jobs_active_key` ON `grading_jobs`;   -- ★防重复领取的唯一索引
ALTER TABLE `grading_jobs` DROP PRIMARY KEY, DROP COLUMN `active_key`, …;
```
**机制**：`grading_jobs.active_key` 是**用 raw SQL 迁移建的生成列**（`CONCAT(assignment_id,":",checker_id)` + 仅 pending/running 生效的唯一索引），**没有在 `schema.prisma` 里建模**（Prisma 无法建模生成列）⇒ 对 Prisma 而言这个列/索引是"多余物"，差量自然要删掉它。
**危害**：照单执行会**拆掉并发安全闸**（重复领取/双写风险回归），而且 `DROP COLUMN` 直接丢数据。
**正确做法**：
1. 已有库补迁移 ⇒ **只逐条应用我们自己的 `prisma/migrations/*/migration.sql`**（只补缺的那些），不要用差量 SQL；
2. 判断"缺哪些"用**对象存在性检查**（`information_schema.tables/columns`），不要用 Prisma 差量；
3. 任何 DDL 之前**先备份**，之后**核对行数与关键列/索引是否仍在**（本轮即靠 `active_key` 列+唯一索引双检查确认没被误删）；
4. 云上那次之所以能用差量（0 条 DROP），是因为云端是**全新表**、不存在 raw-SQL 生成列 ⇒ 结论不能推广。
**同类风险**：`prisma db push` 到已有库（同样会把 raw-SQL 生成列当作多余物）。
**坑 2 的镜像面（2026-10-13 云上实测发现）**：用 `migrate diff`/`db push` **建新表**时，raw-SQL 生成列同样会**缺席**（不是被删，而是从来没建）。
实例：云上 `grading_jobs` 由差量 SQL 从 `schema.prisma` 建出 ⇒ **没有 `active_key` 生成列与 `uniq_grading_jobs_active_key` 唯一索引** ⇒ 并发安全闸在云上**一直缺失**（单 worker 时不显形，一旦多 worker 就会重复领取）。
发现方式：真机复核时做列清单对拍（本地 vs 云上）⇒ `active_key=0`。
修复：预检「重复活动行数=0」→ `ADD COLUMN active_key … GENERATED … STORED` → （旧三列唯一索引存在才）`DROP INDEX` → `CREATE UNIQUE INDEX uniq_grading_jobs_active_key` ⇒ 双校验通过（列=1、索引=1）。
**结论**：凡是用 Prisma 差量/db push 打过或建过表的库，都要**逐列对拍 raw-SQL 产物**（生成列、唯一索引、CHECK 等），差量既不认识它们、也不会替我们建。
