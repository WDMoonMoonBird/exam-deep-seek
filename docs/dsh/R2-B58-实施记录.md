# R2-B58 实施记录：自助改密码策略（强度校验 + 原密码错误限速）

> 摘要（≤10 行）：① 用户拍板「要」⇒ 采纳强度校验（≥8 位 / 含字母与数字 / 不得与原密码相同）**仅用于自助改密码**（`PUT /auth/password`，`authController.changePassword`）；
> ② 原密码错误**限速**：连续 **5 次** ⇒ 锁定 **15 分钟**（内存 `Map`，**重启即清零**、多实例各自计数）；锁定期间即使原密码正确也返回 **429**「原密码错误次数过多，请 N 分钟后再试」；**成功一次即清零**；
> ③ 顺序：**锁定判定 ⇒ 强度校验 ⇒ 原密码校验（计数）⇒ 落库并清零**；强度失败**不计入**错误次数（避免用户被自己的输入错误锁死）；
> ④ 日志只记 `userId` + 原因分类（`too_short`/`need_letter_digit`/`same_as_old`/`bad_old_password`/`lock_triggered`/`locked`），**不记明文/哈希**；响应体不回显任何密码；
> ⑤ 前端三端（teacher/student/admin 的「我的信息」）加**同一套**规则提示与提交前本地拦截（`composables/passwordPolicy.js`，文案与后端逐字一致），后端业务消息仍经 `errorCopyOf` 上屏；
> ⑥ **「使既有 token 失效」本批不动**（需改表结构 + 鉴权中间件，见 §5 方案与成本）；⑦ 测试：新增 w67 单测+API 用例 **21/21**；⑧ 回归：verify-frontend（含构建）**39/39 rc=0**、jest w67+w52+w61+w62 全绿、check-layers 141 文件 0 违规、指纹按环境 29/28/30。

## 1. 规则与文案（后端权威，前端同口径）
| 规则 | 触发条件 | HTTP | code | 中文消息 |
|---|---|---|---|---|
| 长度 | `newPassword.length < 8` | 400 | 1001 | 「新密码至少 8 位」 |
| 字母+数字 | 不同时含 `[A-Za-z]` 与 `[0-9]` | 400 | 1001 | 「新密码需同时包含字母和数字」 |
| 不得与原密码相同 | `newPassword === oldPassword` | 400 | 1001 | 「新密码不能与原密码相同」 |
| 原密码错误 | `bcrypt.compareSync` 失败且未达阈值 | 400 | 1001 | 「原密码错误」 |
| 达到阈值/锁定中 | 连续 5 次原密码错误 | **429** | 1002 | 「原密码错误次数过多，请 15 分钟后再试」（锁定中为剩余分钟数） |
- 非法输入（`undefined`/数字/空）按长度不足处理，**不抛**；`oldPassword` 非字符串不会绕过 bcrypt 校验（先转字符串再比）。

## 2. 限速参数与取舍
- 参数：`PWD_FAIL_THRESHOLD = 5`、`PWD_LOCK_MS = 15 * 60 * 1000`、计数键 = `userId`（登录后已知，无需额外维度）。
- 存储：进程内 `Map`（**重启即清零**）——取舍：零依赖、零迁移、无 Redis 依赖；代价是多实例/重启后计数不共享（可接受的"软限速"）；若将来要强一致，可换 Redis/DB 计数（记录在案）。
- 行为：达阈值的那一次**即返回锁定文案**（而非先 400 再等下次）；锁定期间任何改密请求先被拒（**包括原密码正确**）；`clearOldPasswordFailures` 在**成功落库后**调用。
- 不影响其它路径：限速表只在 `changePassword` 内读写（W67-5 静态断言：策略函数只在 `authController.js` 出现）；锁定期间**登录**与其它带令牌接口均正常（API 用例断言）。

## 3. 校验顺序（为何这样排）
```
① lockRemainingMs(userId) > 0  ⇒ 429（最省资源，且锁定优先级最高）
② validateSelfServicePassword(old, new)  ⇒ 400（**纯函数、不计数** ⇒ 用户不会因"输入太弱"被锁）
③ bcrypt.compareSync(old, user.password) 失败 ⇒ noteOldPasswordFailure(userId) ⇒ 400 / 达阈值 429
④ 成功：hashSync(new) + update + clearOldPasswordFailures(userId) ⇒ 200
```
- 理由：先做**无副作用**的限速判定，避免为已锁定用户白跑 bcrypt（bcrypt 是慢哈希，正是暴力破解的成本点）；强度校验放在原密码校验**之前**，使"弱密码 + 错原密码"优先得到可操作的提示，且**不计入**计数 ⇒ 不会被自己的弱口令锁死。
- 安全：强度失败不计数（W67-2 断言 6 次强度失败后仍可成功改密）；日志不含任何密码/哈希；响应不含新密码（W67-1 断言）。

## 4. 前端三端（与后端一致）
- 新增 `client/src/composables/passwordPolicy.js`：`PWD_MIN_LEN=8`、`PASSWORD_RULE_TEXT`（「密码至少 8 位，且需同时包含字母和数字」）、`localPasswordIssue({oldPassword,newPassword,confirmPassword})`（顺序：非空 ⇒ 长度 ⇒ 字母+数字 ⇒ 不得与原密码相同 ⇒ 两次一致）与 `PWD_MSG`（四条文案与后端逐字一致）。
- teacher/student/admin 三端 `Layout.vue`：表单内新增 `<p class="pwd-rule-hint">{{ PASSWORD_RULE_TEXT }}</p>`；`changePassword()` 在发请求前 `const issue = localPasswordIssue(pwdForm); if (issue) return message.warn(issue);` ⇒ **本地拦截**；catch 统一 `message.error(errorCopyOf(e, { tag, action: '修改' }))`（服务端业务消息优先上屏，其余固定友好文案，原始错误只进 console）。
- 注意：teacher/student 的 catch 由原来的 `e?.response?.data?.message || '修改失败'` 收敛到 `errorCopyOf`（同样满足 B55 口径，行为等价）。

## 5. 「使既有 token 失效」（用户第二项需求，**本批只上报，不动代码**）
- 方案 A（推荐）：`User` 增加 `password_changed_at DATETIME NULL` + JWT 签发时把 `iat` 与库值比较 ⇒ 改密后**所有旧令牌**在下一次请求即 401。成本：1 个迁移（新列）+ `middleware/auth.js` 一次查询（可按 userId 缓存 60s 降频）+ 前端 401 既有处理（跳登录）。
- 方案 B（最省）：`User.token_version INT DEFAULT 0`，JWT 带 `ver`，改密 `ver+1` ⇒ 校验只需比对令牌内的 `ver` 与库值（无时间语义、实现直观）。成本：同上（1 迁移 + 中间件 1 行比对）。
- 方案 C（零迁移）：把 JWT 有效期从当前值缩短 + 前端在改密成功后主动 `logout()`（只解决"本机"）；**不能**覆盖"别处的会话"⇒ 不作为安全方案。
- 现状事实（本批实测）：改密成功后**旧 token 仍然有效**（W67-3 用旧 token 继续调用成功）—— 因此方案 A/B 落地前，改密**不等于**踢下线；建议纳入下一批（属 `server/prisma/` + `server/src/middleware/`，本批 out of scope）。
